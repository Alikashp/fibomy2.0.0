## 1. Контекст и цель

### 1.1 Что есть сейчас
Telegram-бот (aiogram 3 + ARQ + Playwright) генерирует PDF по 4 HTML-шаблонам, которые жёстко привязаны к типу презентации. Один большой LLM-вызов возвращает JSON со слайдами и layout'ом для каждого слайда. Среднее время генерации около 21 с. Подробный разбор: `docs/CURRENT_STATE.md`.

### 1.2 Проблемы, которые решаем
1. **Однообразие.** В колоде повторяется один и тот же вид слайда: layout выбирается из небольшого набора, а визуал определяется типом презентации.
2. **Контент подгоняется под макет.** Модель выдумывает даты для таймлайна, пишет длинный текст, который вылезает из рамки, и оставляет пустые колонки. Нужно наоборот: макет выбирается под форму контента.
3. **Только PDF.** Пользователь не может отредактировать результат, а это главный барьер для взрослой и корпоративной аудитории.
4. **Цифры из документов теряются.** Таблицы docx пропускаются, данные не превращаются в графики.
5. **Нет API** для подключения к другому боту.

### 1.3 Цель
Новый движок генерации, в котором:
- для каждого **типа контента** есть пул из 4–5 **вариантов представления**, а поверх накладываются **темы оформления**, поэтому две презентации на одну тему выглядят по-разному;
- результат отдаётся одновременно в **PDF и редактируемом PPTX** с нативными объектами (текст, фигуры, таблицы, диаграммы);
- на вход принимаются тема, текст или файл (pptx, docx, pdf, txt);
- время от нажатия кнопки до файла у пользователя **не больше 120 с** (p95, без очереди);
- есть REST API.

### 1.4 Что НЕ входит в задачу
- Загрузка пользовательского шаблона или брендбука.
- Веб-интерфейс.
- Несколько вариантов колоды на выбор (отдаём одну).
- LLM-аудит на проде.
- Правки слайдов через API.

## 2. Пользователи и сценарии

| Сегмент | Доля сейчас | Типовой запрос | Что критично |
|---|---|---|---|
| Студенты | основная | доклад, защита проекта или курсовой | структура по канону (актуальность, цели, выводы), титул с ФИО и группой, скорость, цена |
| Преподаватели | заметная | лекция, методичка → слайды | работа с длинным документом, точность фактов |
| Корпоративные сотрудники | целевая | отчёт о результатах, презентация проекта, питч | цифры → графики, редактируемый PPTX, сдержанный деловой вид |

**Решение:** визуально закладываемся под корпоративный уровень (сдержанные темы, сетка, аккуратная типографика). Студентам это тоже подходит, а обратное не работает: «весёлый» визуал отталкивает корпоративных пользователей.

## 3. Функциональные требования

### 3.1 Входные данные [MVP]

| Вход | Лимит | Как обрабатываем |
|---|---|---|
| Тема | 3–300 символов | генерация «из знаний модели» (см. правила фактов, 3.3.3) |
| Текст | до 30 000 символов в сообщении | используется как источник |
| Файл .docx | до 20 МБ, до 100 000 символов текста | абзацы + **таблицы** (сейчас пропускаются, это баг) |
| Файл .pptx | до 20 МБ, до 100 слайдов | текст, заметки, **таблицы и данные нативных диаграмм** |
| Файл .pdf | до 20 МБ, до 50 страниц | текст + таблицы (pdfplumber); сканы без текста → понятная ошибка пользователю |
| Файл .txt | до 2 МБ | chardet для определения кодировки |

**Обработка длинного входа:**
- Если извлечённый текст не больше ~40 000 символов, в LLM он уходит целиком.
- Если больше, текст режется на части по ~15 000 символов. Части **параллельно** прогоняются через шаг «выжимка»: тезисы + все числа, даты и таблицы с привязкой к месту в документе. Результат склеивается в `SourceDigest`.
- Если вход превышает лимит, обрабатываем начало документа и **явно предупреждаем** пользователя, какой объём не вошёл. Молча терять хвост, как сейчас, нельзя.
- Лимиты вынесены в конфиг и могут отличаться по тарифу.

**Безопасность файлов:** docx и pptx — это zip-архивы. Проверяем размер после распаковки (не больше 200 МБ) и количество файлов в архиве, чтобы защититься от zip-бомбы. Парсинг идёт с таймаутом 15 с.

**Структурированные данные.** Все таблицы и ряды чисел из входа извлекаются в `SourceDigest.datasets` (название, колонки, строки, единицы измерения, место в источнике). Эти данные — единственный источник для диаграмм в режиме «по документу».

### 3.2 Параметры генерации [MVP]

| Параметр | Значения | По умолчанию |
|---|---|---|
| `slides_count` | 4–20 | зависит от типа презентации |
| `language` | список из 15 языков (см. 11, вопрос 3) | язык интерфейса пользователя |
| `presentation_type` | доклад, защита проекта, отчёт о результатах, питч, лекция, общая | общая |
| `audience` | как сейчас | — |
| `theme` | id темы или `auto` | `auto` (случайная из подходящих) |
| `image_mode` | `none` / `web` / `ai` | `web` |
| `author` | ФИО, группа/должность (для титула) | из профиля |
| `source_mode` | `strict` — только материал пользователя; `extend` — материал + общие знания (правила — 3.3.3). Только если приложен файл или текст, в режиме «по теме» не используется | бот: последний выбор из профиля; API: `strict` |
| `speaker_notes` | вкл/выкл | [v1.x] |

**Вопрос о `source_mode` в боте** *(решение по вопросу 10 раздела 11, 26.09.2026):*
- задаётся, **только если пользователь приложил файл или прислал текст**; в режиме «по теме» вопроса нет;
- две кнопки: «Только мой материал» (`strict`) и «Дополнить общими знаниями» (`extend`);
- выбор запоминается в профиле пользователя и в следующий раз подставляется по умолчанию: прошлый вариант стоит первым и отмечен «как в прошлый раз».

**Ключевое изменение:** тип презентации управляет **структурой повествования** (набором и порядком смысловых блоков), а не визуалом. Визуал определяется темой и вариантами макетов. Сейчас эти вещи склеены в 4 шаблонах, и мы их разделяем.

### 3.3 Структура и контент

#### 3.3.1 Сценарии повествования [MVP]
Для каждого `presentation_type` — отдельный файл `prompts/storylines/<type>.yaml` с каноном блоков. Пример для доклада: титул → актуальность → цель и задачи → основная часть (N блоков) → результаты → выводы → финал. LLM адаптирует канон под объём и тему, но не выкидывает обязательные блоки.

#### 3.3.2 Типы контента (content kinds) [MVP]
На этапе плана LLM для каждого слайда определяет **тип контента** — какую форму имеет информация. Сам макет модель **не выбирает**.

| kind | Когда применяется | Обязательные данные |
|---|---|---|
| `title` | первый слайд | заголовок, подзаголовок, автор |
| `agenda` | содержание (для 8+ слайдов) | 3–6 пунктов |
| `section` | разделитель частей (для 12+ слайдов) | название части, номер |
| `statement` | одна главная мысль, цитата, вывод | 1 утверждение ≤ 20 слов, опц. пояснение |
| `bullets` | 3–6 равноправных пунктов | пункты: заголовок ≤ 6 слов + текст ≤ 20 слов |
| `comparison` | 2–3 объекта по одним критериям, «за/против», «до/после» | объекты + пары пунктов |
| `process` | 3–6 упорядоченных шагов **без дат** | шаги, флаг `cyclic` |
| `timeline` | события с **реальными датами** из источника | 3–6 пар «дата — событие» |
| `metrics` | 1–4 ключевых числа | значение, единица, подпись |
| `chart_series` | ряд чисел по времени или категориям | dataset: категории + 1–5 серий |
| `chart_share` | доли целого (сумма около 100%) | 2–6 долей |
| `table` | объекты × атрибуты | до 6 строк × 5 колонок |
| `image_focus` | слайд, где главное — изображение | картинка + подпись |
| `conclusion` | итоги, выводы | 2–5 выводов |
| `closing` | финальный слайд | благодарность / вопросы / контакты |

**Правило, которое закрывает баг с выдуманными датами:** `timeline` разрешён только если даты есть в источнике или являются общеизвестными историческими фактами. Этапы без дат — это `process`. Проверяется кодом: у `timeline` каждое событие обязано иметь дату, которая парсится.

#### 3.3.3 Правила фактов [MVP]
- **Режим «по документу»** (файл или текст пользователя): каждое число на слайде обязано найтись в `SourceDigest`. Проверка детерминированная (нормализация чисел: пробелы, запятые, %, единицы). Если число не найдено, слайд перегенерируется один раз с указанием на ошибку. Если число снова не найдено, `metrics` или `chart_*` деградирует в `bullets` без этого числа. Проверка одинакова для обоих значений `source_mode`.
  - **`strict` — только материал.** Все утверждения — из материала. Слайдов **не больше выбранного**, минимум 5. Если самостоятельных мыслей в материале меньше, колода делается короче (повторы и добор недопустимы, 4.8.4), а пользователь получает сообщение, например: «В материале хватило на 7 слайдов — добавьте текст, если нужно больше».
  - **`extend` — материал + общие знания.** Слайдов **ровно столько, сколько выбрано**. Недостающие слайды дополняются общими знаниями по теме — пояснения, контекст, определения, — но **без конкретных чисел, дат и ссылок на источники**. Числа и даты — только из материала; утверждения из общих знаний не выдаются за данные материала.
- **Режим «по теме»** (файла и текста нет):
  - числа допустимы **только как оценка**. На каждый слайд, где есть число, код добавляет сноску «Оценочные данные — проверьте перед показом»;
  - ссылки на конкретные отчёты, исследования и организации («Grand View Research, 2024», «отчёт отдела маркетинга») запрещены;
  - поле `source` модель не заполняет — его проставляет код (в этом режиме — той же сноской);
  - типы `chart_series` и `chart_share` по умолчанию отключены (см. 11, вопрос 2). Выдуманная диаграмма в студенческом докладе — прямой репутационный риск: преподаватель спросит, откуда цифры.

  Пример того, что эти правила закрывают, — `tests/fixtures/specs/prodazhi_topic_only.json`: выдуманные «2 млн руб.» и «+15%», источники «Отчеты отдела маркетинга», «Финансовая отчетность компании», противоречие «новых клиентов +30%» / «Новые клиенты 20%» на соседних слайдах (`docs/PROMPT_REVIEW.md`, 10.1–10.2).
- **Заголовки слайдов** формулируются как вывод, а не как тема: «Выручка выросла на 40% за счёт B2B», а не «Выручка». Исключения: `title`, `agenda`, `section`, `closing`.

### 3.4 Система макетов: варианты представления

#### 3.4.1 Пул вариантов
Для каждого `kind` описано 3–5 вариантов. Вариант — это декларативный файл `layouts/<kind>/<variant>.yaml` (формат в 4.3.2). Цель v1.0 — ~55 вариантов, MVP — 24.

| kind | Варианты (MVP выделены **жирным**) |
|---|---|
| title | **cover_center**, **cover_split_image**, **cover_band**, cover_minimal |
| agenda | **numbered_list**, cards_row, side_index |
| section | **big_number**, color_block, image_divider |
| statement | **big_quote**, **statement_image**, highlight_band, statement_icon |
| bullets | **icon_list**, **cards_grid**, **numbered_columns**, text_image_split, classic_list |
| comparison | **two_columns**, **pros_cons**, comparison_table, before_after |
| process | **horizontal_steps**, **chevrons**, vertical_steps, numbered_cards, cycle (только при `cyclic`) |
| timeline | horizontal_timeline, vertical_timeline, milestone_cards |
| metrics | **big_number**, **kpi_cards**, number_with_text, number_with_bar |
| chart_series | **column_chart**, **line_chart**, bar_chart, chart_with_insight, data_table |
| chart_share | **donut**, pie, stacked_100, share_cards |
| table | **native_table**, table_highlight, cards_matrix |
| image_focus | full_bleed_caption, split_image, image_grid |
| conclusion | **numbered_takeaways**, cards, single_message |
| closing | **thanks_center**, qa_contacts, closing_image |

MVP: 11 kinds, 24 варианта. `timeline`, `image_focus`, `agenda` и `section` в MVP деградируют в ближайший kind (`process`, `statement` и т.д.).

#### 3.4.2 Требования к каждому варианту
- Геометрия задаётся абсолютными координатами на логической сетке 1920×1080. 1 единица = 6350 EMU, что даёт точные 16:9 в PPTX (12 192 000 × 6 858 000 EMU).
- Для каждого слота указаны: тип (text / image / chart / table / shape / icon), бокс, текстовый стиль из типошкалы темы, **вместимость** (максимум строк и символов при базовом кегле, минимальный кегль).
- Указаны **ограничения применимости**: диапазон числа элементов, нужна ли картинка, допустимая длина текстов. По ним выбирается вариант (3.4.3).
- Внутренние поля слайда не меньше 80 единиц сетки со всех сторон. Колонтитул и водяной знак — в зарезервированной зоне.
- Цвета слотов задаются **только ссылками на токены темы** (`primary`, `surface`…), без HEX в макете.
- Каждый вариант проходит «стресс-галерею» (7.3) до попадания в прод.

#### 3.4.3 Алгоритм выбора варианта [MVP]
Вариант выбирает **код**, а не модель. Алгоритм детерминирован при фиксированном `seed` колоды:
1. **Фильтр применимости.** Оставляем варианты, у которых ограничения совместимы с планом слайда (число элементов, есть ли картинка при `image_mode`, длина текста).
2. **Скоринг:**
   - штраф, если вариант уже использован в колоде (−3 за каждое использование);
   - штраф, если у соседнего слайда та же «визуальная семья» (например, две сетки карточек подряд) (−2);
   - бонус за соответствие типу презентации (опционально, из storyline) (+1);
   - малый случайный шум от `seed`, чтобы колоды различались.
3. Берём вариант с максимальным скором.
4. Если применимых вариантов нет, берём запасной вариант kind'а (всегда есть самый вместительный) или деградируем в `bullets`.

**Метрики разнообразия (проверяются в тестах):**
- в колоде из 10+ слайдов нет двух подряд одинаковых вариантов;
- не меньше 60% контентных слайдов имеют уникальный вариант;
- для одинакового входа с разным `seed` различается не меньше 50% вариантов.

### 3.5 Темы оформления [MVP]
Тема — это файл `themes/<id>.yaml` с токенами:
- **Цвета:** `bg`, `surface`, `surface_alt`, `primary`, `accent`, `text`, `text_muted`, `on_primary`, `border`, `chart_1…chart_6`.
- **Шрифты:** пара `heading` / `body` из **безопасного списка** (6.3).
- **Типошкала** (pt): `display 60`, `h1 36`, `h2 26`, `h3 20`, `body 18`, `small 14`, `min 12`. Значения примерные, утверждаются на фазе 1.
- **Стиль:** радиус скругления карточек (0 / 8 / 16), стиль карточек (заливка / обводка / тень), обработка картинок (без рамки / скругление / цветная подложка), декоративный элемент (нет / полоса / геометрия).

**Требования:**
- Все пары «текст / фон», которые реально встречаются в макетах, имеют контраст не ниже 4.5:1. Проверяется автотестом при добавлении темы, а не на проде.
- MVP — 6 тем (3 светлых, 2 тёмных, 1 контрастная), v1.x — 10–12.
- Темы помечены тегами (`business`, `academic`, `bold`), чтобы `auto` подбирал уместную по `presentation_type`.
- На бесплатном тарифе доступно ограниченное число тем — это рычаг монетизации (см. 11, вопрос 1).

### 3.6 Изображения [MVP]
**Режим `web`: основной источник — Pexels, не Unsplash.**
- Правила Unsplash API требуют использовать исходные URL картинок (хотлинкинг) и формулируют API для «неавтоматизированного» использования. Встраивание файла в PPTX с автоматическим выбором картинки с этим конфликтует.
- Pexels разрешает скачивание при условии указания Pexels и автора.
- Unsplash оставляем выключенным до письменного подтверждения от них.

**Указание авторства:**
- мелкая подпись на слайде в зарезервированной зоне («Фото: Имя / Pexels»);
- полный список источников — в заметках докладчика последнего слайда.

**Квоты:** дефолтный лимит Pexels — 200 запросов в час и 20 000 в месяц. На горизонте 10k колод в месяц подаём заявку на снятие лимита: это бесплатно при подтверждённой атрибуции.

**Режим `ai`: SiliconFlow, Z-Image-Turbo.**
- Промпт картинки строится из смысла слайда + стиль темы (палитра, «без текста на изображении»).
- Генерация параллельная, до 6 одновременно, таймаут 20 с на картинку. При таймауте выбирается вариант макета без картинки.

**Общее:**
- Картинки **скачиваются и встраиваются** в PPTX, а не подгружаются по ссылке при рендере.
- Каждая картинка обрезается под пропорции слота (cover-crop) и сжимается до 1600 px по длинной стороне (JPEG q=82).
- Кэш по хэшу запроса: Redis, 7 дней.
- Не больше 1 картинки на 2 слайда по умолчанию. Слоты картинок решает макет.

### 3.7 Вписывание текста (text fitting) [MVP]
Главный источник брака в PPTX. В HTML лишний текст прятал `overflow:hidden`, в PPTX такого механизма нет.

1. LLM получает **точную вместимость** слотов выбранного варианта (символы, строки) и пишет под неё.
2. **Fitter** (код) измеряет текст реальными метриками шрифта (TTF-файлы в образе, Pillow), переносит строки и считает высоту:
   - текст влезает → ок;
   - не влезает → уменьшаем кегль по шагам типошкалы, но не ниже `min`;
   - всё ещё не влезает → параллельный LLM-запрос «сократи до N символов» (1 попытка);
   - всё ещё не влезает → переключаемся на более вместительный вариант того же kind'а;
   - в крайнем случае обрезаем по границе предложения и пишем предупреждение в лог.
3. В PPTX автоподбор размера отключён (`autofit = none`). Размеры задаём сами: PowerPoint, Keynote и Google Slides применяют автоподбор по-разному.

### 3.8 Экспорт [MVP]
**PPTX:**
- Каждый слайд собран из нативных объектов: текстовые поля, фигуры, **нативные таблицы**, **нативные диаграммы** (python-pptx chart с данными внутри, то есть редактируемые), картинки как отдельные объекты.
- Слайд, целиком сохранённый картинкой, считается браком.
- Иконки: SVG → PNG высокого разрешения как объект-картинка (допустимо) или фигуры. Иконочный веб-шрифт не используем.
- Mermaid убираем. Схемы процессов строятся фигурами (варианты `process`).
- Файл открывается без предупреждения о восстановлении в PowerPoint (Win/Mac), Keynote, Google Slides и LibreOffice.
- Метаданные: title, author = пользователь, `creator = Fibonacci AI`.
- Заметки докладчика: источники картинок [MVP], текст для выступления [v1.x].

**PDF:** получается **конвертацией готового PPTX** через LibreOffice headless (решение D-001, 4.6). PDF по построению совпадает с PPTX.

**Размер файла:** до 20 МБ для 20 слайдов с картинками. Лимит Telegram на отправку ботом 50 МБ, запас остаётся.

### 3.9 Тарифы и водяной знак
- Водяной знак «Fibonacci.» — только на бесплатном тарифе. Он ставится в PDF (фигура в зарезервированной зоне колонтитула).
- В редактируемом PPTX водяной знак удаляется одним кликом, поэтому защищать им PPTX бессмысленно. Рекомендация: **PPTX — функция платного тарифа** (см. 11, вопрос 1).
- Лимиты тарифов проверяются **на сервере** (в воркере и в API), а не только в хендлерах бота.

### 3.10 REST API [MVP-лайт на фазе 3]
Асинхронная модель: генерация занимает десятки секунд, держать HTTP-соединение открытым нельзя.

```
POST   /v1/decks            создать задачу (JSON или multipart с файлом) → 202 {id, status}
GET    /v1/decks/{id}       статус: queued | processing | done | failed, прогресс по этапам,
                            при done — ссылки на pptx/pdf (подписанные, живут 24 ч)
GET    /v1/themes           список тем
GET    /v1/health
```
- Авторизация: `Authorization: Bearer <api_key>`, ключи хранятся хэшами, у каждого ключа свой клиент и лимиты.
- `Idempotency-Key` в заголовке: повтор запроса не создаёт вторую генерацию.
- `webhook_url` (опционально): POST на него по завершении, подпись HMAC.
- Rate limit на ключ (по умолчанию 10 генераций в минуту).
- Ошибки в едином формате `{error: {code, message}}`.
- Параметры те же, что в 3.2. Правки слайдов в API не предусмотрены.
- `source_mode`: `strict` | `extend` — как обращаться с материалом (правила — 3.3.3). Учитывается, только если в запросе есть текст или файл; по умолчанию `strict`. В запросе «по теме» параметр игнорируется. Профиля у API-клиента нет, поэтому значение по умолчанию не запоминается.
- Спецификация OpenAPI генерируется FastAPI автоматически.

### 3.11 Редактирование в боте [v1.x, фаза 4]
Становится возможным, потому что `DeckSpec` сохраняется в БД (4.4):

| Действие | LLM | Время |
|---|---|---|
| Сменить тему всей колоды | нет | ~15 с (только рендер) |
| «Другой вид» для слайда N (следующий вариант того же kind) | нет | ~15 с |
| Перегенерировать слайд N | 1 вызов | ~25 с |
| Сократить / расширить текст слайда N | 1 вызов | ~25 с |
| Заменить картинку на слайде N | нет | ~15 с |

Первые два действия почти ничего не стоят по себестоимости и сильно повышают ценность. Их делаем первыми.

## 4. Архитектура

### 4.1 Пайплайн

```
 Telegram-бот ──┐                    ┌─ REST API (FastAPI)
                ▼                    ▼
          ┌──────────── Redis (ARQ) — очередь задач ────────────┐
                                    │
                               WORKER
 ┌──────────────────────────────────────────────────────────────────┐
 │ 1. INGEST    парсинг входа → SourceDigest (текст, тезисы,        │
 │              datasets); длинный вход — параллельная выжимка      │
 │ 2. OUTLINE   1 LLM-вызов: план колоды — kind, заголовок-вывод,   │
 │              ключевая мысль, ссылки на datasets, image_query     │
 │ 3. SELECT    код: выбор варианта макета и темы (seed)             │
 │ 4. CONTENT   N LLM-вызовов ПАРАЛЛЕЛЬНО: наполнение слотов        │──┐
 │              под вместимость выбранного варианта                 │  │ параллельно
 │ 5. IMAGES    поиск (Pexels) / генерация (Z-Image) ПАРАЛЛЕЛЬНО    │──┘
 │ 6. FIT       код: вписывание текста, проверка фактов,            │
 │              автоисправления (+ точечные LLM-дозапросы)          │
 │ 7. RENDER    DeckSpec → PPTX (python-pptx)                       │
 │ 8. CONVERT   PPTX → PDF (LibreOffice headless)                   │
 │ 9. DELIVER   сохранение DeckSpec + файлы → Telegram / S3 + webhook│
 └──────────────────────────────────────────────────────────────────┘
          │                              │
     PostgreSQL                    S3-совместимое хранилище
 (users, decks + DeckSpec JSONB)   (pptx/pdf, TTL 30 дней)
```

**Почему план и наполнение разделены (два уровня LLM вместо одного вызова):**
- Вариант выбирается между планом и наполнением, поэтому модель пишет текст **под конкретную вместимость**. Это основная защита от переполнения.
- Наполнение 20 слайдов идёт параллельно: время ≈ один вызов, а не сумма.
- Ретрай идёт по слайду, а не по колоде. Сейчас одна ошибка JSON перезапускает всю генерацию (81 с в логах).
- Общий префикс промпта наполнения (SourceDigest + план) одинаковый для всех слайдов. Промпт-кэширование провайдера удешевляет повторные вызовы — префикс держим байт-в-байт одинаковым.

### 4.4 Хранение
- **PostgreSQL.** Таблица `decks`: id, user_id, api_client_id, статус, входные параметры, `spec JSONB`, длительности этапов, токены, стоимость, ошибки, created_at. Миграции через Alembic.
- **Исходные файлы пользователя** не храним дольше обработки. В очередь передаётся ссылка на временный объект в S3, а не байты в аргументах задачи.
- **Готовые файлы:** для бота отправляем напрямую, копию кладём в S3 на 30 дней (нужна для API и повторной отправки). S3-совместимое хранилище, например Cloudflare R2 (без платы за исходящий трафик).
- **FSM бота** — RedisStorage вместо MemoryStorage.

### 4.5 Бюджет времени (20 слайдов, картинки включены)

| Этап | Цель p95 | Как обеспечиваем |
|---|---|---|
| Ingest | 5 с (20 с для длинного документа) | параллельная выжимка частей |
| Outline | 20 с | один вызов, компактный JSON |
| Content (параллельно, ≤ 8 одновременно) | 30 с | structured outputs, ретрай по слайду |
| Images (параллельно с Content) | 20 с | таймаут → вариант без картинки |
| Fit + исправления | 3 с (15 с с дозапросами) | дозапросы параллельно |
| Render PPTX | 3 с | — |
| Convert PDF | 10 с | пул LibreOffice, прогретый процесс |
| Deliver | 5 с | — |
| **Итого** | **≤ 90 с p95, жёсткий потолок 120 с** | `job_timeout = 150 с` |

Если на каком-то этапе время вышло, колода всё равно отдаётся с деградацией (см. 4.6). Молчаливый провал недопустим.

### 4.6 Надёжность и деградация
- **LLM:**
  - structured outputs (`json_schema`, strict) вместо `json_object`;
  - явный таймаут клиента 45 с;
  - 2 попытки на вызов;
  - провайдер и модель задаются конфигом, отдельно для каждого этапа (outline может использовать модель сильнее, content — дешевле).
- **Слайд не сгенерировался:** собираем `bullets` из ключевых мыслей плана без LLM.
- **Картинка не нашлась:** берём вариант без картинки.
- **PDF не сконвертировался:** отправляем PPTX с сообщением, PDF — отдельной повторной задачей.
- **Колода не собралась целиком:** пользователь получает понятное сообщение, генерация не списывается с лимита.

**Решения, зафиксированные в этом ТЗ** (переносятся в `docs/DECISIONS.md`):

| № | Решение | Почему | Отвергнутая альтернатива |
|---|---|---|---|
| D-001 | PPTX — первичный артефакт, PDF получаем конвертацией через LibreOffice | один рендерер, PDF гарантированно совпадает с редактируемым файлом | HTML→PPTX (растр или поехавшая вёрстка); два рендерера из одной спецификации (двойная работа, диаграммы расходятся) |
| D-002 | Макет выбирает код, а не LLM | воспроизводимость, разнообразие по правилам, модель не может выбрать несуществующий layout | выбор моделью (уже сейчас нестабилен: пустые колонки, чужие layout'ы) |
| D-003 | План и наполнение — раздельные вызовы | вместимость известна до написания текста, параллелизм, ретрай по слайду | один большой вызов (текущий) |
| D-004 | Тип презентации → сюжет, тема → визуал | комбинаторное разнообразие, нет дублирования шаблонов | шаблон на тип (текущий) |
| D-005 | Шрифты только из безопасного списка | PPTX у пользователя не должен подменять шрифты | Google Fonts (красиво в PDF, подмена в PowerPoint) |
| D-006 | Pexels вместо Unsplash для web-картинок | условия Unsplash конфликтуют со встраиванием в файл | Unsplash |
| D-007 | Остаёмся на Railway до ~10k колод/мес | стоимость инфраструктуры мала по сравнению с LLM, а девопс-нагрузка на команду нулевая | VPS |

**Запасной план для D-001:** если на фазе 0 LibreOffice покажет неприемлемое качество нативных диаграмм или шрифтов, PDF рендерится из той же `DeckSpec` отдельным HTML-рендерером с абсолютным позиционированием (Playwright уже есть в образе). Решение принимается по результатам спайка.

### 4.7 Наблюдаемость [MVP]
- JSON-логи с `deck_id` во всех строках. Для каждого этапа: `stage`, `duration_ms`, `status`.
- По каждой колоде в БД: токены на входе и выходе по этапам, число картинок, **расчётная стоимость в $**.

### 4.8 Проектирование запросов к LLM [MVP]

*Добавлено 26.09.2026 по итогам разбора двух колод текущего движка — `docs/PROMPT_REVIEW.md`. Там же конкретные примеры, откуда взялись ошибки.*

Главный вывод разбора: выдумки, обрезки и повторы вызывает в основном не модель, а запрос. Промпт требовал то, чего нет в источнике, — дату у каждого этапа, ровно 3 метрики, отчётную структуру у любого документа. Таблицы приходили без адресов ячеек. Принципы ниже обязательны для промптов нового движка (OUTLINE, CONTENT, дозапросы) и для правок старого.

#### 4.8.1 Анализ источника — отдельный шаг
В режиме «по документу» до плана колоды выполняется анализ источника. Его результат — часть `SourceDigest`, дальше он передаётся в OUTLINE и CONTENT:
- **жанр:** `report` (отчёт о сделанном), `requirements` (ТЗ, задание, положение о конкурсе), `plan` (план, предложение), `article` (статья, лекция, объяснение), `other`;
- **главные мысли** — 3–7 тезисов со ссылками на фрагменты источника;
- **статус каждого утверждения:** `fact` | `plan` | `requirement` | `constraint` | `opinion`. Статус переходит в слайд без изменений: требование нельзя показать как результат, ограничение — как достижение;
- **какие данные есть:** наборы данных (таблицы, ряды чисел) с id — см. 4.8.2;
- **каких данных нет:** явный список того, что аудитория ожидала бы увидеть, но чего в источнике нет. Например, «рост общей выручки в % — нет», «даты этапов — нет». Этот список попадает в промпт плана с инструкцией «этих данных нет — не пиши их».

Сюжет колоды (3.3.1) выбирается по жанру, а не только по `presentation_type`: доклад по ТЗ строится как «задача → требования → ограничения → критерии», а не «что сделано → результаты».

> Плохо: ТЗ хакатона → слайды «Что сделано: разработаны три варианта вёрстки» и «Результаты: 95% качество парсинга, 5 минут».
> Хорошо: «Участникам нужно сделать три варианта вёрстки одной презентации», «Ограничение: генерация — не дольше 5 минут».

#### 4.8.2 Таблицы подаются структурно, с id ячеек
- Каждая таблица источника становится набором данных с id. Колонки — с названием и единицей измерения, строки — с названием, ячейки адресуются как `ds2:r1c4`. Таблицы PDF извлекаются как таблицы (`extract_tables`), а не как плоский текст страницы. Если таблицу распознать не удалось, это отмечается в `SourceDigest`.
- В промпт таблица идёт в формате, где у каждого значения видны строка и колонка:
  ```text
  [ds2] Выручка по каналам за III кв. 2026
  колонки: c1 Канал | c2 Выручка, млн руб. | c3 Доля, % | c4 Рост к III кв. 2025, %
  r1: Продажи в зале | 30,7 | 65 | +8
  r4: Корпоративные заказы | 3,4 | 7 | −6
  ```
- Каждое число на слайде несёт `source_ref` — адрес ячейки или фрагмента текста (см. 4.3.1).
- **Проверка чисел (7.1, «Факты») сверяет пару «число + ячейка», а не только наличие числа в источнике.** Проверка наличия пропускает перенос числа к чужой подписи: «+8%» из строки «Продажи в зале», поставленное к «выручке», в источнике «находится».

> Плохо: `Продажи в зале | 30,7 | 65 | +8` плоской строкой, заголовок колонки — один раз, пятью строками выше.
> Хорошо: `ds2:r1c4 = +8` (строка «Продажи в зале», колонка «Рост к III кв. 2025, %»), и на слайде `{"value": "+8%", "label": "рост продаж в зале", "source_ref": "ds2:r1c4"}`.

#### 4.8.3 Схема не провоцирует выдумку
- **Необязательно всё, чего может не быть в источнике.** Поле обязательно только для того kind, где без него слайд не имеет смысла, а сам kind доступен лишь при наличии этих данных в `SourceDigest`. Пример: `date` обязателен у `timeline`, но `timeline` разрешён только при датах в источнике (3.3.2). Без дат — `process`.
- **Число элементов — диапазон «до N», а не «ровно N».** Вместимость берётся из `LayoutSpec` (4.3.2) и подставляется в промпт кодом — единственный источник правды. Если элементов в ряду больше вместимости, выбирается другой kind (`table`, `chart_*`) или ряд делится на два слайда. **Обрезать ряд нельзя**, особенно выбрасывать отрицательные значения.
- **У числовых элементов есть статус** (`fact` / `plan` / `requirement` / `constraint`), и рендерер подписывает его: «цель», «требование», «не более».
- **Поля с «объяснением»** (`trend`, `source`, следствие в пункте) заполняются только из источника, иначе остаются пустыми. Шаблон пункта «утверждение — следствие» не навязывается.
- **Список допустимых значений** (kinds, иконки) в промпте ровно тот, который код умеет нарисовать для этого типа. Чужие значения в схеме — прямое приглашение их выбрать.

> Плохо: `"timeline_items": [{"date": "string", …}]` обязательное + в промпте «4 этапа, у каждого date» → «Октябрь 2026 / Ноябрь 2026 / …» при источнике «в IV квартале».
> Хорошо: в `SourceDigest` дат нет → `timeline` недоступен → план ставит `process` или `bullets` «В IV квартале — три приоритета».

#### 4.8.4 План колоды — список уникальных тезисов
- OUTLINE сначала формирует список тезисов: одна мысль — один слайд, у каждой ссылки на источник. Дубли запрещены и проверяются кодом (7.1, «два слайда с одинаковым заголовком или содержимым»).
- **Слайдов-наполнителей нет.** Блоки сюжета (3.3.1), для которых в источнике нет содержания, пропускаются. «Выводы» — это то, что следует из фактов, а не их пересказ.
- **Заголовок каждого тезиса — вывод** (3.3.3), он формулируется уже в плане и не копирует заголовок раздела источника.
- **Если тезисов меньше, чем выбранное число слайдов,** колода не добирается повторами. В `strict` колода становится короче (минимум 5 слайдов) с сообщением пользователю, в `extend` недостающие слайды дополняются общими знаниями без чисел, дат и источников — 3.3.3.

> Плохо: отчёт из 4 разделов → 9 слайдов, программа лояльности упомянута на 3 слайдах, два итоговых слайда подряд.
> Хорошо: 7 тезисов → 7 содержательных слайдов, каждый факт — на одном слайде.

#### 4.8.5 Примеры «плохо / хорошо» для ключевых правил
Каждое ключевое правило в промпте сопровождается парой «плохо / хорошо». Правило без примера модель трактует шире, чем задумано: правило про заголовки с примером-темой «Как модель учится на примерах» дало заголовки-темы. Правила, для которых пара обязательна:
1. числа только из источника, пропуск лучше выдумки;
2. число подписывается тем, к чему относится (строка и колонка);
3. статус утверждения сохраняется (требование ≠ результат);
4. даты только из источника, без уточнения («IV квартал» ≠ «октябрь»);
5. ряд не обрезается, отрицательные значения не выбрасываются;
6. заголовок — вывод, а не тема;
7. одна мысль — один слайд;
8. причины и следствия — только из источника.

Примеры в промптах берутся **не из кейсов golden-корпуса** — берётся аналог из другой области. Иначе прогон корпуса мерит запоминание примера, а не соблюдение правила.

#### 4.8.6 Промпты разделены по режимам кодом, а не условиями в тексте
Блоки, которые верны только для одного режима, подставляет код по `source_type` и `presentation_type`. Пример — «используй данные из своих знаний» и якорь «роадмапа» от текущей даты для режима «по теме». Условия «если есть блок МАТЕРИАЛ, то…» внутри текста допустимы только как временная мера в старом движке. Инструкции разных уровней не должны противоречить друг другу: системный промпт весомее пользовательского, и общий разрешающий блок в системном перебивает частный запрет в пользовательском.

#### 4.8.7 Изменение промптов — только через прогон golden-корпуса
- Любой PR, меняющий `prompts/`, содержит отчёт прогона golden-корпуса (7.4) до и после правки: `tests/golden/reports/<дата>.md`. Каждый кейс — не меньше 3 прогонов: при ненулевой температуре одного мало.
- В том же PR повышается `prompts/VERSION`, версия пишется в `DeckSpec.meta.versions.prompts` (4.3.1).
- Правка не мёржится, если хотя бы один кейс стал хуже по обязательным проверкам кейса (списки «обязано быть» / «не должно быть» в 7.4) или по детерминированным проверкам 7.1.
- Пока корпус меньше 30 входов, минимальный прогон — все кейсы из 7.4 плюс 2 колоды питч-дека по теме (регрессия режима «по теме»).

## 5. Инфраструктура

**Сервисы Railway:** `bot`, `api`, `worker` (с LibreOffice и шрифтами), PostgreSQL, Redis. S3 — внешний (R2).
- Команды запуска всех сервисов хранятся **в репозитории** (`railway.toml` / `Procfile`), а не только в интерфейсе Railway.
- Воркер: `max_jobs = 5`, не больше 2 одновременных конвертаций LibreOffice (у каждой свой профиль пользователя, иначе процессы конфликтуют), RAM 2 ГБ.
- **Лимит расходов** в Railway выставлен обязательно.
- Масштабирование: при p95 очереди больше 30 с добавляем реплику воркера. На горизонте 10k колод в месяц (~330 в день) хватает одной-двух реплик.

**Процесс разработки:**
- Код попадает в `main` только через pull request от Claude Code. Ручная загрузка файлов через веб-интерфейс GitHub запрещена.
- GitHub Actions на каждый PR: линтер + unit-тесты + стресс-галерея (без LLM).
- `.gitignore`, `.env.example` со всеми переменными.

## 6. Нефункциональные требования

### 6.1 Производительность
- p95 ≤ 120 с от нажатия кнопки до получения файлов, без учёта очереди. Цель — 90 с.
- p50 ≤ 60 с.
- Выдерживать пик 30 генераций в час на одной реплике воркера.

### 6.2 Совместимость PPTX
Файл открывается без ошибок и без предупреждений о восстановлении, вёрстка не ломается в:
- PowerPoint 365 (Windows, macOS);
- Keynote (актуальная версия);
- Google Slides (импорт);
- LibreOffice Impress.

Проверяется вручную на фазе 0 (спайк) и на каждом новом варианте макета (выборочно).

### 6.3 Языки и шрифты
- Безопасный список шрифтов утверждается на фазе 0 по тесту на всех целевых языках. Кандидаты: шрифты, которые есть в Windows и macOS с Office и которые поддерживает Google Slides.
- Проверка: для каждого языка из списка нет «квадратиков» (tofu) ни в PPTX, ни в PDF. Для языков со своей письменностью (армянский, грузинский) в теме допускается шрифт-подстановка по языку.
- RTL-языки (арабский, иврит, фарси) не входят в MVP: для них нужна зеркальная вёрстка всех макетов.
- Язык колоды единый. Язык интерфейса бота и язык презентации — разные настройки.

### 6.4 Стоимость
- Целевая себестоимость колоды считается и логируется (4.7). Бюджет утверждается владельцем продукта после первых 100 генераций на новом движке.
- Картинки: Z-Image-Turbo ≈ $0,005 за штуку → 5 картинок ≈ $0,025 на колоду.

### 6.5 Безопасность
- Секреты только в переменных окружения, все через `Settings`.
- API-ключи хранятся хэшами.
- Входной текст пользователя передаётся в LLM только как данные в разметке, а не как инструкции (защита от prompt injection из документа).
- Файлы пользователя удаляются после обработки.

## 7. Аудит и тестирование

Аудит **не выполняется на проде как отдельный этап**. На проде работает только модуль `core/checks` в составе этапа FIT: он быстрый (миллисекунды) и исправляет ошибки автоматически. Полный аудит — инструмент разработки.

### 7.1 Детерминированные проверки (`core/checks`, прод + тесты)
Читают готовый PPTX обратно (python-pptx) или `DeckSpec`.

| Группа | Проверка | На проде |
|---|---|---|
| Вёрстка | элемент за границами слайда | да |
| | пересечение блоков (кроме разрешённых макетом наложений) | да |
| | текст не влезает в рамку (по метрикам fitter) | да, исправляет fitter |
| | контент в полях у краёв | да |
| | картинка растянута (пропорции ≠ пропорциям файла ±2%) | да |
| Тема | шрифт или кегль не из темы | тесты |
| | цвет не из палитры темы | тесты |
| | контраст текста к фону < 4.5:1 | тесты (на уровне тем) |
| | водяной знак/колонтитул не на своём месте | тесты |
| Плотность | > 6 пунктов, пункт > 20 слов, таблица > 7×5, > 5 серий | да (ограничено схемой) |
| | заполненность слайда < 25% или > 75% площади полезной зоны | тесты |
| Целостность | файл не открывается (python-pptx + LibreOffice) | да |
| | заглушки: lorem, XXX, TODO, «вставьте текст», фигурные скобки шаблона | да |
| | пустой слайд или только заголовок | да |
| | слайд — одна картинка на весь кадр без редактируемых объектов (кроме `image_focus`) | да |
| | у диаграммы нет подписей осей, единиц или легенды (если серий > 1) | да |
| | два слайда с одинаковым заголовком или содержимым | да |
| Факты | число на слайде не найдено в источнике (режим «по документу») | да |
| | число не совпадает с ячейкой или фрагментом из своего `source_ref` (4.8.2) | да |
| | `timeline` без дат или с датой, которой нет в источнике | да |
| Разнообразие | метрики из 3.4.3 | тесты |

### 7.2 Контентные проверки (VLM, только dev)
Вход — PNG слайда (PPTX → PDF → PNG) + текст источника. Вопросы «да/нет»:
1. Заголовок формулирует вывод, а не тему?
2. Содержимое соответствует заголовку?
3. Слайд пересказывается одним предложением?
4. Все цифры и факты есть в источнике?
5. Картинка относится к теме слайда?
6. Нет служебного мусора (реплик модели, кусков промпта)?
7. Нет опечаток?
8. Колода на одном языке?
9. Соседние слайды связаны по логике?

Результат — отчёт HTML с миниатюрами слайдов и найденными проблемами. Используется для сравнения версий промптов.

### 7.3 Стресс-галерея макетов (CI, без LLM)
Для **каждого** варианта × **каждой** темы рендерим 3 фикстуры контента: минимальную, типовую и максимальную по вместимости (включая длинные слова на немецком и казахском). Все детерминированные проверки должны пройти. Плюс генерируется PDF-галерея для просмотра глазами. Новый вариант или тема не мёржится без зелёной галереи.

### 7.4 Golden-корпус (перед релизом, с LLM)
30 входов: 10 тем, 10 текстов, 10 файлов (по 2–3 каждого формата, включая документ с таблицами и длинный PDF). Прогон считает:
- p50/p95 времени;
- долю колод без единой ошибки детерминированных проверок;
- процент «да» по VLM-вопросам;
- метрики разнообразия;
- стоимость.

Результаты сохраняются в `tests/golden/reports/<дата>.md`, чтобы сравнивать версии. Обязательные проверки кейсов из списков ниже проверяет скрипт `tests/golden/check_case.py <deck.json> <кейс>` (регулярные выражения по пунктам слайда; до появления `source_ref` пара «число + подпись» проверяется внутри одного пункта).

Кроме общих метрик, у каждого кейса есть свои обязательные проверки: **«обязано быть»** (числа с подписями, факты) и **«не должно быть»** (известные выдумки). Прогон считает долю прогонов кейса, в которых все обязательные проверки прошли. Правило изменения промптов — 4.8.7. Входные файлы кейсов хранятся оригиналами в `tests/fixtures/`.

#### Первые кейсы корпуса

Кейсы взяты из реальных колод текущего движка от 26.09.2026. Разбор ошибок — `docs/PROMPT_REVIEW.md`. JSON колод старого движка — `tests/fixtures/specs/`.

**G-01. Отчёт о продажах сети кофеен (docx с тремя таблицами)**
- Вход: `tests/fixtures/test_prodazhi_Q3.docx`. Выход старого движка для сравнения: `tests/fixtures/bot_output_prodazhi_Q3.pdf`, его JSON — `tests/fixtures/specs/prodazhi_Q3.json` (тот же прогон).
- Параметры: `doklad`, режим «по документу», `source_mode = strict`, язык `ru`, 9 слайдов.

Обязано быть (число → подпись, к чему оно относится):

| Число | Подпись | Ячейка источника |
|---|---|---|
| 47,3 млн руб. | выручка за III квартал (итого) | табл. 1, «Итого за квартал» |
| +41% | рост доставки к III кв. 2025 | табл. 2, «Доставка» |

- Если показаны города — все четыре (Санкт-Петербург, Петрозаводск, Мурманск, Архангельск).
- Заголовки содержательных слайдов — выводы (VLM-вопрос 1). Например, «Доставка выросла на 41% и стала вторым каналом».

Не должно быть:
- любого процента роста **общей** выручки к прошлому году (в источнике его нет), в том числе «на 8% больше прошлого года»;
- месяцев и дат у планов IV квартала («октябрь 2026», «конец декабря») и слайда `timeline` с ними — в источнике только «IV квартал»;
- четвёртого и последующих приоритетов сверх трёх («анализ результатов» и т.п.);
- ряда каналов или городов без отрицательного элемента (корпоративные заказы, Мурманск);
- причин и следствий, которых нет в тексте: «это поможет вернуть клиентов», «это увеличит охват», «47,3 млн — результат увеличения потока клиентов»;
- одного факта больше чем на одном слайде (итоговый слайд формулирует вывод, а не повторяет факт);
- заголовков-тем: «Общая динамика», «Каналы продаж», «Выводы и планы», «Итоги работы».

Обязано быть (число → подпись, к чему оно относится; статус):

| Число | Подпись | Статус | Место в источнике |
|---|---|---|---|
| 3 | бизнес-задачи сервиса: парсинг шаблона; генерация структуры и текста по брифу; генерация слайдов по шаблону с визуализацией | требование | раздел 2 |

Если показано — только с этой подписью:

| Число | Подпись |
|---|---|
| 10–15 слайдов | целевой объём колоды (или заданный пользователем) |
| до 35B | LLM / VLM / text-to-image с открытыми весами, лицензия Apache 2.0 или MIT |
| до 20B | модель text-to-image для задачи со звёздочкой — только для 10 команд после отбора |
| топ-10 | командам после отбора дают Qwen 3.8 27b, инференс VK для них обязателен |
| 9 вариантов | промежуточный этап: 3 варианта на одном контенте × 3 шаблона |
| до 7 минут | питч и видео-демо |
| 4.5:1, 6 буллетов, 15 слов, 7 × 5, 5 серий | пороги проверок из Приложения 1 — это критерии аудита, а не показатели решения |

Не должно быть:
- **любых процентов:** в источнике нет ни одного символа `%`. В том числе «95%» (PDF-фикстура) и «90% успешных генераций» (`specs/hakaton.json`);
- «5 минут» и «3 варианта» как достигнутого результата: «генерация занимает 5 минут», «каждый шаблон генерирует 3 варианта», метрики на слайде «Результаты»;
- источников у чисел: «Тестирование сервиса, 2026», «Внутренние тесты, 2026» — сервиса нет, это задание;
- слайдов и заголовков «Что сделано», «Результаты», «Результаты работы», «Измеримые показатели успеха», «Эффективность сервиса»;
- прошедшего времени о работе участников: «проведён парсинг», «разработаны три варианта», «создана функциональность»;
- оценок качества несуществующего решения: «высокая точность парсинга», «рекордно короткие сроки», «соответствует корпоративным стандартам»;
- `timeline` и любых дат (Q4 2026 — Q3 2027 и т.п.): в источнике единственный год — «2026» в заголовке;
- придуманных «следующих шагов» (сбор отзывов, запуск, расширение функционала). Пилотное тестирование допустимо только как условие организатора: «при полном выполнении ТЗ компания готова провести пилот»;
- layout вне каталога доклада (`problem`, `solution`).

**G-03. Отчёт о продажах по теме, без файла (регрессия режима «по теме»)**
- Вход: тема «Итоги продаж за квартал», файла и текста нет. Пример выхода старого движка — `tests/fixtures/specs/prodazhi_topic_only.json`.
- Параметры: `doklad`, режим «по теме», язык `ru`, 9 слайдов.

Обязано быть: у каждого слайда с числом — сноска «Оценочные данные — проверьте перед показом» (3.3.3).

Не должно быть:
- ссылок на конкретные отчёты, исследования и организации в `source`, `trend` и тексте: «Отчеты отдела маркетинга», «Финансовая отчетность компании», «Анализ внутренних данных компании»;
- `source`, заполненного моделью (его проставляет код);
- разных значений одного показателя на разных слайдах (как «новых клиентов +30%» и «Новые клиенты 20%»);
- конкретики, которой нет в запросе, выданной за факт: название категории товара («электроника»), размер клиентской базы, сумма выручки без пометки оценки;
- `chart_series` и `chart_share` (3.3.3, вопрос 2 раздела 11).

### 7.5 Unit-тесты
