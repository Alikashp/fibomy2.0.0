## Сессия 3. REST API для второго бота

*Перенесено из фазы 3 (ТЗ 3.10, 9) решением владельца 01.10.2026 (D-054): к API подключается второй бот с живыми пользователями сразу после этой сессии.*

**Состав:**
- Сервис FastAPI `src/api/` в том же образе, отдельный сервис Railway «api» (`railway.api.toml`): создаёт строку `decks` и ставит `generate_deck_job(deck_id)` в ту же очередь, что и бот; колоду собирает тот же `core.generate_deck` (D-055).
- Эндпоинты по `04_CONTRACTS.md`, 7: `POST /v1/decks` (тема, текст или файл pdf / docx / pptx / txt; число слайдов, язык, аудитория, тема оформления, `source_mode`, автор, `webhook_url`; `Idempotency-Key`), `GET /v1/decks/{id}` (статус, этап, прогресс, предупреждения, ошибка с кодом), `GET /v1/decks/{id}/files/{pptx|pdf}`, `GET /v1/themes`, `GET /v1/usage`, `GET /v1/health`. Пока только доклад; питч-дек — `400 UNSUPPORTED_TYPE` до сессии 5.
- Авторизация: ключ `Authorization: Bearer fib_…`, в БД — SHA-256; таблица `api_clients` (миграция `0006`): имя, лимит колод в сутки, запросов и колод в минуту, водяной знак, секрет webhook (D-056). Ключ создаёт владелец командой `python -m api.keys create`, ключ показывается один раз.
- Лимиты: колод в сутки (календарные сутки UTC, упавшие не считаются), запросов в минуту и колод в минуту — `429` с понятным текстом и `Retry-After` (D-057).
- Стоимость: `decks.api_client_id`, себестоимость колоды — по клиенту (`python -m api.keys usage`).
- Файлы колод API: S3, если заданы `S3_*`, иначе Redis с TTL 1 ч — временно до S3 сессии 5; скачивание — только через API с ключом (D-058).
- Webhook по готовности (если клиент передал URL): тело — статус, подпись HMAC секретом клиента, 3 повтора.
- Бот не меняется: бот и API работают параллельно.
- Тесты: юнит и интеграционные на все эндпоинты (подменный движок и подменный LLM), авторизацию, лимиты, ошибки; снимок схемы OpenAPI против несовместимых изменений; отдельный шаг «API-тесты» в CI. Golden: одна генерация через API end-to-end (процессы api и воркера, Postgres и Redis).
- `docs/API.md` — руководство для разработчика второго бота.

**Зависит от:** сессии 2.

**Готово, когда:**
- юнит- и интеграционные тесты API и шаг «API-тесты» в CI зелёные;
- golden: колода G-01 через API end-to-end собрана, файлы скачаны, webhook с верной подписью пришёл;
- `docs/API.md` описывает все запросы, ответы и коды ошибок (проверяется тестом).

**Владелец проверяет руками:**
1. Railway: сервис «api» создан, `/v1/health` отвечает `ok` на публичном домене.
2. Ключ для второго бота создан командой `python -m api.keys create`, ключ сохранён в переменных второго бота.
3. Одна генерация через curl по `docs/API.md`, раздел 2: `202` → статус до `done` → PPTX и PDF скачиваются.
4. Бот работает как раньше (доклад по теме → PPTX + PDF).

## Риски плана

| Риск | Где проявится | Что делаем |
|---|---|---|
| proxyapi не принимает `json_schema` strict для gpt-6-luna | сессия 1, первый час | `json_object` + валидация + повтор с ошибкой (заложено) |
| Вызов OUTLINE на `low` дольше 25 с | сессия 1–2 | урезаем план до минимума полей; или `reasoning_effort=none` для OUTLINE по результату замера |
