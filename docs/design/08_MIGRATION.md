# 08. Переход со старого движка на новый

**Статус:** утверждено 01.10.2026 (с временной маршрутизацией, раздел 2.1) · **Дата:** 30.09.2026, правка 01.10.2026 · **Опирается на:** `03_ARCHITECTURE.md` (2.1), `04_CONTRACTS.md` (8), `09_PLAN.md`, D-009, D-010, D-026

---

## 1. Принципы

1. **Без флагов** (D-026). Бот переходит на новый движок в первой сессии реализации. Пользователей нет — сравнивать движки на трафике не нужно. Исключение — временная маршрутизация по виду входа, пока новый движок не умеет материал и питч-дек (раздел 2.1, D-038): это не флаг и не тестовая группа, а правило по возможностям движка, которое удаляется по мере их появления.
2. **Старый код остаётся в репозитории, пока новый не пройдёт golden**, но бот его не вызывает. Он нужен как эталон для сравнения колод и для быстрого отката.
3. **Миграции БД на время перехода только добавляют.** Ни одна таблица и колонка, которые читает старый код, не удаляется до фазы 2. Поэтому откат кода не требует отката БД.
4. **Воркер выкатывается раньше бота**, когда меняется набор задач очереди.

### 2.1 Временная маршрутизация (D-038)

Пока новый движок не умеет часть входов, бот выбирает движок по виду запроса (`dialog.engine_for`):

| Запрос | Сессия 1 | Сессия 2 | Сессия 5+ |
|---|---|---|---|
| Доклад по теме | **новый** (PPTX + PDF) | новый | новый |
| Доклад по материалу (текст в сообщении или файл) | старый (PDF) | **новый** — маршрутизация материала удалена (PR #79) | новый |
| Питч-дек (по теме, с брифом) | старый (PDF) — сюжет питч-дека на kinds фазы 1 появляется в сессии 5 (до порядка D-054 — в сессии 3) | старый (и в сессиях 3–4) | **новый** — маршрутизация удаляется целиком |

- В сводке видно, какой движок сработает: «📦 Файлы: PPTX + PDF» (новый) или «📦 Файлы: PDF» (питч-дек на старом). С сессии 2 выбор дизайна — четыре темы нового движка для всех типов; питч-деку на старом движке тема переводится в его цветовую схему (`dialog.LEGACY_SCHEME_BY_THEME`).
- Код маршрутизации — одна функция `dialog.engine_for` и ветка в `main.generate_and_send`; удаляется одним коммитом сессии 5 вместе с выбором тем старого движка.
- Питч-дек остаётся на старом движке на сессию дольше, чем материал: в сессии 2 нет его сюжета (`09_PLAN.md`, сессия 5). Это продление решения владельца «по теме — в новый, материал — в старый» на питч-дек, а не новое правило.

Критерий перехода к шагу 3 — только golden и ручная проверка файлов владельцем. Если к концу сессии 6 golden не проходит — старый код не удаляется, сессия продолжается исправлениями (сроки двигаются, откат не нужен: бот уже на новом движке).

## 5. Выкатка сессии 1 (переключение)

1. PR сессии 1 смёржен, Railway собирает образ (Wait for CI).
2. **Сначала воркер:** он получает обе задачи (старую и новую) и LibreOffice.
3. **Потом бот:** начинает ставить `generate_deck_job` (доклады по теме; материал и питч-дек — по-прежнему `generate_presentation_job`).
4. Если бот поднялся раньше воркера и успел поставить новую задачу, старый воркер её не знает — ARQ завершит задачу ошибкой «function not found». Колода останется `queued`, статусное сообщение — «В очереди». Сторож зависших колод появляется в сессии 5; до него — просто начать заново через /new после выкатки воркера. Пользователей нет, риск — только у тестировщика.
5. Проверки после деплоя — в описании PR сессии 1 (сценарий «тема → PPTX + PDF»).

## 6. Откат

| Ситуация | Как откатить | Что с данными |
|---|---|---|
| После сессий 1–5 новый движок ломает генерацию | **Railway → Deployments → предыдущий деплой → Rollback** для воркера и бота (минуты). Затем revert PR в GitHub, чтобы следующий деплой не вернул поломку | `decks` остаются, старый код их не читает. Задачи `generate_deck_job` в очереди на старом воркере упадут — пользователь их не дождётся (пользователей нет) |
| После сессии 6 (старый код удалён) | revert PR сессии 6: возвращает старые файлы, Playwright и базовый образ. Образ собирается заново (~10 минут) | без изменений |
| Сломалась миграция `0005` на старте | Railway Rollback: `0005` не применилась целиком (транзакция), старый код стартует | — |
| Новый движок работает, но плохо на части входов | не откатываем: чиним в той же ветке сессии, golden покажет регрессию | — |

Переменные окружения: новые переменные нового движка имеют значения по умолчанию, старый код их игнорирует — при откате менять ничего не нужно.

## 7. Что проверить после каждого шага
- Шаг 1: генерация по теме в боте даёт PPTX + PDF; в `decks` — строка `done` с `spec`, длительностями и стоимостью; в логах `deck_id` на каждой строке.
- Шаги 2–4: golden-комментарий в PR; галерея зелёная.
- Шаг 3: образ собирается без Playwright; размер образа меньше прежнего; генерация всех видов входа.
- Шаг 4: бот и воркер стартуют после миграции удаления, в логах нет обращений к `presentations`.

## 8. Выкатка сессии 3 (REST API)

1. PR сессии 3 смёржен, Railway собирает образ (Wait for CI).
2. **Сначала воркер:** получает задачу `deliver_webhook_job`, сохранение файлов колод API и миграцию `0006` (применяется тем сервисом, что стартует первым).
3. **Бот** — без изменений поведения, выкатывается как обычно.
4. **Потом сервис «api»** (новый, `railway.api.toml`): стартует только после воркера — иначе колоды API, поставленные в очередь старому воркеру, не сохранят файлы (`files = null`) и отдадут `409`.
5. Ключ второму боту — командой бота `/apikey create` (владелец, `ADMIN_TELEGRAM_IDS`, D-061) или `python -m api.keys create` (`docs/API.md`, 1.1–1.2); проверка — одна колода через curl. Задача `delete_message_job` (удаление сообщения с ключом) — у воркера, поэтому воркер по-прежнему выкатывается раньше бота.

Откат API: удалить или остановить сервис «api» в Railway — бот и воркер работают как раньше; таблица `api_clients` остаётся (миграция добавляющая).
