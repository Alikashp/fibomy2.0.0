## 2. Как считается вместимость

Вместимость слота в промпте и в YAML (`max_chars`) — оценка сверху, которую модель должна соблюдать. Точное решение принимает fitter по реальным метрикам шрифта.

```
знаков_в_строке = floor(ширина / (кегль_pt × 2 × k)),  k = 0,55 (обычный), 0,59 (полужирный)
строк           = min(max_lines, floor(высота / (кегль_pt × 2,4)))
вместимость     = floor(знаков_в_строке × строк × 0,9)      # 0,9 — потери на переносе по словам
```

- `max_lines` ограничивает число строк **базового** стиля. На шагах кегля вниз строк столько, сколько помещается по высоте бокса (поэтому на минимальном стиле вместимость больше). У однострочного слота потерь на переносе нет — множитель 0,9 не применяется.

- `k` — средняя ширина знака в долях кегля по замеру Liberation Sans на русском и казахском тексте (0,50–0,55) с запасом: полужирный шире на ~8%.
- Заголовки (h1–h3, display, hero) — полужирные, текст (body, small) — обычный.
- **Числа** (`value`) нельзя сокращать, поэтому их применимость проверяется по вместимости на **минимальном** стиле слота.
- **Тексты, известные до SELECT** (заголовок-утверждение `statement`, тема на титуле), тоже проверяются по минимальному стилю. **Тексты, которые пишет CONTENT**, модель пишет под базовую вместимость варианта.
- Fitter (ТЗ 3.7): мерит текст Liberation Sans (Pillow), переносит по словам, считает высоту; не влезает — шаг кегля вниз до `min_style` → сокращение LLM (1 попытка) → более вместительный вариант того же kind → обрезка по границе предложения с записью в лог.

**Типошкала** (pt): `hero 96` (только `big_number`), `display 60`, `h1 36`, `h2 26`, `h3 20`, `body 18`, `small 14`, `min 12`. Шаги fitter'а: hero → display; display → h1 (титул — до h2); h1 → h2; h2 → h3; h3 → body; body → small. Ниже `small` основной текст не опускается, `min` — только колонтитул.

Таблицы ниже сгенерированы по этой формуле из той же геометрии, что и вайрфреймы. Столбец «Вместимость» — база, в скобках — на минимальном стиле.

### 3.1 `title` — титульный слайд

**Когда:** всегда первый слайд. **Данные:** тема пользователя (заголовок — **дословно**, ставит код, G-05), подзаголовок (план, `deck.subtitle`), автор (ФИО и группа из профиля), фото (если выбран вариант с фото и оно нашлось).

- Автора нет — слот не рисуется, остальная геометрия не сдвигается.

## 4. Выбор варианта кодом (ТЗ 3.4.3)

Вариант выбирает `core/selection` после OUTLINE и до CONTENT. Модель вариант не выбирает и о вариантах не знает (D-002).

### 4.1 Входы
Для каждого слайда плана: `kind`, `role`, `items_planned`, длина заголовка (для `statement` и титула), наличие `image_query`, dataset (число категорий, `axis`, сумма долей), `image_mode`. Для колоды: `seed`, тема, уже выбранные варианты соседей.

### 4.2 Алгоритм
1. **Фильтр применимости** по `applies_when` варианта: число элементов, картинка (`required` — только если `image_mode = web`, у слайда есть `image_query` и бюджет картинок не исчерпан: не больше одной на два слайда), ось времени и число точек (line), сумма долей (donut), длина известных текстов и значений — по вместимости на минимальном стиле (раздел 2).
2. **Скоринг** каждого применимого варианта:
   - −3 за каждое использование варианта в колоде;
   - −2, если у соседнего слайда (слева) та же **визуальная семья** (4.3);
   - +2 за совпадение роли: `ask` → `statement.highlight_band`; `results` с одним числом → `metrics.big_number`; `criteria` и `requirements` → `bullets.numbered_columns` / `process.vertical_steps`;
   - +1 за соответствие сюжету (storyline может задать предпочтение, например титул питч-дека — `cover_split_image`);
   - шум `U(0; 0,5)` из генератора с зерном `hash(seed, slide_id)` — колоды с разным `seed` различаются, с одинаковым — воспроизводимы.
3. Берётся вариант с максимальным скором; при равенстве — по порядку в каталоге.
4. **Нет применимых** → запасной вариант kind (`fallback: true`); не применим и он → kind `bullets` (`cards_grid` или `icon_list`).
5. После CONTENT и FIT: если текст не поместился даже на минимальном стиле и после сокращения — FIT повторяет шаг 2 среди вариантов того же kind, где содержание помещается. Содержание от этого не меняется (`04_CONTRACTS.md`, 5).

### 4.4 Метрики разнообразия (проверяются тестом на колодах golden)
- в колоде из 10+ слайдов нет двух подряд одинаковых вариантов;
- не меньше 60% содержательных слайдов имеют уникальный вариант;
- для одного плана с разным `seed` различается не меньше 50% вариантов (там, где у kind больше одного применимого варианта).

С 22 вариантами и 2–3 вариантами у частых kinds (`bullets`, `statement`, `process`) метрики достижимы на колодах из 9 слайдов. Узкое место — kinds с одним вариантом (`chart_share`, `closing`): они не повторяются в колоде по смыслу.

## 5. Деградация между kinds

| Ситуация | Что делает код |
|---|---|
| `chart_series` / `chart_share` без dataset или «по теме» | `metrics` (≤ 4 числа из refs) или `bullets` |
| `chart_share`: сумма долей вне 95–105%, долей > 6 | `chart_series.column_chart` по тем же данным |
| `metrics` > 4 чисел | `chart_series` (если есть dataset) или `bullets` по пункту на элемент |
| `bullets` > 6 пунктов | план делит на два слайда; если план уже зафиксирован — `process.vertical_steps` (до 6) |
| `comparison` с 3 объектами | `bullets.cards_grid` |
| `process` > 6 шагов | `vertical_steps` + два слайда |
| Слайд без контента после CONTENT | `bullets` из `key_message` и заголовка (без LLM) |
| Картинка не нашлась | тот же kind, вариант без картинки |

## 7. Правила рендера (из спайка PPTX)

1. У каждой фигуры удаляется `<p:style>`, цвета заливки и линии задаются явно — иначе тень темы в LibreOffice и разный вид в приложениях.
2. Автоподбор размера выключен (`MSO_AUTO_SIZE.NONE`), внутренние поля текстовых рамок — 0. Размер текста задаёт fitter.
3. Каждому фрагменту текста — атрибут `lang` по языку колоды (`ru-RU`, `kk-KZ`, …).
4. Кольцевая диаграмма: `has_title = False`, размер дырки 60% через XML; подписи на секторах выключены (значения в легенде слайда).
5. Столбчатая и линейная: подписи значений включены (`show_value = True`), формат числа — как в источнике (запятая как разделитель для ru, kk, uz), ось значений с единицей из dataset, линии сетки — `border`.
6. Нативные таблицы (фаза 2): в `a:tcPr` элементы границ `a:lnL/R/T/B` идут до заливки ячейки.
7. Метаданные: `dc:title` — тема, `dc:creator` — пользователь, `Application` и `lastModifiedBy` — «Fibonacci AI».
8. Заметки последнего слайда — список источников фото (автор, Pexels, ссылка).
