# Ревью изменений

Что проверять в каждом PR и что считается **блокером** — PR не мёржится, пока блокер не исправлен или владелец явно не принял исключение. Правила, из которых вытекают блокеры, — `README.md` (раздел «Правила»), `docs/TZ.md` и `docs/DECISIONS.md`; здесь — критерии и требования к описанию PR.

## Порядок проверки

1. **Живые пользователи API** — не ломает ли изменение второго бота.
2. **Корректность** — делает ли код то, что заявлено, и не ломает ли соседние сценарии: бот, API, старый движок питч-дека.
3. **Понятность** — читается ли код без разбора контекста, обновлены ли README и файлы фич.

Стиль и мелкие оптимизации — замечания, не блокеры.

## Блокеры

| № | Блокер | Пример | Правило |
|---|---|---|---|
| B1 | Несовместимое изменение API `/v1` | удалено или переименовано поле ответа; поле запроса стало обязательным; другой формат ошибки | README «Правила», D-059 |
| B2 | Изменение схемы API без снимка и без `docs/API.md` | новое поле в ответе, `api_contract_v1.json` не обновлён | README «Правила» |
| B3 | Удаляющая или меняющая миграция | `drop_column`, переименование таблицы, смена типа колонки | README «Правила» |
| B4 | Текст на слайде обрезается или кончается «…» | `text[:n] + "…"`; `maxLength` или `maxItems` в схеме ответа LLM | D-071 |
| B5 | Промпт или параметры модели в коде | строка промпта в `.py`; правка `prompts/` без новой строки в `prompts/v2/VERSION` | README «Правила»; ТЗ 4.8.7 |
| B6 | Настройка мимо `src/config.py` | `os.getenv` в модуле; новая переменная без `.env.example` | `src/config.py` |
| B7 | Секрет в коде, коммите или документации | ключ в тесте, в примере `docs/API.md`, в логе | README «Правила» |
| B8 | Вид слайда решается в рендерере | условие «если тема X — рисовать иначе» в `core/render/`, а не в YAML темы или варианта | `docs/ARCHITECTURE.md`, принцип 2 |
| B9 | Числа диаграммы от модели | значение ряда берётся из ответа LLM, а не из `SourceDigest.datasets` | D-028 |
| B10 | `core` зависит от адаптера | импорт aiogram, FastAPI, `bot`, `api`, `worker` в `src/core/` | `docs/ARCHITECTURE.md`, принцип 1 |
| B11 | Сбой этапа роняет колоду без деградации | исключение картинки или CONTENT не перехвачено; колода падает вместо варианта без картинки или запасного слайда | `docs/ARCHITECTURE.md`, принцип 6 и раздел 5 |
| B12 | Красный CI или нет строки про API-тесты в описании PR | `tests`, `gallery` или шаг «API-тесты» не зелёные | README «Правила» |
| B13 | Код изменён, документация нет | перенесён файл, добавлен этап, сервис, роут или фича — README, `docs/ARCHITECTURE.md`, файл фичи или `docs/API.md` не обновлены; работа не отражена в `docs/ROADMAP.md`; `scripts/check_docs.py` красный | D-080 |
| B14 | Удаление без доказательства, что это никому не нужно | удалён роут, поле, колонка или функция без поиска потребителей (бот, API, второй бот, старый движок) | — |

**Не блокеры** (фиксируются комментарием): дублирование, длинная функция, импорт внутри функции, отсутствие теста на некритичную ветку.

## Автор перед PR

1. `python -m unittest discover -s tests/unit -t tests/unit` — все тесты, включая проверку документации.
2. Пройти таблицу блокеров по своему diff.
3. В описании PR — это единственное место требований к нему:
   - **что и почему;**
   - **API-тесты:** строка, что шаг «API-тесты» прошёл, — или что сломалось и почему это допустимо (только с решением владельца);
   - **golden:** если запускался (PR меняет пути из `on.pull_request.paths` в `.github/workflows/golden.yml` или запуск вручную) — ссылка на комментарий бота с таблицей или на страницу запуска; пропущен без секрета `OPENAI_API_KEY` — так и написать;
   - **«Что проверить после деплоя»:** 3–5 конкретных действий в боте (что нажать или прислать → что должно получиться) и шаги в Railway, если нужны: переменные, порядок деплоя сервисов (воркер раньше бота и API). Проверять нечего (например, только документы) — так и написать.
4. Обновить `docs/PROGRESS.md`; архитектурное решение — запись в `docs/DECISIONS.md`.

## Ревьюер

1. Начать с diff и описания PR; сверить заявленное с изменённым.
2. Пройти блокеры сверху вниз: сначала API и данные, потом ядро, потом документация.
3. Блокер — письменно, со ссылкой на номер (B1–B14) и правило. Предложение — автор вправе отклонить с объяснением.
4. Golden: нарушения сравнивать с прошлыми прогонами (`docs/features/quality.md`), а не с нулём.
