Каждое архитектурное решение записывается сюда. Новые записи — **сверху**, над разделом «Восстановленные решения».

**Статусы:**
- **действует** — решение в силе;
- **предложено (PR #N)** — принято при разработке, вступает в силу после мёржа PR;

## 2026-10-08 — Правки владельца по галерее: тёмная тёплая и деловая темы

### D-070 — `ember_dark` без красного и без цветной заливки слайдов; `business_slate` — плоская, без полос и плашек

**Решение:** по итогам просмотра галереи PR #83 (темы `sunny_cream` и `mint_coral` утверждены, не меняются):
- **`ember_dark`** («слишком красно, красный в тексте плохо смотрится»): заголовки слайдов, заголовки пунктов и текст цитаты — светлые (`style.heading_color: text`, `quote_text: text`, `title_color` убран); акцент `primary` `#FFA23A` (оранжево-янтарный) текстом — только в цифрах, номерах и мелких подписях; градиент `brand → brand_2` — тёмно-оранжевый `#E8650F` → янтарный `#FFB23E` с тёмным текстом `on_brand` (малинового нет); целиком цветные только титул и финал (`style.full_color: cover`) — слайд-пауза и утверждение с картинкой рисуются на тёмном фоне с градиентной **панелью** (`panel` в YAML макета); цвета диаграмм — янтарный, синий, бирюзовый, лавандовый, зелёный, серый, без красного и розового.
- **`business_slate`** («выглядит как PowerPoint 2010»): диагональные полосы и градиентная плашка заголовка убраны; заголовок — тёмный текст с тонкой акцентной линией (`header: underline`); плоский стиль: `brand = brand_2` (рендерер рисует сплошную заливку вместо градиента), карточки — светлая заливка без полосы, скругление 16; один яркий акцент — насыщенный синий `#2563EB` к тёмно-синему тексту `#14213D`; на содержательных слайдах декора нет; титул и финал — плоская синяя заливка с крупными плоскими кругами; пауза — синяя панель на белом фоне.
- **Пороги галереи для спокойных тем — свои** (поле `gallery` темы): `business_slate` — доля цвета содержательного слайда ≥ 0,5%, линейной диаграммы ≥ 8%, медиана ≥ 5%; `ember_dark` — содержательные ≥ 2,5%. Остальные пороги и темы — как в D-065.

**Почему:** решения владельца по галерее; «больше воздуха, один акцент» и «акцент текстом только в цифрах» уменьшают долю цвета по построению — общий порог 4% требовал бы вернуть то, что владелец просил убрать. Плоская тема через `brand = brand_2` — без отдельного режима в макетах: все `$brand`-фигуры становятся сплошными.

**Отвергнутые альтернативы:**
- Оставить общий порог и добавить цвета в деловую тему (полосы карточек, цветные подложки) — против прямого требования «плоский стиль, больше воздуха».
- Красить заголовки пунктов `ember_dark` в акцент — владелец просил акцент текстом только в цифрах.
- Отдельные макеты паузы для тёмной темы — дублирование; панель задаётся одним полем `panel` в YAML и включается стилем темы.

**Статус:** предложено (PR #83); владелец утверждает по новой галерее

## 2026-10-08 — Сессия 4: всё визуальное — темы, декор, варианты, ИИ-картинки, галерея

Решения сессии 4 (`docs/design/09_PLAN.md`). Ориентиры владельца — три шаблона в `docs/design/references/` (Премиум, Focus, Креативный; PPTX и PNG-миниатюры).

### D-063 — Четыре новые темы в духе шаблонов-ориентиров; старые id переводятся на новые

**Решение:** темы фазы 1 — `business_slate` «Деловая серо-синяя» (светло-серый фон, белые карточки с синей полосой, тёмно-синий градиент на титуле и в плашке заголовка, номера во флажках — как Focus; по умолчанию), `ember_dark` «Тёмная тёплая» (почти чёрный фон, градиент малиновый → жжёный оранжевый, оранжевые заголовки и числа, иконки в градиентных квадратах — как Премиум), `sunny_cream` «Молочная с жёлтым» (молочный фон, белые карточки с жёлтой обводкой и полосой, номера в жёлтых квадратах, чёрный титул с жёлтым текстом, жёлтый слайд-пауза с белыми карточками — как Креативный; фирменную ломаную линию не копируем — свои круги, полукруги и точки), `mint_coral` «Мята и коралл» (изумрудно-бирюзовый градиент, коралловый акцент, волны). Токены темы расширены: `brand` / `brand_2` / `on_brand` (большие цветные площади, градиент), `accent` / `on_accent` (декор и плашки, не мелкий текст), `paper` / `on_paper` (карточки на цветном фоне), `on_status` (текст на шапках «за / против»); `style` — фигура номера, оформление заголовка, стиль и полоса карточки, плашка цитаты, пауза; `decor` — декоративные фигуры по наборам (`cover`, `band`, `content`, `header`, `pause`). Старые id (`graphite_light` → `business_slate`, `graphite_dark` → `ember_dark`, `azure_coral` и `fresh_green` → `mint_coral`) — поле `replaces` в YAML: их принимают профиль бота, запрос API (`theme_id`) и рендерер (DeckSpec прошлых колод); `GET /v1/themes` отдаёт новый список. Контраст всех пар «текст / фон», в том числе заданных стилем темы (цитата, пауза, номер), — ≥ 4.5:1, цвета диаграмм — ≥ 3:1 и CIEDE2000 ≥ 20 (тест).

**Почему:** главная жалоба владельца — дизайн блёклый; владелец хочет «между тем, что сейчас, и примерами». Темы сессии 1 различались только цветом токенов на одинаково белых слайдах. Перевод старых id — у второго бота и у пользователей бота в профиле сохранены старые темы (D-059: значения перечисления не удаляются).

**Отвергнутые альтернативы:**
- Оставить старые id и перекрасить темы — «Графит» и «Лазурь» уже не про новые темы, названия в сводке врали бы.
- Удалить старые id из запроса API — несовместимое изменение (D-059).
- Скопировать элементы шаблонов один в один — владелец просил приёмы, не копию.

**Статус:** предложено (PR #83); `sunny_cream` и `mint_coral` утверждены владельцем, `ember_dark` и `business_slate` переделаны — D-070

### D-064 — Оформление — нативные фигуры PPTX: градиенты, декор темы, фигуры номеров, цветные фоны

**Решение:** рендерер рисует оформление темы фигурами, которые перекрашиваются в PowerPoint: градиентная заливка (`gradFill`, два стопа `brand → brand_2`) у фона титула, финала и паузы, плашки заголовка, панели `big_number`, вывода диаграммы, шевронов, подложки иконок; декор темы — `custGeom` (дуги, круги, волны, многоугольники, точки), обрезанный по своей области (не выходит за слайд и за цветную полосу), прозрачность — `a:alpha`; оформление заголовка содержательного слайда по теме (`plate` — градиентная плашка, `underline`, `marker`, `bar`); номера — в фигуре темы (`circle`, `square`, `pennant`, `flag`, `chevron`); карточки — заливка или обводка и цветная полоса по стилю темы; картинки — `roundRect` со скруглением темы. Высота карточек и панелей — по содержимому: fitter после подбора кегля ужимает ячейки до «текст + поля» и ставит блок по центру зоны (`Fit.items_area`, `Fit.boxes`). У фигур по-прежнему нет `<p:style>` (без теней).

**Почему:** требования владельца (05_LAYOUTS.md, 8) и приёмы шаблонов-ориентиров; картинки фигур (PNG) не перекрашиваются и не редактируются. Ручная геометрия декора с обрезкой — PDF и PPTX выглядят одинаково, ничего не висит за краем слайда.

**Отвергнутые альтернативы:**
- Декор картинками PNG — не перекрашивается под правки пользователя.
- Пресеты «дуга» и «волна» PowerPoint — разная отрисовка в LibreOffice, нельзя обрезать по области.
- Фон слайда-паузы прямоугольником на весь слайд — его случайно двигают в PowerPoint; фон слайда (`p:bg`) — нет.

**Статус:** предложено (PR сессии 4)

### D-065 — Каталог: 25 вариантов; пороги доли цвета откалиброваны по галерее

**Решение:** все 22 варианта `05_LAYOUTS.md` плюс `statement.color_pause` (слайд-пауза целиком в цвете темы, пояснение в белой карточке) и два варианта «текст + картинка» для пунктов: `bullets.text_image_split` (пункты слева, картинка справа на пол-слайда) и `bullets.image_numbered` (картинка слева, пункты с номерами справа). Галерея (`tests/gallery/`, job `gallery`, артефакт `gallery-pdf`) — 25 вариантов × 4 темы × 3 заполнения = 300 слайдов; проверки: геометрия и поля, шрифт и кегль, нет `<p:style>` и автоподбора, вписывание без обрезки на min и typical, заполненность зоны контента 40–75% (typical, слайды с пунктами и панелями; `big_number` — градиентная панель на всю зону — исключение), доля цвета темы (пиксели PNG, ближе к цветам темы, чем к нейтральным, без площади картинок): титул и финал ≥ 35%, с диаграммой ≥ 10%, остальные содержательные **≥ 4%** (предлагалось 6%), медиана по колоде темы ≥ 8%; на заполнении min доля цвета только в отчёте.

**Почему:** после усиления элементов (цветные заголовки в тёмной и мятной темах, полосы карточек, волна и декор внизу слайда, градиентная полоса вывода у линии, градиентная панель вывода у столбцов) медианы тем — 11–29%, но списки и выводы в светлых темах держат цвет на номерах и декоре и дают 4–6%: дальнейший цвет делал их пёстрыми. Порог 6% по 05_LAYOUTS.md, 8 был предложением «уточняется по галерее».

**Отвергнутые альтернативы:**
- Оставить 6% и залить списки цветом — пёстро, хуже читается.
- Мерить долю цвета по геометрии PPTX, а не по PNG — не видит градиенты, обводки и цветной текст так, как их видит человек.

**Статус:** предложено (PR сессии 4)

### D-066 — SELECT: картинки, расстановка цветных слайдов, полярность сравнения

**Решение:** вариант с картинкой применим, только если пайплайн выделил слайду картинку (`has_image`), и получает +4 — картинка, если пришла, почти всегда встаёт. «Цветные» варианты (`color_heavy`: пауза, полоса, утверждение с картинкой на цветном фоне) — не ближе трёх слайдов к титулу, финалу и друг к другу (≤ одного на 3–4 слайда). `comparison.pros_cons` выбирается после CONTENT по полю `polarity` (модель указывает `neutral`, `pros_cons`, `before_after`). Одно число (`metrics`, 1 элемент) — `metrics.big_number`, план допускает metrics 1–4. Длина заголовка-утверждения и темы проверяется по метрикам шрифта на минимальном стиле, а не только числом знаков. Картинка не пришла — `without_image`: тот же kind, вариант без картинки и не «цветной».

**Почему:** требования владельца (пауза не чаще одного на 3–4 слайда; картинки на титуле и 2–3 слайдах); «за / против» по одному заголовку плана не определить — нужна полярность, которую видит только CONTENT.

**Статус:** предложено (PR сессии 4)

### D-067 — ИИ-картинки: SiliconFlow Z-Image-Turbo, параллельно с CONTENT, 3 на колоду; Pexels не используем

**Решение:** `core/images`: `POST {SILICONFLOW_BASE_URL}/images/generations` (`model: Tongyi-MAI/Z-Image-Turbo`, `image_size: 1024x1024`, `seed`), картинка — по URL из ответа (`images[0].url`, живёт час) или `b64_json`. Промпт = `image_query` плана (OUTLINE пишет его у 2–3 слайдов и `deck.cover_image_query` для титула, по-английски, сцена или предметы) + внешность людей по языку колоды (`prompts/v2/images/appearance.yaml`: ru, en — европейская, kk, uz — центральноазиатская; указывается всегда) + стиль темы и общие правила (`style.yaml`: фотореализм, без текста, букв, цифр, логотипов, без крупных лиц и рук) — хвост одинаков у всех картинок колоды. Не больше `per_deck` = 3 картинок (титул + 2 слайда, не подряд), параметры — `prompts/v2/images/config.yaml`. Генерация стартует после SELECT и идёт параллельно с CONTENT, у каждой картинки таймаут 20 с; не успела или ошибка — вариант без картинки, колода не ждёт. Файл — cover-crop под слот, ≤ 1600 px, JPEG q82, встраивается в PPTX. Стоимость — этап `images` в `decks.usage` / `decks.cost_rub` (0,5 ₽ за картинку ≈ $0.005 по прайсу SiliconFlow) — и в расходе клиента API. В заметках последнего слайда — «Изображения сгенерированы ИИ». Доступно всем в фазе 1 (ТЗ 11, вопрос 11): в боте всегда, в API — необязательное поле `image_mode` (`ai` по умолчанию, `none`). Без `SILICONFLOW_API_KEY` колоды собираются без картинок. Кэша картинок нет: промпт уникален для слайда, попаданий почти не будет, а Redis уже держит файлы колод API (D-058).

**Почему:** решение владельца по вопросу 11 ТЗ; без указания внешности модель рисует людей азиатской внешности. Бюджет: LLM ~1,2 ₽ на колоду (golden сессий 2–3) + 3 × 0,5 ₽ = ~2,7 ₽ — в пределах 3 ₽ (D-041).

**Отвергнутые альтернативы:**
- Pexels (D-006, D-042) — решение владельца: не используем; фото со стоков хуже попадают в смысл слайда и требуют атрибуции.
- 4 картинки на колоду — ~3,2 ₽, выше бюджета; число — в конфиге.
- Ждать картинки после CONTENT без таймаута — колода дольше на время самой медленной картинки.

**Последствия / что проверить:** точный формат ответа SiliconFlow проверен по документации и примеру провайдера, но не живым вызовом (из среды разработки провайдер недоступен) — клиент принимает оба вида ответа; первая проверка — golden с секретом `SILICONFLOW_API_KEY` и ручная после деплоя. Ключ в Railway — у воркера.

**Статус:** предложено (PR сессии 4); заменяет D-006 и часть D-042 про картинки

### D-068 — Уведомление владельцу о 80% и 100% суточного лимита клиента API

**Решение:** после создания колоды API (и при отказе по лимиту) `api.limit_alerts` сравнивает расход клиента за сутки UTC с `daily_limit`: на 80% и на 100% — по одному сообщению на порог в сутки (ключ Redis `api:limit_alert:<клиент>:<дата>:<порог>`, `SET NX`, 2 суток). Сообщение ставится задачей `notify_admins_job` в очередь и уходит от воркера (у сервиса api нет Telegram-токена) всем `ADMIN_TELEGRAM_IDS` в личку; в тексте — имя клиента, расход и команда `/apikey limit <имя> <лимит×2>`. Нет админов, Redis или очереди — уведомление пропускается, запрос клиента не страдает.

**Почему:** запрос владельца — узнавать о близком исчерпании лимита до жалоб пользователей второго бота.

**Отвергнутые альтернативы:**
- Отправка прямо из сервиса api — ему пришлось бы дать Telegram-токен.
- Счётчик порогов в БД — лишняя миграция ради флага на сутки.

**Статус:** предложено (PR сессии 4)

### D-069 — Титул — тема с заглавной буквы; сноски «по данным: <файл>» нет

**Решение:** заголовок титула — тема пользователя дословно, но первая буква — заглавная (`pipeline.deck_title`). Сноска источника у слайдов с числами по материалу («по данным: <файл>» / «ваш текст») убрана; сноска «Оценочные данные — проверьте перед показом» «по теме» остаётся.

**Почему:** решения владельца (мелочи сессии 4).

**Статус:** предложено (PR сессии 4); в части сноски по материалу заменяет D-017 / D-025 для нового движка

## 2026-10-02 — Роль сервиса — переменной SERVICE_ROLE, а не Config as Code

### D-062 — Образ сам выбирает процесс по SERVICE_ROLE (bot | worker | api)

**Решение:** CMD Dockerfile — `python src/start.py`; он читает `SERVICE_ROLE` (через `Settings`) и заменяет себя (`exec`) нужным процессом: `bot` (по умолчанию) — `src/main.py`, `worker` — `arq worker.WorkerSettings`, `api` — `uvicorn api.app:app` на `$PORT` с `--proxy-headers`. Неизвестная роль — выход с кодом 2 и понятной ошибкой, бот не запускается. В Railway роль задаётся переменной сервиса. `railway.api.toml` помечен устаревшим, `railway.worker.toml` работает до 01.12.2026 — воркеру уже сейчас задаётся `SERVICE_ROLE=worker`.

**Почему:** сервис api, созданный по инструкции PR #80, крашился: Railway отключает Config as Code — сервисы, созданные после 28.08.2026, не могут его включить, поле Railway Config File игнорируется, и сервис запускал CMD образа — бота без `TELEGRAM_BOT_TOKEN` (`TokenValidationError` по кругу). Существующие файлы конфигурации перестанут работать 01.12.2026 — та же поломка ждала бы воркер. Переменные окружения работают у любого сервиса и не зависят от этого механизма.

**Отвергнутые альтернативы:**
- Custom Start Command в настройках каждого сервиса — команда живёт только в интерфейсе Railway, вне репозитория; легко ошибиться при копировании.
- Infrastructure as Code Railway — новый механизм, его формат не изучен; переход — отдельной задачей, если понадобится больше, чем команда запуска.
- Угадывать роль по `RAILWAY_SERVICE_NAME` — неявно, ломается при переименовании сервиса.
- Отдельные образы на сервис — три сборки вместо одной.

**Последствия / что проверить:** новый сервис без переменной запускается как бот (как и раньше) — роль нужно задать до первого деплоя. Healthcheck `/v1/health` при желании задаётся в настройках сервиса api (раньше — в `railway.api.toml`).

**Статус:** предложено (PR #82)

## 2026-10-02 — Админ-команды бота для ключей API

### D-061 — Ключи API — командами `/apikey` в основном боте, только для ADMIN_TELEGRAM_IDS

**Решение:** владелец управляет клиентами API в личном чате с ботом: `/apikey create <имя> [лимит]`, `list`, `limit <имя> <лимит>`, `watermark <имя> on|off`, `revoke <имя>` (с подтверждением кнопкой), `rotate <имя>`. Доступ — Telegram ID из переменной `ADMIN_TELEGRAM_IDS` (через запятую) и только в личном чате. Фильтр `IsAdmin` стоит на обработчиках, которые регистрируются **первыми** в диспетчере: у не-админа фильтр не срабатывает, апдейт идёт дальше по боту, как любая незнакомая команда (бот не выдаёт, что команда существует); у админа «/apikey» не перехватывает обработчик состояния диалога. Логика — новый модуль `api/admin.py` (проверки, поиск клиента по имени или id, уникальность имён активных клиентов, сводка расхода за сутки и 30 дней); его вызывают и бот (`bot/admin.py`), и CLI `python -m api.keys` (теперь тоже принимает имя). Сообщение с ключом бот удаляет через 5 минут отложенной задачей воркера `delete_message_job` (`_defer_by=300`); если очередь недоступна — задачей в процессе бота.

**Почему:** владелец не разработчик — `railway ssh` и командная строка для неё неудобны (D-056 предполагал CLI). Бот уже есть, Telegram-аутентификация владельца — по ID, без новых паролей и публичных эндпоинтов. Удаление сообщения уменьшает время, пока ключ лежит в истории чата; задача воркера переживает перезапуск бота.

**Отвергнутые альтернативы:**
- Админ-эндпоинт API с паролем — ещё один секрет и публичная точка управления; владельцу нужен был бы curl.
- Веб-админка — отдельный сервис и вход ради редкой операции.
- Ответ «нет доступа» не-админам — выдаёт существование команды; требование владельца — как на незнакомую команду.
- Отдельный бот для админки — ещё один токен и сервис.
- Удаление через `asyncio.sleep` в боте всегда — теряется при перезапуске бота в эти 5 минут.

**Последствия / что проверить:** выкатка — воркер раньше бота (новая задача `delete_message_job`); ключ всё равно виден в чате 5 минут и в уведомлении на телефоне — владелец копирует его сразу. Команды в группах не работают намеренно.

**Статус:** действует (PR #81)

### D-055 — API — отдельный сервис FastAPI из того же образа; колоду собирает общий воркер

**Решение:** `src/api/` (FastAPI, uvicorn) — сервис Railway «api» (`railway.api.toml`, `uvicorn api.app:app --proxy-headers`). `POST /v1/decks` кладёт материал во временное хранилище (как бот), создаёт строку `decks` (`api_client_id`, `request.client.kind = "api"`) и ставит `generate_deck_job(deck_id)` в ту же очередь ARQ. Воркер собирает колоду тем же `core.generate_deck`; для колоды API сохраняет PPTX и PDF в хранилище, пишет предупреждения (`decks.warnings`, миграция `0006`), прогресс (Redis) и ставит `deliver_webhook_job`. Бот не менялся. Модули API без FastAPI (`errors`, `schemas`, `status`, `store`, `limits`, `auth`, `webhook`) импортирует воркер. `TELEGRAM_BOT_TOKEN` и `OPENAI_API_KEY` в `Settings` стали необязательными — сервису api они не нужны; воркер проверяет их на старте, бот падает без токена, как раньше.

**Почему:** ТЗ 4.2 — бот и API тонкие адаптеры одной функции ядра; один образ — один деплой и одна версия движка; общий воркер — колоды API сразу получают все улучшения движка.

**Отвергнутые альтернативы:**
- API внутри процесса бота — бот на long polling, падение одного валит другое, масштабирование раздельно невозможно.
- Отдельный воркер для API — вдвое больше LibreOffice и памяти; приоритет очереди — открытый вопрос 6 ТЗ 11, решим по замеру (сессия 5).
- Генерация прямо в HTTP-запросе — десятки секунд, таймауты прокси Railway.

**Статус:** действует (PR #80)

### D-056 — Ключи API: «fib_» + 256 бит, в БД только SHA-256; создаёт владелец командой

**Решение:** таблица `api_clients` (миграция `0006`): `key_hash` (SHA-256, уникальный), `key_prefix`, `webhook_secret`, лимиты, `watermark`, `active`. Ключ `fib_<43 знака>` передаётся в `Authorization: Bearer`. Создание, смена лимитов, выпуск нового ключа, отзыв, отчёт о расходе — `python -m api.keys create | list | set | rotate | revoke | usage` (в контейнере api через `railway ssh` или локально с `DATABASE_PUBLIC_URL`). Ключ и секрет webhook печатаются один раз.

**Почему:** ключ случайный и длинный — соль и медленный хэш не нужны, а SHA-256 позволяет найти клиента одним индексом. Команда вместо админ-эндпоинта — нет лишней поверхности атаки; ключей единицы.

**Отвергнутые альтернативы:**
- Хранить ключ как есть — утечка БД раздаёт доступ.
- bcrypt / argon2 — поиск клиента по ключу без индекса, лишняя задержка на каждом запросе.
- Админ-эндпоинт с токеном владельца — ещё один секрет и публичная точка управления ради редкой операции.

**Статус:** действует (PR #80); способ управления ключами дополнен D-061 — команды бота `/apikey` для владельца

### D-057 — Лимиты ключа: колоды в сутки по БД, частота — окно минуты в Redis

**Решение:** три лимита на клиента: `daily_limit` колод за календарные сутки UTC (по умолчанию 100), `decks_per_min` новых колод (10), `rate_limit_per_min` любых запросов (120). Суточный — `count(decks)` клиента с 00:00 UTC без упавших; проверка и вставка — в одной транзакции под `SELECT … FOR UPDATE` строки клиента. Минутные — `INCR` ключа `api:rl:{scope}:{client}:{минута}` в Redis; при отказе Redis запрос пропускается. Превышение — `429` (`DAILY_LIMIT_EXCEEDED` / `RATE_LIMITED`) с текстом и `Retry-After`; заголовки `X-RateLimit-*`. Повтор с тем же `Idempotency-Key` лимит не тратит.

**Почему:** требование владельца — лимит генераций в сутки и частоты запросов. Упавшая колода не списывается — как в боте. Сутки UTC однозначны для разработчика клиента. Блокировка строки клиента — чтобы параллельные запросы не прошли лимит оба.

**Отвергнутые альтернативы:**
- Скользящие 24 часа — сложнее объяснить «когда снова можно».
- Суточный счётчик в Redis — расходится с `decks` при сбоях; источник правды — БД.
- Один лимит «10 колод в минуту» из контракта — не ограничивает сутки и опрос.

**Статус:** действует (PR #80)

### D-058 — Файлы колод API: S3, если настроен, иначе Redis на 1 час; скачивание только через API

**Решение:** `core.storage.files`: с `S3_ENDPOINT_URL` — объекты `decks/ГГГГ/ММ/ДД/<deck_id>.<ext>`, срок ссылок 24 ч (удаление — правило жизненного цикла бакета на `decks/`, например 2 дня); без S3 — Redis `deckfile:<deck_id>:<fmt>` с TTL 1 час. `decks.files = {"pptx", "pdf", "expires_at", "backend"}`. `GET /v1/decks/{id}/files/{fmt}` отдаёт байты с проверкой ключа (`410 FILE_EXPIRED` после срока). **Redis на 1 час — временное решение до S3 (сессия 5).**

**Почему:** S3 на проде ещё нет, а второму боту файлы нужны сейчас; клиент скачивает файл сразу после `done`, часа хватает. Ссылка через API работает с любым хранилищем и не раздаёт файл без ключа.

**Отвергнутые альтернативы:**
- `302` на подписанную ссылку S3 (как в контракте) — без S3 не работает; ссылка живёт без ключа.
- Файлы в Postgres — раздувает БД и бэкапы.
- Отдавать файлы в теле статуса (base64) — +33% к размеру и тяжёлый опрос.

**Последствия:** Redis держит 2–3 МБ на колоду в течение часа; при сотнях колод в час — следить за памятью Redis до S3.

**Статус:** действует (PR #80)

### D-059 — С сессии 3: API меняется только обратно совместимо, миграции только добавляющие

**Решение:** в API v1 можно добавлять пути, необязательные поля запроса, поля ответа, коды ошибок, значения `stage`, темы; нельзя удалять и переименовывать поля, менять типы, делать поля запроса обязательными, убирать значения перечислений. Несовместимое — только `/v2`. Проверка — `tests/unit/test_api_contract.py`: схема OpenAPI против снимка `tests/unit/api_contract_v1.json` и все коды ошибок описаны в `docs/API.md`; отдельный шаг «API-тесты» в CI. Миграции — только добавляющие (исключение — удаление `presentations` в фазе 2 отдельным решением владельца). Правило — в `CLAUDE.md`.

**Почему:** с сессии 3 к API подключён второй бот с живыми пользователями; ломающее изменение роняет его без предупреждения. Добавляющие миграции позволяют откатить код без отката БД.

**Статус:** действует (PR #80)

### D-060 — Правки контракта API при реализации

**Решение:** отличия реализации от первоначального описания `04_CONTRACTS.md`, 7 — таблица 7.5 там же: `200` с байтами вместо `302`; `POST` отвечает полным `DeckStatus`; `/v1/themes` — объект `{"themes": [...]}`; `presentation_type` — строка с `UNSUPPORTED_TYPE`; `warnings` — объекты `{code, message}`; `DeckStatus` + `title`, `slides`, `started_at`; `GET /v1/usage`; новые коды ошибок; webhook подписывается отдельным секретом `whsec_…` (хранится как есть), а не ключом; ошибки валидации — `400`, а не `422`; колода «в работе» дольше 15 минут отдаётся как `failed` / `DEADLINE_EXCEEDED`, строка не правится (сторож — сессия 5).

### D-047 — Правила доклада по теме: определение вторым слайдом, общеизвестные факты без источника, без выдуманной статистики

**Решение:** в режиме «по теме» первый слайд плана — определение темы и её происхождение (кто, когда, почему; `role = definition`); если истории у темы нет — только определение. Доклад — готовый текст, а не шаблон: без указаний читателю («заполните…», «укажите…») и ссылок на несуществующие документы. **Отвергнутые альтернативы:**
- Запрет любых чисел «по теме» (как было) — исчезают даты и авторы, которые и есть суть определения.
- Проверка чисел «по теме» по внешнему источнику — источника нет; ограничиваемся правилом и сноской.

**Статус:** действует (PR #79)

| Средняя стоимость | 1,15 ₽ | 1,20 ₽ |

Выигрыш `medium` по нарушениям — в основном G-01 (выбор колонок таблицы); главная проверка сессии G-04 у `medium` не лучше (две из трёх колод без диаграммы долей). При этом `medium` вдвое медленнее: OUTLINE выходит за цель этапа (ТЗ 4.5: 20 с p95), колода — за цель 90 с p95 (94,7 с без картинок и очереди), и уже на девяти прогонах был отказ по таймауту. Ошибки выбора колонок исправлены правилами и данными (D-051), а не рассуждениями.

**Отвергнутые альтернативы:**
- `medium` для OUTLINE — время и отказ; стоимость почти та же, но цель по времени важнее.
- `medium` только для материала — тот же рост p95 именно на длинных входах, где OUTLINE и так дольше.

**Статус:** действует (решение по данным, вопрос 13)

### D-050 — Числа на слайдах «по материалу» проверяет код по источнику; исправление — один вызов, затем вычистка

**Решение:** после CONTENT каждое число на слайде с материалом должно найтись в `SourceDigest` (текст фрагментов или ячейки таблиц, сравнение с допуском формата); у числа `metrics` со ссылкой `source_ref` на ячейку — совпасть с ней (`core/checks/facts.py`). Не проверяются числа диаграмм (их ставит код), номера шагов и целые 0–12 без процента. При ошибках — один вызов «исправь факт» (`prompts/v2/fit/fix_facts.txt`, этап `fit`, одна попытка); если ошибки остались — код удаляет предложения и элементы с чужими числами, `metrics` с меньше чем двумя числами становится утверждением из плана. Всё записывается в `degradations`.

**Почему:** ТЗ 4.8.2: ни одного числа, которого нет в источнике. Golden старого движка показывал «рост в 6,6 раза» и посчитанные моделью проценты. Проверка по множеству чисел источника дешёвая и не требует LLM; повтор одним вызовом исправляет большинство ошибок, вычистка гарантирует правило, даже если повтор не помог.

**Отвергнутые альтернативы:**
- Проверка вторым вызовом LLM («найди выдуманные числа») — дороже, медленнее и сама ошибается.
- Повтор до победы — растёт время колоды; после одного повтора вычистка надёжнее.

**Статус:** действует (PR #79)

### D-051 — Диаграммы: числа ставит код из таблицы, вывод видит остальные колонки; ряды без диаграммы — замечание плана

**Решение:**
1. План ссылается на набор данных (`dataset: id, label_column, value_columns, rows`), числа, категории, порядок и доли в `Slide.data` ставит код (`planning/datasets.resolve`); строка «Итого» в ряд не входит; доли — колонка-процент с суммой 95–105% или доли, посчитанные кодом из положительных значений; иначе `chart_share → chart_series`.
2. Задание CONTENT для диаграммы получает не только показанный ряд, но и остальные колонки той же таблицы по тем же строкам («Рост, %», «Выполнение плана, %») — модель называет их главные значения в выводе (`datasets.related_columns`, `content.fill.data_block`). Эти числа есть в источнике, проверка D-050 их пропускает.
3. Замечание плана (D-048): таблица долей (сумма ≈100%) или ряд по времени из 4+ точек, который не попал ни на одну диаграмму, — «покажи диаграммой» (`datasets.coverage_remarks`, только «по материалу»).
4. Метрики фазы 1 — 2–4 карточки (`metrics.kpi_cards`); ряд из 5+ значений — диаграмма.

**Почему:** golden PR #79 (low): в G-01 модель выбирала колонку выручки, и рост каналов (+41%, −6%, +8%) и выполнение плана городов (87%, 112%) не попадали в колоду; в одной из трёх колод G-04 доли запросов шли карточками без диаграммы. Модель хорошо выбирает, *что* показать, но не должна переписывать числа таблицы — это делает код.

**Отвергнутые альтернативы:**
- Модель пишет числа диаграммы сама — ошибки переписывания и пропуски точек (golden старого движка).
- Несколько рядов на одной диаграмме ради всех колонок — разные единицы (₽ и %) на одной оси нечитаемы.
- Отдельный слайд на каждую колонку — колода разрастается, правило «одна колонка — одна диаграмма» соблюдается и без этого.

**Статус:** действует (PR #79)

### D-052 — Номер колоды не показывается пользователю; в ошибке — короткий код поддержки

**Решение:** сообщения бота о ходе генерации и выдаче не содержат `dk_…`. В тексте ошибки — «код для поддержки» из последних 6 знаков номера (`bot/delivery.support_code`); полный номер остаётся в логах и `decks`.

**Отвергнутые альтернативы:** полный номер в ошибке — длинный; без кода — поддержка не найдёт колоду.

**Статус:** действует (PR #79)

### D-053 — Материал идёт в новый движок; маршрутизация остаётся только для питч-дека

**Решение:** доклад с материалом (текст в сообщении или файл docx / pdf / pptx / txt) — новый движок (`dialog.engine_for`: доклад → новый, питч-дек → старый до сессии 3). **Отвергнутые альтернативы:** текст в аргументах задачи ARQ — большие сообщения в Redis и второй путь кода.

**Статус:** действует (PR #79); D-038 в части материала заменено этим решением

### D-043 — Structured outputs: json_schema strict с автоматическим переходом на json_object

**Решение:** клиент LLM нового движка (`core/llm/client.py`) запрашивает ответ как `response_format: json_schema, strict`. Если провайдер отвечает 400 на `response_format`, клиент запоминает это для модели на время жизни процесса и переходит на `json_object`: схема уходит текстом в системный промпт, ответ проверяет pydantic, при ошибке — повтор с прошлым ответом и перечнем ошибок. Режим можно задать принудительно: `LLM_STRUCTURED_OUTPUTS=json_schema | json_object`. Пределы (`maxItems`, `maxLength`) в любом случае стоят и в тексте задания, и в проверке кода (число элементов) и fitter'а (длина). **Почему:** ответ техлида на вопрос 6 — проверить первым делом, запасной вариант как в проекте. Из песочницы API недоступен, поэтому проверка — в CI, а код работает при любом результате.

**Отвергнутые альтернативы:** только `json_object` — теряем гарантии схемы у провайдера, который её поддерживает; только `json_schema` — колода падает, если прокси не пропускает параметр.

**Статус:** предложено (PR #78)

### D-044 — Вместимость считает код по геометрии YAML; формат LayoutSpec

### D-031 — Содержание слайда хранится по схеме kind; вариант — только раскладка

**Решение:** в `DeckSpec` у слайда поле `content` описано схемой **типа контента** (bullets: пункты с заголовком, текстом и иконкой; metrics: значения с подписями и статусом и т.д.), одинаковой для всех вариантов kind. Подробно — `docs/design/04_CONTRACTS.md`, 5.

**Почему:** правки фазы 4 (ТЗ 3.11) «сменить тему» и «другой вид слайда» становятся рендером без LLM, а «перегенерировать слайд» — одним вызовом CONTENT без повторного плана. Это же позволяет FIT переключить вариант, если текст не влез, не переписывая текст.

**Отвергнутые альтернативы:**
- Хранить содержание по слотам варианта (как `slots` в примере ТЗ 4.3.1) — смена варианта требует переписать текст моделью.
- Хранить только готовый PPTX — правки невозможны без новой генерации (как сейчас с PDF).

**Статус:** действует (утверждено 01.10.2026)

### D-032 — Анализ источника выполняется в том же вызове, что и план (OUTLINE)

**Решение:** OUTLINE возвращает `analysis` (жанр, тезисы со статусами, запросы, «чего нет») и затем план. Анализ сохраняется в `SourceDigest.analysis` и уходит в CONTENT. Отдельный вызов остаётся только для выжимки частей длинного документа (фаза 2).

**Отвергнутые альтернативы:** отдельный вызов ANALYZE до OUTLINE (буква ТЗ 4.8.1) — дольше и дороже без подтверждённого выигрыша.

**Статус:** действует (утверждено техлидом 01.10.2026, вопрос 7); по golden сессии 2 достаточно — см. «D-032 — оценка по golden» в записи сессии 2

### D-033 — Титул и финальный слайд собирает код

**Решение:** заголовок титула — тема пользователя дословно (`meta.title = topic`), модель пишет только подзаголовок (`deck.subtitle`). Финальный слайд («Спасибо за внимание» на языке колоды, контакты из брифа, автор) модель не пишет. План OUTLINE содержит только содержательные слайды.

**Почему:** G-05 — тема на титуле дословно; модель переформулирует её, если ей дать это поле. Финальный слайд одинаков по смыслу, тратить на него вызов и рисковать выдумкой не нужно.

**Статус:** действует (утверждено 01.10.2026)

### D-035 — Вместимость слотов считается по формуле, окончательное решение — за fitter

**Решение:** `max_chars` слота = знаков в строке × строк × 0,9, где знаков в строке = ширина / (кегль × 2 × k), k = 0,55 для обычного и 0,59 для полужирного начертания (замер Liberation Sans на ru/kk с запасом). Числа и тексты, известные до SELECT (утверждение, тема на титуле, значения метрик), проверяются по вместимости на минимальном стиле слота. Fitter мерит реальными метриками и решает окончательно. Таблицы — `docs/design/05_LAYOUTS.md`.

**Почему:** модели нужна понятная цифра до генерации (ТЗ 3.7, п. 1), а точная вёрстка по словам возможна только после. Коэффициенты уточняются стресс-галереей.

**Статус:** действует (утверждено 01.10.2026)

### D-036 — Слайд-запрос: роль `ask`, последний содержательный, код страхует

**Решение:** если в источнике есть запрос или решение к аудитории (`analysis.asks`), в плане обязателен слайд `role = ask` (kind `statement`, вариант с приоритетом `highlight_band`) — последний перед финальным. Если модель его не поставила, код добавляет его из текста запроса и убирает слайд с наименьшим приоритетом сюжета.

**Почему:** старый движок терял запрос (G-04) — при нехватке слайдов модель выбрасывала его наравне с деталями. Правило в промпте плюс проверка кода делают потерю невозможной.

**Статус:** действует (утверждено 01.10.2026)

## 2026-09-30 — Короткий диалог со сводкой, полнота рядов, источник у питч-дека

### D-023 — Диалог: тип → тема или текст → материал/бриф → сводка с «Сменить…»; прошлый выбор — в профиле

**Решение:**
- Пошаговые вопросы (аудитория, язык, дизайн, объём, число слайдов, есть ли материал, режим) заменены сводкой. После типа, темы и материала (у питч-дека — брифа) бот показывает одно сообщение со всеми параметрами. У каждого параметра — «Сменить…», экран выбора и возврат к сводке редактируют то же сообщение. Запуск — «✅ Сгенерировать презентацию».
- Режим (`source_mode`) — строка сводки, есть только при приложенном материале, меняется кнопкой. **Заменяет D-013**, где режим спрашивали отдельным вопросом с отметкой «как в прошлый раз».
- Дефолты — последний выбор из профиля: новые колонки `users.last_language`, `last_slide_count`, `last_audience`, `last_color_scheme` (миграция `0004`) и прежняя `users.source_mode`. Если выбора не было: язык Telegram пользователя (если поддерживается), иначе ru; доклад — 9 слайдов; «общая» аудитория; Classic Light; `strict`. Сохраняется по нажатию «Сгенерировать» (`dialog.last_choices`): число слайдов — только от доклада, режим — только если был материал. Платная схема не подставляется пользователю на бесплатном тарифе.
- Сообщение длиннее 300 символов на шаге темы — текст: у доклада это материал, у питч-дека — бриф; тема — первая строка. Файл на шаге темы — материал доклада.
- Вопрос об объёме (`content_volume`) из бота убран: бот передаёт `medium`, объём задаётся числом слайдов. В API параметр остаётся.
- Тексты, клавиатуры и дефолты — чистые функции в `src/dialog.py`; обработчики и FSM — в `src/main.py`. Кнопки старого диалога в истории чата (`aud:`, `lang:`, `scheme:`, `oq:`) отвечают «Сессия устарела» и начинают заново.

**Почему:** старый диалог — до 9 шагов до генерации, повторному пользователю приходилось заново отвечать на те же вопросы. В сводке он видит всё и жмёт одну кнопку. Довод D-013 («подставленное молча значение скрыто») сводка снимает: режим виден перед запуском и меняется одним нажатием. Правка одного сообщения вместо новых не засоряет чат.

**Отвергнутые альтернативы:**
- Оставить пошаговый диалог и только подставлять ответы — шагов столько же.
- Хранить прошлый выбор в FSM (Redis) — теряется при `/new` и через 7 дней.
- Одна JSON-колонка `users.last_choices` вместо четырёх — проще добавлять параметры, но без типов и значений по умолчанию на уровне БД. Параметров мало, отдельные колонки нагляднее в запросах аналитики.
- Сохранять выбор сразу при каждом «Сменить…» — пользователь мог передумать и не генерировать; по нажатию «Сгенерировать» сохраняется то, с чем реально делали колоду.

**Последствия / что проверить:** миграция `0004` применяется при старте бота и воркера (advisory lock из `init_db`). Порядок деплоя сервисов не важен: воркер новых полей не читает.

**Статус:** действует (PR #76)

### D-024 — Полнота ряда и обязательные пункты материала — отдельными правилами промпта доклада

**Решение:**
- `prompts/doklad/layout_catalog.txt`, правило 6: показатель ряда (доля, рост, план, балл) стоит у **каждого** элемента, у которого он есть в материале, в любом layout. Проверка «доли в сумме ≈ 100%». Ссылка на правило — в описании metrics.

## 2026-09-30 — gpt-6-luna и CI

### D-020 — Параметры запроса к LLM зависят от модели и описаны в `prompts/models.yaml`

**Решение:** аргументы `chat.completions.create` собирает `generation/llm_models.completion_params` по профилю модели из `prompts/models.yaml`:
- `token_param` — `max_tokens` или `max_completion_tokens`;
- есть ли рассуждения;
- допустимые `reasoning_effort`;
- когда можно `temperature` — `always`, `effort_none` или `never`;
- JSON-режим, потолок вывода, цены.

Профиль ищется по точному имени, затем по самому длинному префиксу; нет записи — прежние параметры (как у gpt-4o). У моделей с рассуждениями `max_completion_tokens` = бюджет видимого JSON + запас на рассуждения по уровню effort (low — 8000, medium — 16 000, …), не выше лимита модели. Новые поля уходят через `extra_body`: `openai==1.35.0` не знает аргументов `max_completion_tokens` и `reasoning_effort`.

**Почему:** на проде gpt-6-luna упала с 400 на `max_tokens`. По документации OpenAI (сверено по вторичным источникам: developers.openai.com закрыт в песочнице):
- токены рассуждений входят в `max_completion_tokens`;
- `temperature` принимается только при `reasoning_effort=none`, иначе следующий 400;
- `response_format` поддерживается.

Без запаса рассуждения съедают лимит, и JSON обрезается. Потолок — не расход: платим за фактические токены.

**Отвергнутые альтернативы:**
- Обновить `openai` до версии с этими аргументами — лишний риск для прода (совместимость с `httpx` и другими пакетами) ради двух полей, которые и так уходят через `extra_body`.
- Условия `if model.startswith(...)` в коде — правила модели разбросаны по вызовам. Правило 4 CLAUDE.md: конфиги LLM — в `prompts/`.
- Один общий множитель лимита — токены рассуждений зависят от effort, а не от длины ответа.

## 2026-09-26 — Число слайдов и режим работы с материалом в боте

### D-013 — `source_mode` хранится в `users.source_mode`, прошлый выбор предлагается первым, а не подставляется молча

**Решение:** правило из ТЗ 3.2 («выбор запоминается в профиле и подставляется по умолчанию») реализовано так:
- последний выбор пишется в новую колонку `users.source_mode` (миграция `0003`);
- вопрос задаётся каждый раз, когда приложен материал, но прошлый вариант стоит первым с пометкой «✓ как в прошлый раз»;
- значение уходит в `UserRequest.source_mode` (`strict` | `extend`; `None` в режиме «по теме» и у задач, поставленных в очередь до деплоя).

В API значение по умолчанию — `strict` (ТЗ 3.10).

**Почему:** в Telegram «подставить по умолчанию» без вопроса значит отправить генерацию с настройкой, которую пользователь не видит на этом шаге. Экран подтверждения сразу ставит задачу, и изменить режим было бы негде. Режим напрямую влияет на то, откуда берутся факты, а цена ошибки — выдумка на слайде. Отмеченный вариант стоит пользователю одного нажатия, как и отдельная кнопка «Создать», но выбор остаётся на виду. `strict` в API — безопасный вариант и совпадает с прежним поведением «строго по материалу».

**Отвергнутые альтернативы:**
- Не спрашивать повторно, брать значение из профиля, менять в «👤 Профиль» — режим скрыт в момент генерации, пользователь забывает, что выбрал «дополнить».
- Хранить выбор в FSM (Redis) — живёт 7 дней и теряется при `/new` → `state.clear()`.
- `extend` по умолчанию в API — интегратор без явного параметра получает общие знания вперемешку с его данными.

**Статус:** заменено D-023 (30.09.2026): режим виден в сводке перед генерацией и меняется кнопкой; колонка `users.source_mode` и `strict` в API остаются.

### D-014 — Число слайдов доклада: 5 / 7 / 9 / 12 / 15, бюджет токенов растёт пропорционально

**Решение:** бот спрашивает число слайдов доклада кнопками 5, 7, 9 (по умолчанию, отмечено ✓), 12, 15 и передаёт его в `slide_count_hint`. `max_tokens` основного вызова: 8000 до 9 слайдов включительно, дальше пропорционально (`ceil(8000 · N / 9)`), не больше 16 000. Для питч-дека вопроса нет: его каркас жёстко задан на 11 слайдов.

**Почему:** раньше бот число слайдов не передавал вовсе, и доклад всегда был из 9 (баг). Кнопки вместо ввода числа — меньше ошибок ввода, а значения укладываются в границы `UserRequest.slide_count_hint` (5–20). Выше 15 не предлагаем: тарифные лимиты не решены (ТЗ 11, вопрос 1), а 20 слайдов в одном вызове упираются в потолок ответа модели. Бюджет 8000 подобран под 9 слайдов (решение 2026-08). При том же бюджете 12–15 слайдов обрезались бы молча, поэтому бюджет растёт, а для 9 слайдов остаётся прежним.

**Отвергнутые альтернативы:**
- Свободный ввод числа — лишние проверки, опечатки, выход за 5–20.
- Фиксированный `max_tokens = 16000` для всех — меняет поведение и стоимость прежних 9-слайдовых колод без прогона корпуса.

**Последствия / что проверить:** каркасы доклада в промпте по-прежнему требуют «строго 9 слайдов» (`PROMPT_REVIEW.md`, 10.5). Пока их не поправят через golden-корпус, при выборе не 9 модель может вернуть 9. Воркер сравнивает число слайдов с выбранным и пишет предупреждение в лог. *Дополнено 30.09.2026:* каркасы поправлены (П7, D-016) — «строго 9» больше нет.

**Статус:** действует (PR #73)

**Почему:** ТЗ 5 требует хранить команды запуска в репозитории. Config-as-code в Railway имеет приоритет над интерфейсом. Если положить `startCommand` в общий `railway.toml`, воркер, читающий его по умолчанию, запустил бы бота.

**Отвергнутые альтернативы:**
- `Procfile` — при сборке из Dockerfile Railway его не использует.
- Общий `railway.toml` со `startCommand` — ломает один из двух сервисов.

**Статус:** предложено (PR #65)

### D-011 — Формат промптов: `.txt` для цельных текстов, `.yaml` для словарей, загрузка при импорте

**Решение:** промпты лежат в `prompts/` в корне репозитория. Цельный промпт — файл `.txt`. Наборы по ключу enum (тип, аудитория, объём, layout) — файлы `.yaml`. Подстановки остаются прежними (`str.format` для system, `string.Template` для остальных). Файлы читаются при импорте модуля. Версия набора — `prompts/VERSION`, пишется в лог генерации.

**Почему:** правило 4 `CLAUDE.md`, ТЗ 4.2. YAML уже выбран в ТЗ для storylines, layouts и тем — один формат на всё. Чтение при импорте роняет процесс на старте при опечатке в имени файла, а не посреди генерации.

**Отвергнутые альтернативы:**
- Jinja2 для промптов — лишняя логика в текстах; при переносе важно было сохранить промпты байт в байт.
- Один большой YAML со всеми промптами — неудобно ревьюить диффы длинных текстов.

**Статус:** предложено (PR #67)

### D-001 — PPTX — первичный артефакт, PDF получаем конвертацией через LibreOffice

**Решение:** единственный рендерер строит PPTX из `DeckSpec` (python-pptx). PDF получается конвертацией готового PPTX через LibreOffice headless. Второго HTML-рендера нет.

**Отвергнутые альтернативы:**
- HTML → PPTX — растр или поехавшая вёрстка.
- Два рендерера из одной спецификации — двойная работа, диаграммы расходятся.

**Последствия / что проверить:** запасной план из ТЗ — если спайк фазы 0 покажет неприемлемое качество диаграмм или шрифтов в LibreOffice, PDF рендерится из той же `DeckSpec` отдельным HTML-рендером (Playwright уже в образе). Результаты спайка — `docs/SPIKE_PPTX.md` (PR #68): на сервере качество приемлемое, ждём ручной проверки в PowerPoint, Keynote и Google Slides.

**Статус:** действует (подтверждение по спайку ожидает ручной проверки)

### D-002 — Макет выбирает код, а не LLM

**Решение:** вариант макета выбирает детерминированный алгоритм по форме контента и `seed` колоды (ТЗ 3.4.3). LLM определяет только тип контента слайда.

**Почему:** воспроизводимость, разнообразие по правилам. Модель не может выбрать несуществующий layout.

**Отвергнутые альтернативы:** выбор моделью — уже сейчас нестабилен: пустые колонки, чужие layout'ы.

**Статус:** действует

### D-003 — План и наполнение — раздельные вызовы LLM

**Решение:** один вызов строит план колоды (OUTLINE). После выбора варианта макета слайды наполняются параллельными вызовами (CONTENT) с известной вместимостью слотов.

**Почему:** вместимость известна до написания текста, слайды наполняются параллельно, ретрай идёт по слайду, а не по колоде.

**Отвергнутые альтернативы:** один большой вызов (текущий).

**Статус:** действует

### D-004 — Тип презентации → сюжет, тема → визуал

**Решение:** `presentation_type` управляет структурой повествования (storyline). Визуал определяется темой оформления и вариантами макетов.

**Почему:** комбинаторное разнообразие, нет дублирования шаблонов.

**Отвергнутые альтернативы:** шаблон на тип (текущий).

**Статус:** действует

### D-005 — Шрифты только из безопасного списка

**Решение:** темы используют шрифты только из безопасного списка. Список утверждается на фазе 0 по тесту на всех целевых языках (ТЗ 6.3).

**Почему:** PPTX у пользователя не должен подменять шрифты.

**Отвергнутые альтернативы:** Google Fonts — красиво в PDF, подмена в PowerPoint.

**Последствия / что проверить:** предварительный список по спайку — Arial, Calibri, Times New Roman (`docs/SPIKE_PPTX.md`, PR #68). Итоговый список записать сюда после ручной проверки.

**Статус:** действует (список шрифтов ожидает ручной проверки)

### D-006 — Pexels вместо Unsplash для web-картинок

**Решение:** основной источник web-картинок — Pexels с указанием авторства. Unsplash выключен до письменного подтверждения от них.

**Почему:** условия Unsplash (хотлинкинг, «неавтоматизированное» использование) конфликтуют со встраиванием картинки в файл.

**Отвергнутые альтернативы:** Unsplash.

**Статус:** заменено D-067 (сессия 4): картинки нового движка — ИИ (SiliconFlow), Pexels не используется

### 2026-08 — Генерация в отдельном ARQ-воркере

**Решение:** бот (`src/main.py`) только ставит задачу в очередь ARQ на Redis; LLM, картинки и рендер PDF выполняет отдельный процесс `src/worker.py`. `max_jobs=5`, `job_timeout=180 с`.

**Почему:** синхронная генерация внутри хендлера блокировала бота на всё время генерации — остальные пользователи не получали ответов.

**Отвергнутые альтернативы:**
- Celery — тяжелее для async-стека aiogram.
- Фоновые задачи внутри процесса бота — не изолируют Chromium и не переживают рестарт.

**Статус:** действует (ТЗ 4.1 сохраняет ARQ-воркер)

### 2026-08 — PDF через HTML-шаблоны Jinja и Playwright

**Решение:** презентация рендерится из Jinja2-шаблона в HTML и печатается в PDF через headless Chromium (Playwright). Один браузер на воркер, новый контекст на каждый рендер. Холст 794×446 px.

**Почему:** CSS даёт быструю итерацию дизайна; Chromium корректно рисует веб-шрифты и SVG.

**Отвергнутые альтернативы:** не зафиксированы.

**Последствия:** для редактируемого PPTX этот путь не подходит — см. риски в `docs/CURRENT_STATE.md`.

**Статус:** заменено D-001 (рендер один — PPTX, PDF — конвертацией). HTML-путь работает до перевода бота на новый движок (фаза 3)

### 2026-08 — Отдельный шаблон для DOKLAD

**Решение:** DOKLAD рендерится своим шаблоном `templates/doklad/` независимо от `source_type`. Раньше шаблон выбирался по `source_type`: conference для темы, corp_report для материала.

**Почему:** утверждённый макет доклада с собственной палитрой и набором layout'ов.

**Отвергнутые альтернативы:** ветвление между conference и corp_report по `source_type` — удалено.

**Статус:** заменено D-004 (тип презентации задаёт сюжет, визуал — тема; шаблонов на тип нет)

### 2026-08 — Иконки Tabler вшиты в шаблон как base64

**Решение:** webfont Tabler Icons (woff2, MIT) встроен в CSS шаблона doklad как `data:` URI. Используется закрытый список из 25 иконок; неизвестное имя от модели заменяется на `point`.

**Почему:** Playwright открывает HTML через `data:` URL — относительные пути к файлам шрифта не резолвятся, а CDN уже подводил (Mermaid).

**Отвергнутые альтернативы:**
- CDN — ненадёжен при рендере.
- Эмодзи — непредсказуемо рендерятся в Chromium.
- Файл шрифта рядом с шаблоном — не резолвится из `data:` URL.

**Последствия:** шаблон весит 640 КБ.

**Статус:** заменено D-001 (в PPTX иконочный веб-шрифт не используется — иконки картинками или фигурами, ТЗ 3.8)

### 2026-08 — Для DOKLAD layout выбирает модель по каталогу

**Решение:** для доклада модель сама выбирает layout каждого слайда из `LAYOUT_CATALOG` (bullets, metrics, two_column, diagram, quote, timeline, image_full, image_hero) по смысловой канве из 9 слайдов. Первый слайд принудительно `title`, последний — `closing`.

**Почему:** жёсткая позиционная структура давала однотипные презентации и пустые слайды там, где контент не подходил под заданный layout.

**Отвергнутые альтернативы:** жёсткая структура «позиция → layout», как у питч-дека.

**Последствия:** модель иногда выбирает layout без содержимого — см. следующие два решения.

**Статус:** заменено D-002 (макет выбирает код)

### 2026-08 — Пустые слайды не роняют генерацию

**Решение:** слайд, у которого нет поля, нужного его layout'у, не вызывает ошибку валидации. Вместо этого в `llm.py`:
1. локальная деградация в bullets без вызова LLM — для two_column, metrics, diagram, image_hero, timeline;
2. если после этого содержимого нет — один точечный дозапрос к LLM только на этот слайд;
3. если и он не помог — слайд остаётся как есть, пишется предупреждение в лог.

**Почему:** жёсткая валидация с ретраем всей генерации на практике роняла job целиком — модель стабильно повторяла тот же пустой слайд на всех 3 попытках, и пользователь не получал ничего.

**Отвергнутые альтернативы:**
- `raise ValueError` в валидаторе и ретрай всей генерации — ухудшил надёжность.
- Только логирование без исправления — пользователь видел пустые слайды.

**Статус:** заменено D-003 (ретрай по слайду при раздельном наполнении). Сам принцип «не ронять колоду, деградировать слайд в bullets без LLM» сохранён в ТЗ 4.6

### 2026-08 — Заполняемость важнее разнообразия

**Решение:** в промпте правило «минимум 4 разных layout» смягчено до «стремись, если содержание позволяет». Добавлен явный приоритет: не выбирать layout, для которого нет содержимого. Описание `two_column` расширено: не только сравнение, но и два самостоятельных тезиса.

**Почему:** требование разнообразия толкало модель ставить layout без содержимого, особенно `two_column` на темах без естественного противопоставления.

**Отвергнутые альтернативы:** не зафиксированы.

**Статус:** заменено D-002 (разнообразие обеспечивает код по правилам ТЗ 3.4.3, а не промпт)

### 2026-08 — Ограничение числа страниц PDF через page_ranges

**Решение:** `page.pdf(..., page_ranges="1-N")`, где N — число слайдов.

**Почему:** Chromium режет документ по фиксированной высоте страницы, а не по границам слайдов. Доли пикселя переполнения давали лишнюю пустую последнюю страницу (реальный PDF: 9 слайдов → 10 страниц).

**Отвергнутые альтернативы:** подгонка CSS-высот — хрупко, зависит от метрик шрифта.

**Статус:** заменено D-001 (PDF — конвертация PPTX, печати из Chromium нет)

### 2026-08 — Бюджет токенов основного вызова 8000

**Решение:** `max_tokens=8000` вместо 4500.

**Почему:** в режиме `json_object` при нехватке бюджета модель закрывает JSON раньше и молча теряет последние слайды (было 8 слайдов вместо 9 без ошибки парсинга).

**Отвергнутые альтернативы:** не зафиксированы.

**Статус:** заменено D-003 (одного большого вызова нет)

### 2026-08 — Профиль автора не от модели

**Решение:** ФИО и группа докладчика вводятся пользователем в разделе бота «👤 Профиль», хранятся в `users.author_name/author_group` и подставляются в `PresentationMeta` воркером. Модель эти поля не заполняет.

**Почему:** данные о пользователе нельзя доверять генерации.

**Отвергнутые альтернативы:** не зафиксированы.

**Последствия:** колонки добавлены через `ALTER TABLE ... IF NOT EXISTS` в `init_db`, так как Alembic в проекте нет.

**Статус:** действует (ТЗ 3.2: `author` — из профиля). Примечание про `ALTER TABLE` снимается с переходом на Alembic (D-009)
