## 2. Пайплайн генерации

**Путь от сообщения до PDF (код):**

1. `src/main.py` — диалог: `on_type` → `on_topic` → `on_audience` → `on_language` → `on_scheme` → `_ask_onboarding_question`.
   - Питч-дек: вопрос-бриф.
   - Доклад: объём (`content_volume`) и «есть ли материал»; если есть — `on_material` (текст или файл).
2. `_confirm_and_generate` проверяет лимит и решает про водяной знак. `generate_and_send` собирает `request_data` (обычный dict) и вызывает `arq_pool.enqueue_job("generate_presentation_job", ...)`. Байты документа передаются прямо в аргументах задачи.
3. `src/worker.py::generate_presentation_job`:
   1. `extract_from_document` — если прислан файл;
   2. `UserRequest.model_validate`;
   3. `llm.generate_presentation_structure` — основной вызов LLM, валидация, дозаполнение пустых слайдов;
   4. диагностические логи (только для доклада);
   5. подстановка ФИО и группы из профиля в БД (только для доклада);
   6. `image_fetcher.fetch_images_for_slides`;
   7. `template_engine.render_presentation` (Jinja → HTML);
   8. `pdf_renderer.html_to_pdf` (Playwright);
   9. `storage.upload_pdf`;
   10. `record_presentation` (счётчик +1);
   11. `send_document`.

   Между этапами редактируется статусное сообщение пользователю.

**LLM (код):**
- Один провайдер: OpenAI-совместимый API через `api.proxyapi.ru` (значение по умолчанию в `src/config.py`). Модель `gpt-4o` (меняется через env `OPENAI_MODEL`).
- Параметры: `temperature=0.7`, `response_format=json_object`, `max_tokens=8000`.
- Вызовов на одну презентацию:
  - **1 основной**;
  - до **3 попыток** всей генерации через tenacity при любой ошибке (сеть, JSON, валидация);
  - **0…N дозапросов** (`max_tokens=800`) — по одному на каждый слайд без содержимого, если локальная деградация слайда в bullets не помогла.
- Всё строго последовательно, параллельных LLM-вызовов нет.

**Где промпты:** только в коде — строковые константы в `src/generation/llm.py`: `SYSTEM_PROMPT`, `STRUCTURE_BLOCKS`, `LAYOUT_CATALOG`, `DOKLAD_NARRATIVE_TOPIC/TEXT`, `VOLUME_INSTRUCTIONS`, `TYPE_CONTEXTS`, `AUDIENCE_CONTEXTS`, `_LAYOUT_PATCH_INSTRUCTIONS`. Отдельных файлов нет (нарушает правило из `CLAUDE.md`).

**Промежуточное представление:** Pydantic-модель `PresentationSchema` (`src/schemas/presentation.py`), пример:

```json
{"meta": {"title": "...", "presentation_type": "doklad", "audience": "general", "language": "ru",
          "author_name": null, "author_group": null},
 "slides": [{"index": 2, "layout": "bullets", "title": "...", "subtitle": "...",
             "bullets": [{"text": "...", "subtitle": "...", "icon": "target"}],
             "metrics": [], "two_column": null, "timeline_items": [], "mermaid_code": null,
             "image_query": "english query", "competition_table": null, "team_members": []}]}
```

- 16 значений `SlideLayout` — один общий enum на все типы презентаций.
- Слайдов от 5 до 20. Первый принудительно `title`, последний — `closing`.

**Выбор layout и шаблона:**
- Питч-дек, конференция, отчёт: layout для каждой позиции жёстко задан в промпте (`STRUCTURE_BLOCKS`).
- Доклад: модель сама выбирает layout из каталога (`LAYOUT_CATALOG`) по смысловой канве. Затем код раскладывает слайды без содержимого в bullets или дозапрашивает их.
- Остальные типы (диплом, обучение, продажи, роадмап) — общий fallback-промпт; из меню бота недостижимы.
- Шаблон — по `TEMPLATE_MAP[presentation_type]` в `src/generation/template_engine.py`: pitch_deck / conference / corp_report / doklad; прочие типы → pitch_deck.
- Внутри шаблона — ветвление `if/elif` по `slide.layout`. В doklad дополнительно:
  - сетка bullets зависит от числа пунктов;
  - предпоследний слайд рисуется как нумерованные «выводы»;
  - для незнакомого layout есть запасной `else`.

**Рендер PDF:** HTML + CSS → Playwright/Chromium (`src/generation/pdf_renderer.py`).
- Один браузер на весь воркер, новый контекст на каждый рендер.
- HTML передаётся как `data:` URL.
- Ожидание `networkidle` до 5 с (шрифты), ожидание SVG Mermaid до 10 с.
- `page.pdf(794×446px, page_ranges=1-N)`.

**Шаблоны:** 4 файла `src/templates/<тип>/template.html`, каждый со встроенным CSS.

| Шаблон | Строк | Веток layout | Цветовые схемы | Геометрия |
|---|---|---|---|---|
| pitch_deck | 583 | 14 | 4 | свой flex/grid |
| conference | 391 | 13 | 4 | абсолютные зоны из `src/layouts/zones.py` |

| doklad | 490 (640 КБ из-за шрифта) | 10 + запасной `else` | 1 фиксированная палитра, `color_scheme` игнорируется | свой flex/grid |

**Картинки (код):**
- Поиск в Unsplash (горизонтальные, берётся 2-й результат, размер regular); при неудаче — Pexels.
- Кэш в Redis на 24 часа, не более 3 параллельных запросов.
- В PDF вставляются **ссылками**: Chromium скачивает картинку уже при рендере.
- ИИ-генерации картинок нет. SiliconFlow не подключён — не найдено.
- Параметр `team_photo_urls` воркер не передаёт, поэтому в слайде команды — эмодзи вместо фото.

**Шрифты (код):**
- Outfit и DM Sans с Google Fonts CDN во всех шаблонах; если не загрузились за 5 с — системные.

## 5 главных рисков для «редактируемый PPTX + 4–5 вариантов макета на тип контента»

1. **Дизайн существует только как HTML/CSS.**
   - Геометрия зашита во flex/grid четырёх шаблонов; единой машиночитаемой спецификации макета нет.
   - `zones.py` приблизительный, неполный, doklad и pitch_deck его не используют.
   - PPTX-рендерер придётся писать с нуля параллельно HTML. С вариантами число сочетаний (layout × вариант × тема × 2 рендерера) взрывается.
   - Без единого описания макетов HTML и PPTX быстро разойдутся.

   > **Примечание (2026-09-26, решение D-001, ТЗ 4.6):** второго рендерера не будет. Рендер один — PPTX из `DeckSpec`; PDF получается **конвертацией готового PPTX** через LibreOffice headless, а не вторым HTML-рендером. Поэтому расхождение HTML и PPTX снимается как риск. Остаётся задача единой машиночитаемой спецификации макетов (`layouts/<kind>/<variant>.yaml`, ТЗ 4.3.2) — теперь как источника для одного рендерера. Запасной план (отдельный HTML-рендер PDF из той же `DeckSpec`) — только если спайк фазы 0 покажет неприемлемое качество LibreOffice.
2. **Элементы без нативного аналога в PPTX:**
   - Mermaid (JS + CDN), SVG-кольца метрик, иконочный веб-шрифт, CSS-оверлеи.
   - Шрифтов Outfit и DM Sans у пользователя может не быть — PowerPoint их подменит.
   - Каждый такой элемент придётся либо вставлять картинкой (теряется редактируемость), либо рисовать нативными фигурами и графиками.
3. **Переполнение текста.**
   - HTML прячет лишнее через `overflow:hidden`; в PPTX такого нет, автоподбор размера по-разному работает в PowerPoint, Keynote и Google Slides.
   - Лимиты полей подняты до 400 символов, переполнение в HTML-макетах уже подтверждалось.
   - У каждого варианта своя вместимость, а модель о ней не знает.
4. **Выбор варианта и воспроизводимость.**
   - Layout уже сейчас выбирает модель, и это нестабильно: пустой `two_column` 3 раза подряд, чужие layout'ы, обрезка ответа.
