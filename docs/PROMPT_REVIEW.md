# Разбор промптов текущего движка на двух входах

**Дата:** 26.09.2026 · **Версия промптов:** `prompts/VERSION` = `2026-09-26` (коммит `05a7af4`, после мёржа PR #71)
**Статус:** диагностика. Код и промпты в этом PR **не менялись**. Правки из раздела 7 — предложение на ревью техлиду.

Поводом стали две колоды, которые бот собрал 26.09.2026 из отчёта о продажах кофеен и из ТЗ хакатона VK. Владелец продукта нашёл в них 7 ошибок. Гипотеза техлида: причины в основном не в модели, а в промпте, схеме и формате входных данных. Этот документ её проверяет.

## 0. Коротко

1. **Гипотеза подтверждается.** Каждую из 7 ошибок промпт и схема прямо требуют или разрешают. Чистых нарушений моделью явных инструкций два: «95%» в колоде хакатона и пропущенный слот «Сложности». Но и в этих случаях соседние инструкции толкают модель к нарушению.
2. **Главный источник выдумки — блок «ДАННЫЕ И ЦИФРЫ» в системном промпте.** Он велит брать числа «из своих знаний» и писать «реалистичный диапазон» вместо пропуска. Блок действует и в режиме «по документу», где противоречит запрету выдумывать из `source_material.txt`. Системный промпт при этом весомее пользовательского.
3. **Каркас доклада по материалу — «что сделано → результаты» из 9 слайдов, для любого документа.** ТЗ хакатона поэтому превращается в отчёт о сделанном. Короткий отчёт растягивается на 7 смысловых слотов, отсюда повторы. Один и тот же каркас даёт одинаковую последовательность макетов.
4. **Требования к числу элементов жёсткие и расходятся между файлами:** metrics — 3, timeline — 4 этапа, у каждого дата, bullets — 4 пункта. Модель подгоняет материал под числа: 4 канала обрезает до 3, к 3 приоритетам добавляет четвёртый, 3 метрики добирает выдуманным «95%».
5. **Таблицы приходят плоскими строками без адресов ячеек.** В промпте нет понятия «к какой строке и колонке относится число». «+8» из строки «Продажи в зале» поэтому приклеилось к общей выручке. Проверка «число есть в источнике» (ТЗ 3.3.3) такую ошибку **не поймает**: «8» в источнике есть. Нужна проверка пары «число + подпись» через ссылку на ячейку. Это вошло в новые принципы ТЗ 4.8.
6. **Заголовки-темы задаёт сам промпт.** Правило 5 каталога приводит как верный пример заголовок-тему. Слоты каркаса называются «Что сделано» и «Результаты». Строки «заголовок по содержанию, а не по роли» из учебного каркаса в каркасе по материалу нет.
7. **Одна ошибка сверх семи:** выдуманные причинно-следственные связи вида «— это поможет вернуть клиентов». Их напрямую требует формат пункта «Утверждение — объяснение или следствие» из `volume.yaml`.

| Параметр | Значение | Откуда |
|---|---|---|

## 2. Как собирается запрос

Одна генерация = **один** вызов `chat.completions` (`llm.generate_presentation_structure`): `gpt-4o` через proxyapi.ru, `temperature=0.7`, `response_format=json_object`, `max_tokens=8000`. Если потом находятся пустые слайды — отдельные маленькие вызовы-дозаполнения (`patch_slide.yaml`, в них материал обрезан до 3000 символов).

**Системный промпт** = `system.txt` с подстановками:
- `{volume_instruction}` ← `volume.yaml[medium]`;
- `{structure_block}` ← `doklad/layout_catalog.txt` + `doklad/narrative_text.txt` (для DOKLAD и `source_type ≠ topic`);
- `{schema}` ← `json_schema.txt`;
- `{current_date}` ← дата в виде `Q3 2026 (26 сентябре)`;
- блоки конкурентов и рынка для доклада пустые.

**Пользовательский промпт** = `user.txt` с подстановками:
- `$source_material_block` ← `source_material.txt` + текст из `content_extractor.extract_from_document` (обрезка до 15 000 символов);
- `$type_context` ← `doklad/type_contexts.yaml[material]`;
- `$audience_context` ← `audience_contexts.yaml`.

Системный промпт у двух входов **идентичен байт в байт**: он зависит только от языка, даты, объёма и ветки DOKLAD. Пользовательские промпты различаются темой и материалом.

Тексты ниже собраны тем же кодом, что в проде: функции `llm._pick_structure_block`, `llm._build_user_prompt` и `SYSTEM_PROMPT.format(...)` вызваны с параметрами из 1.2. Системный промпт — 8 373 символа, пользовательский для входа 1 — 2 808.

**Как воспроизвести** (из корня репозитория, зависимости из `requirements.txt`; ключи нужны только для импорта `config`, в сеть запрос не уходит):

```python
import asyncio, os, sys
from datetime import datetime
sys.path.insert(0, "src")
os.environ.setdefault("TELEGRAM_BOT_TOKEN", "x"); os.environ.setdefault("OPENAI_API_KEY", "x")
from generation import llm
from generation.content_extractor import extract_from_document
from schemas.presentation import UserRequest, ContentVolume

DOCX = "application/vnd.openxmlformats-officedocument.wordprocessingml.document"
raw = asyncio.run(extract_from_document(open("tests/fixtures/test_prodazhi_Q3.docx", "rb").read(), DOCX))
req = UserRequest.model_validate(dict(
    topic="Итоги продаж за квартал", presentation_type="doklad", audience="general", language="ru",
    source_type="document", content_volume="medium", raw_text=raw))
now = datetime(2026, 9, 26)
months = ["январе","феврале","марте","апреле","мае","июне","июле","августе","сентябре","октябре","ноябре","декабре"]
block = llm._pick_structure_block(req)
system = llm.SYSTEM_PROMPT.format(
    schema=llm._get_json_schema(), language=req.language,
    current_date=f"Q{(now.month-1)//3+1} {now.year} ({now.day} {months[now.month-1]})",
    volume_instruction=llm.VOLUME_INSTRUCTIONS[ContentVolume.MEDIUM], structure_block=block,
    competition_table_block=llm._competition_table_block(block), market_slide_block=llm._market_slide_block(block))
user = llm._build_user_prompt(req)
```

Формула даты скопирована из `generate_presentation_structure`: там дата берётся из `datetime.now()`, поэтому её пришлось повторить с фиксированным значением.

## 4. Как таблицы попадают в текст

### 4.1 docx (вход 1) — `content_extractor._extract_docx` → `_docx_table_to_text`

Абзацы и таблицы идут в порядке документа. Таблица превращается в строку-маркер `[Таблица N]` и строки «ячейка | ячейка». Фрагмент того, что получает модель (без изменений):

```text
1. Общая динамика
Квартал закрыт с ростом выручки к прошлому году. Основной вклад дал сентябрь: после возвращения студентов и открытия новой точки трафик заметно вырос. Средний чек вырос медленнее выручки, то есть рост обеспечен прежде всего числом гостей, а не ценой.
Таблица 1. Помесячные показатели
[Таблица 1]
Месяц | Выручка, млн руб. | Чеков, шт. | Средний чек, руб.
Июль | 14,2 | 41 380 | 343
Август | 15,1 | 43 050 | 351
Сентябрь | 18,0 | 49 720 | 362
Итого за квартал | 47,3 | 134 150 | 353
2. Каналы продаж
Доставка остаётся самым быстрорастущим каналом. Предзаказ через приложение запущен в июле и уже обогнал корпоративные заказы. Продажи в зале по-прежнему дают основную часть выручки.
Таблица 2. Выручка по каналам за квартал
[Таблица 2]
Канал | Выручка, млн руб. | Доля, % | Рост к III кв. 2025, %
Продажи в зале | 30,7 | 65 | +8
Доставка | 8,5 | 18 | +41
Предзаказ в приложении | 4,7 | 10 | новый канал
Корпоративные заказы | 3,4 | 7 | −6
```

Что с этим не так:
1. **У ячеек нет адреса.** Сказать «число 8 — это строка „Продажи в зале“, колонка „Рост к III кв. 2025“» модель может только по положению в строке. Сослаться на ячейку (`source_ref` из ТЗ 4.3.1) нельзя, проверить подпись к числу — тоже.
2. **Заголовок колонки указан один раз, над таблицей.** В строке `Корпоративные заказы | 3,4 | 7 | −6` не сказано, что `−6` — процент роста к прошлому году. Модели нужно самой сопоставить позиции.
3. **Названия таблиц задвоены.** Абзац-подпись «Таблица 1. Помесячные показатели» и маркер `[Таблица 1]` идут подряд, а маркер номера не несёт названия. Если подписи в документе нет, таблица остаётся безымянной.
4. **В таблицах нет «пустых мест».** В таблице 1 у строки «Итого за квартал» нет колонки роста к прошлому году, в таблице 2 нет строки «Итого». То есть процента роста общей выручки в документе нет вовсе. Промпт этого не сообщает, а блок «ДАННЫЕ И ЦИФРЫ» велит такие пропуски заполнять (см. ошибку 1).
5. **Числа — строки в локальном формате** (`41 380`, `14,2`, `−6` с типографским минусом). Для LLM это не проблема, но детерминированная проверка чисел (ТЗ 3.3.3) должна их нормализовать.

### 4.2 PDF (вход 2) — `content_extractor._extract_pdf`

Для PDF используется только `page.extract_text()`: таблицы как структура не извлекаются вообще (`extract_tables` не вызывается). Исходника хакатона нет, поэтому поведение показано на двух примерах тем же кодом.

**Пример А — таблица 2 из отчёта, напечатанная в PDF** (Chromium, обычная HTML-таблица с рамками):

```text
Доставка остаётся самым быстрорастущим каналом. Предзаказ через приложение запущен в июле и уже обогнал корпоративные заказы.
Таблица 2. Выручка по каналам за квартал
Канал Выручка, млн руб. Доля, % Рост к III кв. 2025, %
Продажи в зале 30,7 65 +8
Доставка 8,5 18 +41
Предзаказ в приложении 4,7 10 новый канал
Корпоративные заказы 3,4 7 −6
```

Разделителей колонок нет. Где кончается «Предзаказ в приложении» и начинается «4,7», модель угадывает по смыслу. В шапке `Канал Выручка, млн руб. Доля, % Рост к III кв. 2025, %` границы колонок не восстанавливаются. Если в ячейке перенос строки, её текст разрывается между строками таблицы.

**Пример Б — вёрстка в две колонки** (страница 4 выходной колонки продаж, прогнанная через тот же экстрактор):

```text
 Выручка  Доставка
Выручка за III квартал составила 47,3 млн руб., что на 8% Доставка показала рост на 41%, став вторым по значимости
больше, чем в прошлом году. каналом продаж.
 Города  Программа лояльности
Санкт-Петербург лидирует по выручке на одну точку, выполнив Запуск программы лояльности в IV квартале для удержания
план на 112%. клиентов.
Fibonacci. 4 / 9
```

Строки левой и правой колонок склеиваются построчно: «…что на 8% Доставка показала рост на 41%, став вторым по значимости / больше, чем в прошлом году. каналом продаж.» ТЗ и требования к хакатонам часто свёрстаны таблицами «критерий — баллы» или «этап — срок». В плоском тексте связь «значение ↔ подпись» теряется, и вероятность приписать число не к той подписи растёт.

## 5. Семь ошибок: откуда каждая

Обозначения причин: **[П]** — строка промпта, **[С]** — поле или ограничение схемы, **[В]** — формат входа, **[Н]** — модель нарушила явную инструкцию. Ссылки: `файл:строка` в `prompts/`, `S:N` — строка собранного системного промпта из 3.1.

### Ошибка 1. «47,3 млн, на 8% больше прошлого года»

**В колоде:** продажи, слайд 4, карточка «Выручка»: «Выручка за III квартал составила 47,3 млн руб., что на 8% больше, чем в прошлом году».
**В источнике:** 47,3 — таблица 1, строка «Итого за квартал». +8 — таблица 2, строка «Продажи в зале», колонка «Рост к III кв. 2025, %». Процента роста общей выручки в документе **нет**, есть только фраза «Квартал закрыт с ростом выручки к прошлому году».

| # | Причина | Цитата |
|---|---|---|
| 1 | **[П]** Системный промпт велит заполнять отсутствующие числа | `system.txt:20` / `S:44` «Используй реальные данные из своих знаний: рынки, статистику, исследования.»<br>`system.txt:23` / `S:47` «НЕ пиши [ЦИФРА] — лучше реалистичный диапазон "$5-15B".» |
| 2 | **[П]** Формат пункта требует конкретику и следствие | `volume.yaml:30–31` / `S:19–20` «одно законченное предложение формата "Утверждение — объяснение или следствие"»<br>`layout_catalog.txt:5` / `S:53` «text — одно информационное предложение с конкретикой: механизмом, следствием, названием или числом» |
| 3 | **[В]** Число не привязано к строке и колонке, пропуск не помечен | см. 4.1, п. 1, 2, 4 |
| 4 | **[Н]**, но слабая инструкция | `source_material.txt:1` «НЕ выдумывай данные и цифры сверх этого текста». Число 8 в тексте есть — с точки зрения этой формулировки модель ничего не выдумала. Инструкция запрещает новые числа, но не запрещает переносить число к чужой подписи. |

**Вывод:** основная причина — формат входа и формулировка запрета. Её же не поймает проверка «число есть в источнике» из ТЗ 3.3.3 — нужна проверка «число + к чему относится».

**В колоде:**

## 7. Предлагаемые правки промпта (было → стало)

> **Не применены.** Ждут ревью техлида. Все правки — только текст в `prompts/`, код не трогают. Каждую нужно прогнать на двух фикстурах (раздел 8) до и после. Для питч-дека поведение не меняется: материал бывает только у доклада, а правки 1 и 2 срабатывают только при наличии блока МАТЕРИАЛ.
>
> **Оговорка про примеры.** Для наглядности примеры «плохо / хорошо» в П3–П8 взяты из кейса G-01 (кофейни). По принципу ТЗ 4.8.5 в промпт так ставить нельзя: прогон G-01 будет мерить запоминание примера. Перед применением примеры нужно заменить аналогами из другой области — например, отчётом школы или склада с той же структурой ошибки.

### П1. `system.txt:19–23` — числа только из материала → ошибки 1, 4

Было:
```text
ДАННЫЕ И ЦИФРЫ:
- Используй реальные данные из своих знаний: рынки, статистику, исследования.
- Источник указывай в поле trend или source: "Grand View Research, 2024".
- Если точных данных нет — используй данные смежной отрасли с пометкой "оценочно".
- НЕ пиши [ЦИФРА] — лучше реалистичный диапазон "$5-15B".
```
Стало:
```text
ДАННЫЕ И ЦИФРЫ:
- Если в запросе есть блок МАТЕРИАЛ — числа, даты, названия и имена бери ТОЛЬКО из него. Своих знаний не добавляй, диапазонов и оценок не придумывай. Нужного числа в материале нет — пиши утверждение без числа или выбери layout без чисел.
- Если блока МАТЕРИАЛ нет: используй реальные данные из своих знаний (рынки, статистику, исследования), источник указывай в поле trend или source: "Grand View Research, 2024". Если точных данных нет — используй данные смежной отрасли с пометкой "оценочно". НЕ пиши [ЦИФРА] — лучше реалистичный диапазон "$5-15B".
```
Риск: низкий. Вторая часть — прежний текст дословно, питч-деку ничего не меняется. Чище сделать это в коде — подставлять блок по `source_type` — но это правка кода, см. 7.2.

## 8. Как проверять правки

1. Прогнать оба входа 3 раза до и 3 раза после (при `temperature=0.7` одного прогона мало), сохранить JSON колод.
2. Сверить с критериями golden-кейсов из ТЗ 7.4 (кейсы G-01, G-02): обязательные числа с подписями, запрещённые утверждения, отсутствие дат.
3. Отдельно проверить питч-дек по теме (любая тема, 2 прогона): рынок и роадмап должны остаться как были.
4. Итог записать в `tests/golden/reports/<дата>.md` (ТЗ 7.4, 4.8).

Пока исходника хакатона нет, кейс G-02 проверяется только по выходу (есть ли «95%», «сделано», «результаты»).
