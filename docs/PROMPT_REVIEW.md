# Разбор промптов текущего движка на двух входах

**Дата:** 26.09.2026 · **Версия промптов:** `prompts/VERSION` = `2026-09-26` (коммит `05a7af4`, после мёржа PR #71)
**Статус:** диагностика. Промпты **не менялись**. Правки из раздела 7 — предложение на ревью техлиду.
**Дополнено 26.09.2026 (вторая сессия):** исходник ТЗ хакатона — реальный текст в 3.3 и 4.2; JSON трёх колод из `presentations.spec` — `tests/fixtures/specs/`; проверка гипотезы о слайде без заголовка — раздел 9; что ещё видно в JSON — раздел 10.

Поводом стали две колоды, которые бот собрал 26.09.2026 из отчёта о продажах кофеен и из ТЗ хакатона VK. Владелец продукта нашёл в них 7 ошибок. Гипотеза техлида: причины в основном не в модели, а в промпте, схеме и формате входных данных. Этот документ её проверяет.

## 0. Коротко

1. **Гипотеза подтверждается.** Каждую из 7 ошибок промпт и схема прямо требуют или разрешают. Чистых нарушений моделью явных инструкций два: «95%» в колоде хакатона и пропущенный слот «Сложности». Но и в этих случаях соседние инструкции толкают модель к нарушению.
2. **Главный источник выдумки — блок «ДАННЫЕ И ЦИФРЫ» в системном промпте.** Он велит брать числа «из своих знаний» и писать «реалистичный диапазон» вместо пропуска. Блок действует и в режиме «по документу», где противоречит запрету выдумывать из `source_material.txt`. Системный промпт при этом весомее пользовательского.
3. **Каркас доклада по материалу — «что сделано → результаты» из 9 слайдов, для любого документа.** ТЗ хакатона поэтому превращается в отчёт о сделанном. Короткий отчёт растягивается на 7 смысловых слотов, отсюда повторы. Один и тот же каркас даёт одинаковую последовательность макетов.
4. **Требования к числу элементов жёсткие и расходятся между файлами:** metrics — 3, timeline — 4 этапа, у каждого дата, bullets — 4 пункта. Модель подгоняет материал под числа: 4 канала обрезает до 3, к 3 приоритетам добавляет четвёртый, 3 метрики добирает выдуманным «95%».
5. **Таблицы приходят плоскими строками без адресов ячеек.** В промпте нет понятия «к какой строке и колонке относится число». «+8» из строки «Продажи в зале» поэтому приклеилось к общей выручке. Проверка «число есть в источнике» (ТЗ 3.3.3) такую ошибку **не поймает**: «8» в источнике есть. Нужна проверка пары «число + подпись» через ссылку на ячейку. Это вошло в новые принципы ТЗ 4.8.
6. **Заголовки-темы задаёт сам промпт.** Правило 5 каталога приводит как верный пример заголовок-тему. Слоты каркаса называются «Что сделано» и «Результаты». Строки «заголовок по содержанию, а не по роли» из учебного каркаса в каркасе по материалу нет.
7. **Одна ошибка сверх семи:** выдуманные причинно-следственные связи вида «— это поможет вернуть клиентов». Их напрямую требует формат пункта «Утверждение — объяснение или следствие» из `volume.yaml`.
8. **Слайд `bullets` без заголовка** (есть во всех трёх колодах из `specs/`) — продукт ветки дозаполнения пустого слайда, но заголовок **не теряется** при деградации: его не было уже в основном ответе модели, а дозаполнение его не восстанавливает. Дозапрос не видит остальных слайдов — отсюда на этом слайде повторы и противоречие «+30% / 20%» в колоде по теме. Подробно — раздел 9.

### 1.2 Параметры запроса

Бот не пишет параметры запроса ни в PDF, ни в `presentations.spec` (там только результат генерации). Поэтому параметры восстановлены по коду бота и по колодам:

| Параметр | Значение | Откуда |
|---|---|---|
| `presentation_type` | `doklad` | шаблон колод — `templates/doklad` (надпись «ГЛАВНАЯ МЫСЛЬ», финал «Готов ответить на вопросы»); материал бот принимает только в докладе (`main.py`, `ONBOARDING_QUESTIONS[DOKLAD]`) |
| `source_type` | `document` | прислан файл |

| `audience` | `general` | **допущение**: в колоде аудитория не видна. От неё зависит одна строка «Контекст по аудитории», остальной текст не меняется |

| Дата | 26.09.2026 | `CreationDate` обоих PDF |

## 2. Как собирается запрос

Одна генерация = **один** вызов `chat.completions` (`llm.generate_presentation_structure`): `gpt-4o` через proxyapi.ru, `temperature=0.7`, `response_format=json_object`, `max_tokens=8000`. Если потом находятся пустые слайды — отдельные маленькие вызовы-дозаполнения (`patch_slide.yaml`, в них материал обрезан до 3000 символов).

**Системный промпт** = `system.txt` с подстановками:
- `{volume_instruction}` ← `volume.yaml[medium]`;
- `{structure_block}` ← `doklad/layout_catalog.txt` + `doklad/narrative_text.txt` (для DOKLAD и `source_type ≠ topic`);
- `{schema}` ← `json_schema.txt`;
- `{current_date}` ← дата в виде `Q3 2026 (26 сентябре)`;
- блоки конкурентов и рынка для доклада пустые.

**Пользовательский промпт** = `user.txt` с подстановками:
- `$source_material_block` ← `source_material.txt` + текст из `content_extractor.extract_from_document` (обрезка до 15 000 символов);
- `$type_context` ← `doklad/type_contexts.yaml[material]`;
- `$audience_context` ← `audience_contexts.yaml`.

Системный промпт у двух входов **идентичен байт в байт**: он зависит только от языка, даты, объёма и ветки DOKLAD. Пользовательские промпты различаются темой и материалом.

Тексты ниже собраны тем же кодом, что в проде: функции `llm._pick_structure_block`, `llm._build_user_prompt` и `SYSTEM_PROMPT.format(...)` вызваны с параметрами из 1.2. Системный промпт — 8 373 символа, пользовательский для входа 1 — 2 808.

**Как воспроизвести** (из корня репозитория, зависимости из `requirements.txt`; ключи нужны только для импорта `config`, в сеть запрос не уходит):

```python
import asyncio, os, sys
from datetime import datetime
sys.path.insert(0, "src")
os.environ.setdefault("TELEGRAM_BOT_TOKEN", "x"); os.environ.setdefault("OPENAI_API_KEY", "x")
from generation import llm
from generation.content_extractor import extract_from_document
from schemas.presentation import UserRequest, ContentVolume

DOCX = "application/vnd.openxmlformats-officedocument.wordprocessingml.document"
raw = asyncio.run(extract_from_document(open("tests/fixtures/test_prodazhi_Q3.docx", "rb").read(), DOCX))
req = UserRequest.model_validate(dict(
    topic="Итоги продаж за квартал", presentation_type="doklad", audience="general", language="ru",
    source_type="document", content_volume="medium", raw_text=raw))
now = datetime(2026, 9, 26)
months = ["январе","феврале","марте","апреле","мае","июне","июле","августе","сентябре","октябре","ноябре","декабре"]
block = llm._pick_structure_block(req)
system = llm.SYSTEM_PROMPT.format(
    schema=llm._get_json_schema(), language=req.language,
    current_date=f"Q{(now.month-1)//3+1} {now.year} ({now.day} {months[now.month-1]})",
    volume_instruction=llm.VOLUME_INSTRUCTIONS[ContentVolume.MEDIUM], structure_block=block,
    competition_table_block=llm._competition_table_block(block), market_slide_block=llm._market_slide_block(block))
user = llm._build_user_prompt(req)
```

Формула даты скопирована из `generate_presentation_structure`: там дата берётся из `datetime.now()`, поэтому её пришлось повторить с фиксированным значением.

- **Процентов в тексте нет ни одного** (символ `%` не встречается). «95%» в колоде из `bot_output_hackathon_vk.pdf` и «90%» в `specs/hakaton.json` — выдумка, причём от прогона к прогону разная (см. 10.4).
- **«5 минут» — ограничение** из блока «Рамки решения»: «Время генерации одной колоды — не более 5 минут». Рядом — «Целевой объем 10-15 слайдов» и «Решение не должно быть заточено под три предоставленных шаблона».

## 4. Как таблицы попадают в текст

### 4.1 docx (вход 1) — `content_extractor._extract_docx` → `_docx_table_to_text`

Абзацы и таблицы идут в порядке документа. Таблица превращается в строку-маркер `[Таблица N]` и строки «ячейка | ячейка». Фрагмент того, что получает модель (без изменений):

```text
1. Общая динамика
Квартал закрыт с ростом выручки к прошлому году. Основной вклад дал сентябрь: после возвращения студентов и открытия новой точки трафик заметно вырос. Средний чек вырос медленнее выручки, то есть рост обеспечен прежде всего числом гостей, а не ценой.
Таблица 1. Помесячные показатели
[Таблица 1]
Месяц | Выручка, млн руб. | Чеков, шт. | Средний чек, руб.
Июль | 14,2 | 41 380 | 343
Август | 15,1 | 43 050 | 351
Сентябрь | 18,0 | 49 720 | 362
Итого за квартал | 47,3 | 134 150 | 353
2. Каналы продаж
Доставка остаётся самым быстрорастущим каналом. Предзаказ через приложение запущен в июле и уже обогнал корпоративные заказы. Продажи в зале по-прежнему дают основную часть выручки.
Таблица 2. Выручка по каналам за квартал
[Таблица 2]
Канал | Выручка, млн руб. | Доля, % | Рост к III кв. 2025, %
Продажи в зале | 30,7 | 65 | +8
Доставка | 8,5 | 18 | +41
Предзаказ в приложении | 4,7 | 10 | новый канал
Корпоративные заказы | 3,4 | 7 | −6
```

Что с этим не так:
1. **У ячеек нет адреса.** Сказать «число 8 — это строка „Продажи в зале“, колонка „Рост к III кв. 2025“» модель может только по положению в строке. Сослаться на ячейку (`source_ref` из ТЗ 4.3.1) нельзя, проверить подпись к числу — тоже.
2. **Заголовок колонки указан один раз, над таблицей.** В строке `Корпоративные заказы | 3,4 | 7 | −6` не сказано, что `−6` — процент роста к прошлому году. Модели нужно самой сопоставить позиции.
3. **Названия таблиц задвоены.** Абзац-подпись «Таблица 1. Помесячные показатели» и маркер `[Таблица 1]` идут подряд, а маркер номера не несёт названия. Если подписи в документе нет, таблица остаётся безымянной.
4. **В таблицах нет «пустых мест».** В таблице 1 у строки «Итого за квартал» нет колонки роста к прошлому году, в таблице 2 нет строки «Итого». То есть процента роста общей выручки в документе нет вовсе. Промпт этого не сообщает, а блок «ДАННЫЕ И ЦИФРЫ» велит такие пропуски заполнять (см. ошибку 1).
5. **Числа — строки в локальном формате** (`41 380`, `14,2`, `−6` с типографским минусом). Для LLM это не проблема, но детерминированная проверка чисел (ТЗ 3.3.3) должна их нормализовать.

### 4.2 PDF (вход 2) — `content_extractor._extract_pdf`

Для PDF используется только `page.extract_text()`: таблицы как структура не извлекаются вообще (`extract_tables` не вызывается).

**Реальный вход — `test_hakaton_Q3.pdf`.** Таблиц в документе нет: `pdfplumber.extract_tables()` на всех 7 страницах возвращает пустой список. Все числа ТЗ стоят в сплошном тексте и списках, поэтому ошибка «число приклеилось к чужой строке таблицы», как в отчёте о продажах, здесь невозможна. Потери при извлечении другие:

1. **Номер страницы попадает в текст отдельной строкой и может разорвать предложение.** Титульная страница без номера, у страниц 2–7 внизу номера 1–6. На стыке страниц 2 и 3 номер «1» оказался посреди пункта 5:
   ```text
   5. Представление результата генерации в трех вариантах верстки для одного и того же
   шаблона и контента. Ось различий команда определяет сама (например: выбор макетов,
   1

   плотность контента, порядок и группировка слайдов, способ визуализации данных) и
   обосновывает свой выбор в документации.
   ```
   Для модели это лишнее число «1» без подписи, для будущей проверки чисел (ТЗ 7.1) — ложное совпадение.
2. **Иерархия разделов потеряна.** Заголовки разделов и пункты списков выглядят одинаково — «число, точка, текст». Нумерация начинается заново семь раз: разделы (1–9), бизнес-задачи (1–3), функциональность (1–7, плюс «3.1 Задача со звездочкой»), структура питча (1–6), критерии оценки (1–5), вопросы аудита (1–11). Строку `3. Программно-аппаратные требования:` от `3. Генерация слайдов по предзагруженному шаблону…` модель отличает только по смыслу.
3. **Переносы строк — по вёрстке, а не по смыслу.** Строки рвутся каждые ~90 символов, слова с дефисом на границе строки остаются разорванными: `контент-` / `пакет`, `дизайн-` / `системы`.
4. **Статус утверждения не размечен.** «Рамки решения» (ограничения), «В рамках задания необходимо» (требования), «Критерии оценки» и «Приложение 1» (пороги проверки) в тексте ничем не отличаются от описательных абзацев. Жанр `requirements` и статус `constraint` модель должна выводить сама — и в обеих колодах не вывела (ошибка 4).

Для этого входа формат извлечения — не главная причина ошибок: всё нужное в тексте есть и прочитывается однозначно. Ошибки 2 и 4 по хакатону вызваны промптом (раздел 5). Но пункты 1 и 2 надо учесть в ingest нового движка: убирать колонтитулы и номера страниц, сохранять уровни заголовков.

Примеры ниже — как выглядит в тексте **PDF с таблицами** (их нет в ТЗ хакатона, но будут в других входах golden-корпуса). Сделаны тем же кодом.

**Пример А — таблица 2 из отчёта, напечатанная в PDF** (Chromium, обычная HTML-таблица с рамками):

```text
Доставка остаётся самым быстрорастущим каналом. Предзаказ через приложение запущен в июле и уже обогнал корпоративные заказы.
Таблица 2. Выручка по каналам за квартал
Канал Выручка, млн руб. Доля, % Рост к III кв. 2025, %
Продажи в зале 30,7 65 +8
Доставка 8,5 18 +41
Предзаказ в приложении 4,7 10 новый канал
Корпоративные заказы 3,4 7 −6
```

Разделителей колонок нет. Где кончается «Предзаказ в приложении» и начинается «4,7», модель угадывает по смыслу. В шапке `Канал Выручка, млн руб. Доля, % Рост к III кв. 2025, %` границы колонок не восстанавливаются. Если в ячейке перенос строки, её текст разрывается между строками таблицы.

**Пример Б — вёрстка в две колонки** (страница 4 выходной колонки продаж, прогнанная через тот же экстрактор):

```text
 Выручка  Доставка
Выручка за III квартал составила 47,3 млн руб., что на 8% Доставка показала рост на 41%, став вторым по значимости
больше, чем в прошлом году. каналом продаж.
 Города  Программа лояльности
Санкт-Петербург лидирует по выручке на одну точку, выполнив Запуск программы лояльности в IV квартале для удержания
план на 112%. клиентов.
Fibonacci. 4 / 9
```

Строки левой и правой колонок склеиваются построчно: «…что на 8% Доставка показала рост на 41%, став вторым по значимости / больше, чем в прошлом году. каналом продаж.» Положения о конкурсах и ТЗ часто свёрстаны таблицами «критерий — баллы» или «этап — срок». В плоском тексте связь «значение ↔ подпись» теряется, и вероятность приписать число не к той подписи растёт.

## 5. Семь ошибок: откуда каждая

Обозначения причин: **[П]** — строка промпта, **[С]** — поле или ограничение схемы, **[В]** — формат входа, **[Н]** — модель нарушила явную инструкцию. Ссылки: `файл:строка` в `prompts/`, `S:N` — строка собранного системного промпта из 3.1.

### Ошибка 1. «47,3 млн, на 8% больше прошлого года»

**В колоде:** продажи, слайд 4, карточка «Выручка»: «Выручка за III квартал составила 47,3 млн руб., что на 8% больше, чем в прошлом году».
**В источнике:** 47,3 — таблица 1, строка «Итого за квартал». +8 — таблица 2, строка «Продажи в зале», колонка «Рост к III кв. 2025, %». Процента роста общей выручки в документе **нет**, есть только фраза «Квартал закрыт с ростом выручки к прошлому году».

| # | Причина | Цитата |
|---|---|---|
| 1 | **[П]** Системный промпт велит заполнять отсутствующие числа | `system.txt:20` / `S:44` «Используй реальные данные из своих знаний: рынки, статистику, исследования.»<br>`system.txt:23` / `S:47` «НЕ пиши [ЦИФРА] — лучше реалистичный диапазон "$5-15B".» |
| 2 | **[П]** Формат пункта требует конкретику и следствие | `volume.yaml:30–31` / `S:19–20` «одно законченное предложение формата "Утверждение — объяснение или следствие"»<br>`layout_catalog.txt:5` / `S:53` «text — одно информационное предложение с конкретикой: механизмом, следствием, названием или числом» |
| 3 | **[В]** Число не привязано к строке и колонке, пропуск не помечен | см. 4.1, п. 1, 2, 4 |
| 4 | **[Н]**, но слабая инструкция | `source_material.txt:1` «НЕ выдумывай данные и цифры сверх этого текста». Число 8 в тексте есть — с точки зрения этой формулировки модель ничего не выдумала. Инструкция запрещает новые числа, но не запрещает переносить число к чужой подписи. |

**Вывод:** основная причина — формат входа и формулировка запрета. Её же не поймает проверка «число есть в источнике» из ТЗ 3.3.3 — нужна проверка «число + к чему относится».

### Ошибка 2. Выдуманные даты в таймлайне

**В колоде:**
- продажи, слайд 7 «Планы на IV квартал» — «ОКТЯБРЬ 2026 / НОЯБРЬ 2026 / ДЕКАБРЬ 2026 / КОНЕЦ ДЕКАБРЯ 2026», причём 4-й этап «Анализ результатов» выдуман целиком;
- хакатон, слайд 7 «Следующие шаги» — «Q4 2026 / Q1 2027 / Q2 2027 / Q3 2027».

**В источнике:** в отчёте — только «IV квартал» и **три** приоритета. В ТЗ хакатона дат нет (сверено с исходником, см. 3.3), есть только условие организатора «при полном выполнении ТЗ — готовы проводить пилотное тестирование». Из него и выросли «следующие шаги» колоды: тестирование → обратная связь → запуск, с датами от Q4 2026 до Q3 2027.

| # | Причина | Цитата |
|---|---|---|
| 1 | **[П]** Системный промпт даёт якорь и велит раскладывать этапы по будущим датам — для всех типов, включая доклад по материалу | `system.txt:15` / `S:15` «ТЕКУЩАЯ ДАТА: Q3 2026 (26 сентябре). Используй её как отправную точку для роадмапа. Все этапы роадмапа — в будущем от этой даты» |
| 2 | **[П]** Каталог требует дату у каждого этапа и ровно 4 этапа | `layout_catalog.txt:34` / `S:82` «timeline — этапы во времени. 4 этапа, у каждого date (период)» |
| 3 | **[П]** Объём требует 4 этапа | `volume.yaml:46` / `S:35` «timeline — 4 этапа.» → 3 приоритета превращаются в 4 этапа |
| 4 | **[С]** Дата обязательна | `json_schema.txt:16` / `S:152` `"timeline_items": [{"date": "string", …}]`; `schemas/presentation.py:107` `date: str = Field(...)` — без даты этап не пройдёт валидацию |
| 5 | **[П]** Контекст типа требует «следующие шаги» | `doklad/type_contexts.yaml:5` «Структура отчётная: что сделано → результаты → сложности → следующие шаги.» В каталоге доклада нет макета для шагов без дат, кроме `diagram` с Mermaid, поэтому «следующие шаги» почти всегда уходят в `timeline` |

**Вывод:** промпт и схема требуют дат. Запрета выдумывать даты при этом нет: `narrative_text.txt:17` запрещает выдумывать «данные, цифры и события», но не даты.

### Ошибка 3. Из 4 каналов показаны 3, пропал единственный с падением (−6%)

**В колоде:** продажи, слайд 3 «Каналы продаж» — три кольца 65% / 18% / 10%. Корпоративные заказы (7%, −6%) пропали. Рост доставки +41% тоже потерян: вместо числа — «Самый быстрорастущий канал». Кроме того, в колоде нет Мурманска (87% плана, единственный город ниже плана): отрицательные факты выпали оба.

| # | Причина | Цитата |

### Ошибка 4. ТЗ хакатона: требования превращены в «результаты»

**В колоде:** хакатон, слайд 3 «Что сделано» («Проведен парсинг шаблонов», «Разработаны три варианта верстки», «Создана функциональность для аудита») и слайд 4 «Результаты / Измеримые показатели успеха»: `95%` «Качество парсинга», `3 варианта`, `5 минут` «Время генерации — Быстрая генерация презентаций».
**В источнике (сверено с `test_hakaton_Q3.pdf`, см. 3.3):** это ТЗ, то есть требования. Процентов в тексте нет вовсе. «5 минут» — ограничение («Время генерации одной колоды — не более 5 минут»), «три варианта верстки» — требование к участникам.
**В другом прогоне** (`specs/hakaton.json`) та же ошибка в той же форме: слайд «Результаты работы / Эффективность сервиса» с метриками «90% — Успешная генерация», «5 минут — Генерация колоды занимает не более 5 минут», «3 варианта — Каждый шаблон генерирует 3 варианта презентации». Выдуманное процентное значение другое, место и роль — те же.

## 7. Предлагаемые правки промпта (было → стало)

> **Не применены.** Ждут ревью техлида. Все правки — только текст в `prompts/`, код не трогают. Каждую нужно прогнать на двух фикстурах (раздел 8) до и после. Для питч-дека поведение не меняется: материал бывает только у доклада, а правки 1 и 2 срабатывают только при наличии блока МАТЕРИАЛ.
>
> **Оговорка про примеры.** Для наглядности примеры «плохо / хорошо» в П3–П8 взяты из кейса G-01 (кофейни). По принципу ТЗ 4.8.5 в промпт так ставить нельзя: прогон G-01 будет мерить запоминание примера. Перед применением примеры нужно заменить аналогами из другой области — например, отчётом школы или склада с той же структурой ошибки.

### П1. `system.txt:19–23` — числа только из материала → ошибки 1, 4

Было:
```text
ДАННЫЕ И ЦИФРЫ:
- Используй реальные данные из своих знаний: рынки, статистику, исследования.
- Источник указывай в поле trend или source: "Grand View Research, 2024".
- Если точных данных нет — используй данные смежной отрасли с пометкой "оценочно".
- НЕ пиши [ЦИФРА] — лучше реалистичный диапазон "$5-15B".
```
Стало:
```text
ДАННЫЕ И ЦИФРЫ:
- Если в запросе есть блок МАТЕРИАЛ — числа, даты, названия и имена бери ТОЛЬКО из него. Своих знаний не добавляй, диапазонов и оценок не придумывай. Нужного числа в материале нет — пиши утверждение без числа или выбери layout без чисел.
- Если блока МАТЕРИАЛ нет: используй реальные данные из своих знаний (рынки, статистику, исследования), источник указывай в поле trend или source: "Grand View Research, 2024". Если точных данных нет — используй данные смежной отрасли с пометкой "оценочно". НЕ пиши [ЦИФРА] — лучше реалистичный диапазон "$5-15B".
```
Риск: низкий. Вторая часть — прежний текст дословно, питч-деку ничего не меняется. Чище сделать это в коде — подставлять блок по `source_type` — но это правка кода, см. 7.2.

### П4. `doklad/layout_catalog.txt:9–11` — metrics без обрезки и без «процентов любой ценой» → ошибки 3, 4

## 9. Слайд `bullets` без заголовка: проверка гипотезы техлида

**Гипотеза:** слайд с `layout: bullets` и `title: null` (есть во всех трёх колодах из `tests/fixtures/specs/`) — это пустой слайд другого типа, деградировавший в bullets. Заголовок теряется при деградации.

**Итог:**
- **«Пустой слайд, дозаполненный как bullets» — подтверждается косвенно**, по четырём признакам в JSON (9.1). Исходный layout по JSON установить нельзя, нужен лог воркера (9.4).
- **«Заголовок теряется при деградации» — не подтверждается.** Код заголовок сохраняет (9.2). Заголовка не было уже в ответе основного вызова, а ветка дозаполнения его не запрашивает и не проверяет.

### 9.1 Что в JSON

| Колода | Слайд | Соседи | Заполнено | Пункты |
|---|---|---|---|---|
| `prodazhi_Q3` | 4 | 3 `metrics`, 5 `bullets` | только `bullets` | 4, у каждого `subtitle` и `icon` |
| `hakaton` | 5 | 4 `metrics`, 6 `quote` | только `bullets` | 4, у каждого `subtitle` и `icon` |
| `prodazhi_topic_only` | 4 | 3 `solution`, 5 `metrics` | только `bullets` | 4, у каждого `subtitle` и `icon` |

Признаки ветки дозаполнения:
1. **Пусто всё, кроме пунктов:** `title`, `subtitle`, `body_text`, `image_query` — `null`. У остальных 20 содержательных слайдов трёх колод `title` и `subtitle` заполнены все без исключения (`S:41`: «Для ЛЮБОГО слайда: subtitle»). Ровно такой слайд получается, если основной ответ дал пустой каркас, а дозапрос вернул только то, что просит его пример ответа, — `{"bullets": [...]}` (`prompts/patch_instructions.yaml`, ключ `bullets`).
2. **Форма — как в инструкции дозапроса:** «Заполни "bullets": 3-4 пункта. У каждого: "text"…, "subtitle"…, "icon"…». Во всех трёх случаях — 4 пункта с `subtitle` и `icon`.
3. **Содержание — пересказ всего материала, а не одна мысль.**
   - Продажи: выручка, доставка, города, программа лояльности — по пункту из каждого из 4 разделов отчёта.
   - Хакатон: парсинг шаблона, структура, визуализация, аудит — пункты «Функциональности». Все четыре взяты из первых 3 000 символов материала — ровно столько получает дозапрос (`raw_text[:3000]`). Ни одного — из «Рамок решения» (символ 3 643) и дальше.

   Дозапрос видит тему и материал, но не видит остальных слайдов. Поэтому он повторяет уже сказанное («47,3 млн» — слайды 2 и 4, «программа лояльности» — 4, 5, 7) и противоречит соседям. В колоде по теме слайд 4: «количество новых клиентов увеличилось на 30%», слайд 5: «Новые клиенты — 20%».
4. **Правила каталога.** Если бы слайд 4 продаж был bullets уже в ответе модели, она нарушила бы сразу два правила каталога: два bullets подряд (4 и 5) и bullets 4 раза. Если он стал bullets после, то в ответе модели bullets — на слайдах 2, 5, 8, и оба правила соблюдены.

**Чего по JSON установить нельзя — исходный layout.** Локальная деградация оставляет поле исходного layout как было. Но у пустого `metrics`, `timeline`, `diagram` или `image_hero` это поле и так пустое — следа не остаётся. Кроме того, слайд мог прийти пустым `bullets`. Тогда он дозаполнялся без смены типа, и «деградации из другого типа» не было.

### 9.2 Что делает код

`llm._patch_empty_slides` обрабатывает каждый слайд, у которого нет поля, нужного его layout (`_slide_has_required_content`):
1. `_locally_degrade_slide` — для `two_column`, `metrics`, `diagram`, `image_hero`, `timeline`: `slide.model_copy(update={"layout": BULLETS, "bullets": bullets})`. Меняются только `layout` и `bullets`; `title`, `subtitle` и остальные поля копируются как есть.
2. Если пунктов после этого нет — `_patch_one_slide`, дозапрос по `patch_slide.yaml`. Ответ модели вливается в слайд **только по ключам, которые есть в ответе** (`merged.update(...)`). В примере ответа для bullets ключа `title` нет.

Проверено прогоном `_patch_empty_slides` с подменённым клиентом LLM, который отвечает как в примере — только `bullets`:

| Слайд на входе | Результат | Вызовов LLM |

| `timeline`, title «Планы», этапов нет | `bullets`, title «Планы», 4 пункта | 1 |
| `two_column`, title «Сравнение», только `left_text` и `right_text` | `bullets`, title «Сравнение», 2 пункта из текстов колонок | 0 |
| `metrics` без title и subtitle, метрик нет | `bullets`, **title `null`**, subtitle `null`, 4 пункта | 1 |
| `bullets` без title и без пунктов | `bullets`, **title `null`**, subtitle `null`, 4 пункта | 1 |

Заголовок при деградации не теряется. Если его не было, он и не появляется:
- когда заголовка нет, `title_part` в промпте дозапроса пустой, и модели никто не говорит, что его нужно написать;
- в инструкции и примере ответа — только `bullets`;
- `_slide_has_required_content` для `bullets` проверяет только `bullets`. После дозаполнения слайд без заголовка считается полным, и предупреждение воркера «slide(s) … missing the specific field» не срабатывает.

Почему основной вызов вернул пустой слайд, по сохранённым данным не установить: сырой ответ модели не сохраняется, а `spec` пишется в БД уже после дозаполнения.

### 9.3 Что из этого следует

1. Заголовок — не главный дефект ветки дозаполнения. Она пишет слайд вслепую, отсюда повторы и противоречия (ошибка 5, 10.2). В режиме «по теме» у неё нет правил о числах, а инструкция для `metrics` прямо просит «правдоподобные для темы цифры» (`patch_instructions.yaml`).
2. Предлагаемые правки — **не применены**, в этом PR только диагностика:
   - код: если у слайда нет `title` или `subtitle`, дозапрос просит их вместе с телом; `_slide_has_required_content` для содержательных слайдов требует `title`;
   - код: дозапрос получает заголовки остальных слайдов («не повторяй: …») и весь материал, а не `raw_text[:3000]` (К16);
   - код: сохранять в `presentations`, какие слайды дозаполнялись и из какого layout, — рядом с `durations_ms`. Тогда такие вопросы решаются запросом к БД, без поиска по логам;
   - промпт: П11 (раздел 7), через golden-корпус.
3. В новом движке проблемы нет по построению (D-003): заголовок-вывод формируется в OUTLINE до наполнения, ретрай идёт по слайду с известным планом.

### 9.4 Как подтвердить исходный layout

В логах воркера на Railway по `deck_id` (он же `job_id`) найти строку уровня info из `llm.py`:
```text
Patched empty slide #4 (layout=bullets, originally metrics)
```
или `Locally degraded slide #4 from layout=…`. `originally bullets` — слайд пришёл пустым bullets, деградации типа не было.

`job_id` колод со слайдом без заголовка:
```sql
SELECT p.job_id, p.created_at, s->>'index' AS slide
FROM presentations p, jsonb_array_elements(p.spec->'slides') s
WHERE s->>'layout' = 'bullets' AND s->>'title' IS NULL
ORDER BY p.created_at DESC;
```

## 10. Что ещё видно в JSON трёх колод

### 10.1 Выдуманные источники в `metrics.source`
- Колода по теме: «Анализ внутренних данных компании», «Отчеты отдела маркетинга», «Финансовая отчетность компании» — к выдуманным 15%, 20% и 10%. Компании в запросе нет вовсе.
- Хакатон: «Тестирование сервиса, 2026», «Внутренние тесты, 2026» — к «90%» и «5 минут». Сервиса ещё не существует: документ — техническое задание.
- Продажи: «Отчет сети кофеен» — источник верный, но общий, без таблицы и строки.

Причина — промпт требует источник всегда: `system.txt:21` / `S:45` «Источник указывай в поле trend или source», `volume.yaml` / `S:26` «source: одно предложение — откуда цифра и как посчитана». Шаблон доклада `metrics.source` не рисует, поэтому в PDF этих источников не видно. Но они лежат в `spec` и попадут в PPTX и заметки, как только их начнут выводить. Отсюда решение в ТЗ 3.3.3: поле `source` модель не заполняет, его проставляет код.

### 10.2 Выдуманные числа и противоречие в колоде по теме
Все числа колоды `prodazhi_topic_only` выдуманы: «2 миллиона рублей», «+15%», «электроника +25%», «новых клиентов +30%», «500 человек», метрики 15%, 20%, 10%. В запросе — только тема «Итоги продаж за квартал», без компании и периода. Одно и то же число расходится на соседних слайдах: «новых клиентов +30%» (слайд 4, дозаполнение, см. 9.1) и «Новые клиенты — 20%» (слайд 5, основной вызов). Первое — следствие раздела 9, второе — блока «ДАННЫЕ И ЦИФРЫ» (К1), который в режиме «по теме» разрешает «реалистичные» числа. Новое правило режима «по теме» — ТЗ 3.3.3: числа только как оценка, со сноской, которую ставит код.

### 10.3 Layout вне каталога доклада
`problem` и `solution` стоят на слайдах 2–3 в двух колодах из трёх (`hakaton` и `prodazhi_topic_only`), причём в колоде по теме — в учебной ветке доклада. Шаблон доклада рисует их запасной веткой. К9 подтверждено.

### 10.4 Выдумка от прогона к прогону разная
У одного входа (ТЗ хакатона) в двух прогонах разные выдуманные значения — «95%» в PDF-фикстуре, «90%» в JSON — и разные заголовки слотов. Сам дефект стабилен: метрика-«результат» из требований. Это подтверждает правило ТЗ 4.8.7: каждый кейс корпуса — не меньше 3 прогонов, проверка по спискам «обязано быть» и «не должно быть», а не сравнение с одним эталонным выходом.

### 10.5 Число слайдов: бот починен, промпт — нет
С этой сессии бот спрашивает число слайдов доклада и передаёт его в `slide_count_hint`, и `user.txt` пишет «Количество слайдов: N (строго)». Но каркасы доклада в системном промпте по-прежнему требуют 9: «СТРУКТУРА … (строго 9 слайдов)», «Слайд 8 — выводы», «Слайд 9 — closing» (`doklad/narrative_text.txt:1–5`, `doklad/narrative_topic.txt:1–5`). При выборе 5, 7, 12 или 15 модель получает два противоречащих требования, а системный промпт весомее (К1, ТЗ 4.8.6). Ожидаемо, что колоды будут тянуться к 9 слайдам.

Исправление — П7 для `narrative_text.txt` и такая же правка `narrative_topic.txt`: каркас без фиксированного числа, «Предпоследний — выводы», «Последний — closing». Применять через golden-корпус (ТЗ 4.8.7).
