# Материал

**Назначение:** колода по тексту или файлу пользователя. Материал хранится только до обработки и превращается в `SourceDigest`: фрагменты текста с id и таблицы чисел с адресами ячеек. Из них модель берёт содержание, а код — числа для диаграмм.

## Как работает

1. **Приём.** Бот принимает текст сообщением (от 20 до 100 000 знаков) или файл .pdf, .docx, .pptx, .txt до 20 МБ. API — то же, через `input.text` или multipart-файл (`docs/API.md`).
2. **Временное хранение.** Байты кладутся во временное хранилище: в S3, если настроен, иначе в Redis на 1 ч. В `DeckRequest.input.material` уходит только ссылка `ref`.
3. **Воркер** забирает байты по ссылке (`get_upload`). Ссылка истекла — ошибка `UPLOAD_EXPIRED`. После обработки файл удаляется в любом случае, успешно или нет (ТЗ 6.5).
4. **INGEST** (`core.ingest.ingest`) разбирает материал в отдельном потоке с таймаутом 15 с:
   - текст и .txt (кодировку определяет chardet);
   - .docx — абзацы, заголовки, таблицы;
   - .pdf — текст и таблицы через `pdfplumber.find_tables`, до 50 страниц;
   - .pptx — текст, заметки, таблицы и данные нативных диаграмм.
5. **Таблицы и ряды чисел** превращаются в `Dataset`. Первая строка — заголовки колонок с единицей («Выручка, млн руб.»), первая колонка — подписи строк, строка «Итого» помечается и в диаграмму не входит. Ряд в тексте («январь — 310, февраль — 720…») — тоже `Dataset`.
6. **Дальше:** OUTLINE планирует по фрагментам и наборам данных (`planning.md`). В режиме «по материалу» числа на слайдах сверяются с источником (`content.md`).

По теме (без материала) `SourceDigest` содержит только тему: фрагментов и наборов данных нет.

## Где в коде

- `src/generation/uploads.py` — временное хранилище (`put_upload`, `get_upload`, `delete_upload`). Лежит в старом пакете, используется обоими движками.
- `src/core/ingest/__init__.py` — разбор по форматам, лимиты, ошибки `IngestError`.
- `src/core/ingest/tables.py` — таблицы → `Dataset`; `src/core/ingest/numbers.py` — разбор чисел («47,3» = «47.3», «1 150» = 1150, «−6» = −6).
- `src/core/ingest/render.py` — `SourceDigest` → текст для промпта.
- `src/core/models/digest.py` — модель `SourceDigest`.
- Режим материала: `DeckRequest.source_mode` — `strict` (только материал) или `extend` (можно дополнить).

## Нюансы

- **В ядро идут первые 40 000 знаков** (`core/ingest/__init__.MAX_CHARS`), хотя бот принимает до 100 000. Остаток отбрасывается, в `SourceDigest.source` ставится `truncated`, пользователь видит в подписи «Вошло начало документа: N знаков из M».
- **PDF без текстового слоя** (скан) — ошибка `SCAN_WITHOUT_TEXT`, колода не собирается. OCR нет.
- **docx и pptx — zip:** до разбора проверяются размер после распаковки и число файлов — защита от zip-бомб.
- **Коды ошибок INGEST:** `SCAN_WITHOUT_TEXT`, `BAD_FILE`, `PARSE_TIMEOUT`, `FILE_UNSUPPORTED`. Пользователь получает понятный текст по коду (`bot/delivery.error_text`), клиент API — код в статусе колоды.
- **Временное хранилище без S3 — Redis с TTL 1 ч** (`UPLOAD_TTL_SECONDS`): задача, пролежавшая в очереди дольше часа, получит `UPLOAD_EXPIRED`.
- **Весь `SourceDigest` уходит в системный промпт каждого вызова CONTENT.** На больших материалах это главная статья расхода: G-06 на ProxyAPI стоил около 4 ₽, `docs/PROGRESS.md`, сессия 5.
- **`SourceDigest` не сохраняется** после колоды: «Повторить» с тем же материалом без повторной отправки файла не сделан.

## Что не разобрано

- Разбор .pptx (заметки, данные диаграмм) сверен по описанию модуля, построчно не проверялся.
