# Fibonacci AI — контекст для Claude Code

## О проекте

Fibonacci AI — Telegram-бот, который по теме, тексту или документу пользователя генерирует готовую презентацию. Пользователь проходит короткий диалог (тип, тема, аудитория, язык, объём, материал), бот ставит задачу в очередь, фоновый воркер строит план слайдов через LLM, подбирает вид каждого слайда, пишет текст, подгоняет его под макет, рисует редактируемый PPTX, конвертирует его в PDF и отправляет оба файла обратно в чат.

Сейчас основная аудитория — студенты и преподаватели (доклады, презентации проектов и результатов); стратегически продукт движется к корпоративным пользователям. Платформа — Telegram, хостинг — Railway. С сессии 3 есть REST API (`docs/API.md`): к нему подключён второй бот владельца с **живыми пользователями**.

Ключевая продуктовая задача ближайшего этапа — уйти от одинаковых слайдов: для каждого типа контента (числа, текст, процесс, сравнение и т.д.) — пул из 4–5 вариантов представления плюс цветовые темы, а также выход в двух форматах: PDF и редактируемый PPTX с нативными таблицами и графиками. Подробности — в `docs/PRODUCT.md`, устройство кода — в `README.md`.

## Правила работы

1. **В начале каждой сессии** прочитай `README.md` (устройство кода), `docs/PROGRESS.md`, `docs/DECISIONS.md` и `docs/TZ.md`. Не начинай работу, не зная последней записи в PROGRESS.
2. **В конце каждой сессии** допиши в `docs/PROGRESS.md` запись: дата, что сделано, что не доделано, следующие шаги. Открытые вопросы к владельцу продукта веди в разделе 11 `docs/TZ.md`. Затем сделай коммит и открой pull request в `main` (см. «Правило работы с git»).
3. **Каждое архитектурное решение** записывай в `docs/DECISIONS.md`: дата, решение, почему, какие альтернативы отвергнуты.
4. **Промпты и конфиги LLM** хранятся отдельными файлами в `prompts/`, не в коде.
5. **Секреты** — только в переменных окружения. Никогда не в коде, не в коммитах, не в документации.
6. **Код — источник истины для документации** (D-080). Нашёл расхождение документа с кодом — правь документ в той же задаче. Требования (каким код должен быть) задаёт ТЗ.
7. **Документы хранят решения и объяснения, не перечисления.** Числа вариантов и тем, списки файлов, переменных и роутов не переписывай в документы — ссылайся на источник (`layouts/`, `themes/`, `.env.example`, снимок контракта) или генерируй скриптом. Не подтверждено кодом — пиши «не сделано» / «не сверялось».
8. **Документация — в той же задаче, что код.** Перенёс файл, добавил этап, роут или фичу — обнови `README.md`, файл фичи в `docs/features/` (и `docs/API.md` для API). Перед PR пройди блокеры `docs/REVIEW.md`. Проверка — `python scripts/check_docs.py`, она входит в юнит-тесты (`tests/unit/test_docs.py`): битый путь или неописанный роут ломает CI.

## Правила для живых пользователей API (действуют с сессии 3, D-059)

- **Изменения API — только обратно совместимые.** Можно: новые пути, новые необязательные поля запроса, новые поля ответа, новые коды ошибок, значения `stage`, темы. Нельзя: удалить или переименовать поле, сменить тип, сделать поле запроса обязательным, убрать значение перечисления, сменить формат ошибки или смысл кода. Несовместимое — только новой версией `/v2`, старая продолжает работать. Совместимое изменение схемы — обновить снимок (`python tests/unit/test_api_contract.py --update`) и `docs/API.md` в том же PR.
- **Миграции — только добавляющие:** новые таблицы, колонки (nullable или с default), индексы. Не удалять и не переименовывать колонки и таблицы, не менять типы — откат кода без отката БД должен оставаться безопасным. Исключение — только отдельным решением владельца.
- **В каждом PR — API-тесты зелёные:** локально `python -m unittest discover -s tests/unit -t tests/unit -p "test_api*.py"`, в CI — шаг «API-тесты (контракт второго бота)» workflow «tests». В описании PR — строка, что API-тесты прошли (или что сломалось и почему это допустимо — только с решением владельца).
- Изменения, которые меняют поведение API без смены схемы (лимиты по умолчанию, срок хранения файлов, тексты ошибок), — в «Что проверить после деплоя» и в `docs/API.md`.

## Правило работы с git (действует всегда)

- **Никогда не пушь в `main` и не мёржи PR сам.** Мёрж делает только владелец репозитория.
- **Один PR на сессию.** Все задачи сессии — в одной ветке от свежего `main` и в одном PR, а не отдельный PR на каждую задачу. Имя ветки — понятное: `docs/prompt-review`, `fix/plan-command`, `spike/pptx` и т.п. Перед созданием ветки: `git checkout main && git pull`.
- **Перед созданием PR все тесты должны проходить:** локально `pip install -r requirements.txt -r requirements-dev.txt` и `python -m unittest discover -s tests/unit -t tests/unit`, после пуша — зелёный workflow «tests» в PR (включая шаг «API-тесты»). Красный CI — не открывать PR на ревью (или сразу чинить в той же ветке).
- **После пуша создай PR в `main`** и дай ссылку на него.
- **Если в PR запускался workflow «golden»** (реальные генерации — PR меняет `prompts/` или `src/generation/`, либо ручной запуск), в описании PR — ссылка на его результат: комментарий бота с таблицей или страница запуска. Если golden пропущен (нет секрета `OPENAI_API_KEY`) — так и напиши.
- **В описании каждого PR — раздел «Что проверить после деплоя»:** 3–5 конкретных действий в боте (что нажать или прислать и что должно получиться) и что сделать в Railway, если нужно (переменные, config path, порядок деплоя сервисов). Если после деплоя проверять нечего (например, PR только с документацией), так и напиши.
- **Если задача зависит от ещё не смёрженного PR** — скажи об этом и подожди. Не делай ветку от чужой ветки.

## Где что в коде

Устройство кода, путь запроса, этапы ядра с файлами, карта репозитория, словарь терминов, запуск, служебные команды, внешние сервисы, деплой и CI — **в `README.md`**. Здесь факты о коде не дублируются, чтобы не устаревали в двух местах (D-080).
