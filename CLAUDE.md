# Fibonacci AI — контекст для Claude Code

## О проекте

Fibonacci AI — Telegram-бот, который по теме, тексту или документу пользователя генерирует готовую презентацию. Пользователь проходит короткий диалог (тип, тема, аудитория, язык, объём, материал), бот ставит задачу в очередь, фоновый воркер строит структуру слайдов через LLM, подбирает картинки, рендерит HTML-шаблон в PDF и отправляет файл обратно в чат.

Сейчас основная аудитория — студенты и преподаватели (доклады, презентации проектов и результатов); стратегически продукт движется к корпоративным пользователям. Платформа — Telegram, хостинг — Railway. С сессии 3 есть REST API (`docs/API.md`): к нему подключён второй бот владельца с **живыми пользователями**.

Ключевая продуктовая задача ближайшего этапа — уйти от одинаковых слайдов: для каждого типа контента (числа, текст, процесс, сравнение и т.д.) — пул из 4–5 вариантов представления плюс цветовые темы, а также выход в двух форматах: PDF и редактируемый PPTX с нативными таблицами и графиками. Подробности — в `docs/PRODUCT.md`, текущее техническое состояние — в `docs/CURRENT_STATE.md`.

## Правила работы

1. **В начале каждой сессии** прочитай `docs/PROGRESS.md`, `docs/DECISIONS.md` и `docs/TZ.md`. Не начинай работу, не зная последней записи в PROGRESS.
2. **В конце каждой сессии** допиши в `docs/PROGRESS.md` запись: дата, что сделано, что не доделано, следующие шаги. Открытые вопросы к владельцу продукта веди в разделе 11 `docs/TZ.md`. Затем сделай коммит и открой pull request в `main` (см. «Правило работы с git»).
3. **Каждое архитектурное решение** записывай в `docs/DECISIONS.md`: дата, решение, почему, какие альтернативы отвергнуты.
4. **Промпты и конфиги LLM** хранятся отдельными файлами в `prompts/`, не в коде.
5. **Секреты** — только в переменных окружения. Никогда не в коде, не в коммитах, не в документации.

## Правила для живых пользователей API (действуют с сессии 3, D-059)

- **Изменения API — только обратно совместимые.** Можно: новые пути, новые необязательные поля запроса, новые поля ответа, новые коды ошибок, значения `stage`, темы. Нельзя: удалить или переименовать поле, сменить тип, сделать поле запроса обязательным, убрать значение перечисления, сменить формат ошибки или смысл кода. Несовместимое — только новой версией `/v2`, старая продолжает работать. Совместимое изменение схемы — обновить снимок (`python tests/unit/test_api_contract.py --update`) и `docs/API.md` в том же PR.
- **Миграции — только добавляющие:** новые таблицы, колонки (nullable или с default), индексы. Не удалять и не переименовывать колонки и таблицы, не менять типы — откат кода без отката БД должен оставаться безопасным. Исключение — только отдельным решением владельца.
- **В каждом PR — API-тесты зелёные:** локально `python -m unittest discover -s tests/unit -t tests/unit -p "test_api*.py"`, в CI — шаг «API-тесты (контракт второго бота)» workflow «tests». В описании PR — строка, что API-тесты прошли (или что сломалось и почему это допустимо — только с решением владельца).
- Изменения, которые меняют поведение API без смены схемы (лимиты по умолчанию, срок хранения файлов, тексты ошибок), — в «Что проверить после деплоя» и в `docs/API.md`.

## Правило работы с git (действует всегда)

- **Никогда не пушь в `main` и не мёржи PR сам.** Мёрж делает только владелец репозитория.
- **Один PR на сессию.** Все задачи сессии — в одной ветке от свежего `main` и в одном PR, а не отдельный PR на каждую задачу. Имя ветки — понятное: `docs/prompt-review`, `fix/plan-command`, `spike/pptx` и т.п. Перед созданием ветки: `git checkout main && git pull`.
- **Перед созданием PR все тесты должны проходить:** локально `pip install -r requirements.txt -r requirements-dev.txt` и `python -m unittest discover -s tests/unit -t tests/unit`, после пуша — зелёный workflow «tests» в PR (включая шаг «API-тесты»). Красный CI — не открывать PR на ревью (или сразу чинить в той же ветке).
- **После пуша создай PR в `main`** и дай ссылку на него.
- **Если в PR запускался workflow «golden»** (реальные генерации — PR меняет `prompts/` или `src/generation/`, либо ручной запуск), в описании PR — ссылка на его результат: комментарий бота с таблицей или страница запуска. Если golden пропущен (нет секрета `OPENAI_API_KEY`) — так и напиши.
- **В описании каждого PR — раздел «Что проверить после деплоя»:** 3–5 конкретных действий в боте (что нажать или прислать и что должно получиться) и что сделать в Railway, если нужно (переменные, config path, порядок деплоя сервисов). Если после деплоя проверять нечего (например, PR только с документацией), так и напиши.
- **Если задача зависит от ещё не смёрженного PR** — скажи об этом и подожди. Не делай ветку от чужой ветки.

## Быстрые факты

- Код: `src/`. Бот — `src/main.py` (тексты и клавиатуры диалога со сводкой — `src/dialog.py`), воркер — `src/worker.py` (ARQ). Старый движок (HTML → PDF): генерация — `src/generation/`, схемы — `src/schemas/`, шаблоны — `src/templates/<тип>/template.html`; удаляется в сессии 6 (порядок сессий — D-054).
- Новый движок (PPTX + PDF, фаза 1): ядро — `src/core/` (`pipeline.generate_deck`), выдача в Telegram — `src/bot/delivery.py`, задача воркера — `generate_deck_job(deck_id)`, колоды — таблица `decks`. Декларативные файлы — `layouts/<kind>/<variant>.yaml` (25 вариантов), `themes/<id>.yaml` (4 темы сессии 4: `business_slate`, `ember_dark`, `sunny_cream`, `mint_coral`; старые id — поле `replaces`, D-063), `fonts/` (метрики fitter'а), `assets/icons/`; промпты — `prompts/v2/`. Оформление (градиенты, декор темы, фигуры номеров) — `src/core/render/pptx/shapes.py`; ИИ-картинки — `src/core/images/` (SiliconFlow Z-Image-Turbo, `SILICONFLOW_API_KEY`, параметры — `prompts/v2/images/`, D-067). Шаблоны-ориентиры владельца по дизайну — `docs/design/references/`. Доклад (по теме и с материалом: `src/core/ingest/`) — новый движок; питч-дек — старый до сессии 5 (`dialog.engine_for`, D-053, D-054).
- Бот, воркер и API — три сервиса Railway из одного Docker-образа. Процесс выбирает переменная сервиса `SERVICE_ROLE` — `bot` (по умолчанию), `worker`, `api` (CMD образа — `src/start.py`, D-062). Config as Code (`railway*.toml`) Railway отключает: новые сервисы его не читают, `railway.worker.toml` работает до 01.12.2026 — на файлы не полагаться. Выкатка: воркер раньше бота и API.
- REST API: `src/api/` (FastAPI; `app.py` — эндпоинты, `store.py` — `api_clients` и колоды клиента, `limits.py`, `webhook.py`, `keys.py` — CLI ключей `python -m api.keys`, `admin.py` — общая логика управления клиентами). Владелец управляет ключами командой бота `/apikey` (`src/bot/admin.py`, доступ — `ADMIN_TELEGRAM_IDS`, обработчики регистрируются первыми в `main.py`, D-061). Колоды API собирает тот же `generate_deck_job`; файлы — `core/storage/files.py` (S3 или Redis 1 ч, D-058). Снимок схемы — `tests/unit/api_contract_v1.json`. Все переменные окружения — в `.env.example`, читаются только через `src/config.py`.
- CI — GitHub Actions: `.github/workflows/tests.yml` (юнит-тесты с конвертацией через LibreOffice, отдельный шаг «API-тесты», снимок промптов относительно базы, `check_case.py` на `tests/fixtures/specs/`; job `gallery` — стресс-галерея `tests/gallery/build_gallery.py`: все варианты × 4 темы × 3 заполнения, проверки и артефакт `gallery-pdf`, по которому владелец утверждает дизайн; без ключей) и `.github/workflows/golden.yml` (реальные генерации golden-корпуса через `tests/golden/run_golden.py`: доклады — новым движком, питч — старым; плюс одна колода через REST API end-to-end — `run_api_e2e.py`, сервисы Postgres и Redis; ручной запуск со входом `outline_effort`; комментарий в PR, артефакт `golden-decks`; нужен секрет `OPENAI_API_KEY`).
- Параметры запроса и цены моделей LLM — `prompts/models.yaml` (код — `src/core/llm/models.py`; `src/generation/llm_models.py` — реэкспорт для старого движка). Модель — `OPENAI_MODEL`, уровень рассуждений — `OPENAI_REASONING_EFFORT`.
- Тесты: `python -m unittest discover -s tests/unit -t tests/unit` (стандартный unittest, LLM подменяется; для тестов API — `requirements-dev.txt`: aiosqlite, fakeredis). API end-to-end с настоящими процессами — `tests/golden/run_api_e2e.py` (шаг workflow «golden», нужны Postgres и Redis). Проверка колоды по golden-кейсу ТЗ 7.4 — `python tests/golden/check_case.py <deck.json> <G-01|G-02|G-03>`. Снимок собранных промптов до и после правки `prompts/` — `python tests/golden/prompt_snapshot.py <папка>`.
