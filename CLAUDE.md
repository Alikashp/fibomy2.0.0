# Fibonacci AI — инструкции для Claude Code

Этот файл — только для агента: как вести сессию, журнал и PR. Что за проект, как устроен код, **карта документации и правила репозитория** — в `README.md`: они общие для людей и агента и здесь не повторяются (D-082). Правило из README обязательно так же, как правило отсюда.

Кратко о проекте: Telegram-бот и REST API, которые по теме, тексту или файлу собирают презентацию — редактируемый PPTX и PDF. К REST API подключён второй бот владельца с **живыми пользователями** — поэтому правила API в README соблюдаются в каждом PR.

## Начало сессии

1. **`README.md` целиком** — карта документации, быстрый старт, правила; устройство кода — `docs/ARCHITECTURE.md`, читай по задаче.
2. **`docs/ROADMAP.md`** — что в работе и что дальше по порядку владельца. Взял пункт — перенеси в «В работе», закончил — строка в «Сделано» с PR; порядок без владельца не меняй.
3. **`docs/PROGRESS.md` — последняя запись** (и предыдущая, если её «Следующие шаги» относятся к задаче). Не начинай работу, не зная последней записи.
4. **`docs/DECISIONS.md` — индекс в начале.** Полный текст решения — поиском по номеру, когда трогаешь место, где в коде стоит ссылка `D-0xx`.
5. **`docs/TZ.md` — разделы по задаче и раздел 11** (открытые вопросы). ТЗ — главный документ: при расхождении в требованиях прав он; в фактах о коде прав код (README, «Как ведём документацию»).
6. **Перед правкой фичи — её файл в `docs/features/`.**
7. **Ветка.** Работай в ветке, которую назначила среда. Если PR этой ветки уже смёржен — пересоздай её от свежего `main` и не складывай новые коммиты поверх смёрженной истории.

Без нужды не читай исторические документы (список — README, «Карта документации») и старые записи PROGRESS: они большие и текущее устройство не описывают.

## Во время работы

- **Правила и блокеры:** README, «Правила»; таблица блокеров B1–B14 — `docs/REVIEW.md`. Пройди её по своему diff до PR.
- **Архитектурное решение** — запись в `docs/DECISIONS.md` по шаблону оттуда, затем `python scripts/decisions_index.py`.
- **Вопрос к владельцу продукта** — в `docs/TZ.md`, раздел 11, с рекомендацией; в PROGRESS — только ссылка на номер. Если без ответа можно продолжать — действуй по рекомендации и скажи об этом.
- **Чего агент не может сделать сам** — задать переменные и секреты в Railway и GitHub, проверить прод, открыть PPTX в PowerPoint или Keynote, мёржить. Такие шаги — владельцу: в «Что проверить после деплоя» и в «Следующие шаги» PROGRESS, с точными именами переменных и порядком деплоя.
- **Нет ключа или секрета** (golden без `OPENAI_API_KEY`) — не подставляй выдуманный результат: напиши, что шаг пропущен и почему.
- **Документы** — по-русски, коротко, без перечислений, которые есть в источнике. Код — источник истины; правила — README, «Как ведём документацию». Не подтверждено кодом — пиши «не сделано» / «не сверялось».

## Конец сессии

1. **Тесты:** `python -m pip install -r requirements.txt -r requirements-dev.txt` и `python -m unittest discover -s tests/unit -t tests/unit` — все зелёные, включая проверку документации (`tests/unit/test_docs.py`) и API-тесты.
2. **Запись в `docs/PROGRESS.md`** — сверху, по шаблону в конце файла: дата, что сделано, что не доделано, следующие шаги. Обнови `docs/ROADMAP.md`: «Сделано», «В работе», найденное — в «Найдено, в очередь не поставлено». Изменил устройство кода — `docs/ARCHITECTURE.md` в том же PR.
3. **Коммит, пуш, PR в `main`.** Один PR на сессию: все задачи сессии — в одной ветке и одном PR. Описание — по `docs/REVIEW.md`, «Автор перед PR». Дай пользователю ссылку на PR.
4. **CI.** Дождись workflow `tests` (и `golden`, если он запускался); красный — чини в той же ветке, а не отдавай на ревью.

## Git

- Никогда не пушь в `main` и не мёржи PR — мёржит только владелец.
- Задача зависит от ещё не смёрженного PR — скажи об этом и подожди; не делай ветку от чужой ветки.
