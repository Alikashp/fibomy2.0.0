# Fibonacci AI — контекст для Claude Code

## О проекте

Fibonacci AI — Telegram-бот, который по теме, тексту или документу пользователя генерирует готовую презентацию. Пользователь проходит короткий диалог (тип, тема, аудитория, язык, объём, материал), бот ставит задачу в очередь, фоновый воркер строит структуру слайдов через LLM, подбирает картинки, рендерит HTML-шаблон в PDF и отправляет файл обратно в чат.

Сейчас основная аудитория — студенты и преподаватели (доклады, презентации проектов и результатов); стратегически продукт движется к корпоративным пользователям. Платформа — только Telegram, хостинг — Railway. Планируется API для подключения из другого бота.

Ключевая продуктовая задача ближайшего этапа — уйти от одинаковых слайдов: для каждого типа контента (числа, текст, процесс, сравнение и т.д.) — пул из 4–5 вариантов представления плюс цветовые темы, а также выход в двух форматах: PDF и редактируемый PPTX с нативными таблицами и графиками. Подробности — в `docs/PRODUCT.md`, текущее техническое состояние — в `docs/CURRENT_STATE.md`.

## Правила работы

1. **В начале каждой сессии** прочитай `docs/PROGRESS.md`, `docs/DECISIONS.md` и `docs/TZ.md`. Не начинай работу, не зная последней записи в PROGRESS.
2. **В конце каждой сессии** допиши в `docs/PROGRESS.md` запись: дата, что сделано, что не доделано, следующие шаги. Открытые вопросы к владельцу продукта веди в разделе 11 `docs/TZ.md`. Затем сделай коммит и открой pull request в `main` (см. «Правило работы с git»).
3. **Каждое архитектурное решение** записывай в `docs/DECISIONS.md`: дата, решение, почему, какие альтернативы отвергнуты.
4. **Промпты и конфиги LLM** хранятся отдельными файлами в `prompts/`, не в коде.
5. **Секреты** — только в переменных окружения. Никогда не в коде, не в коммитах, не в документации.

## Правило работы с git (действует всегда)

- **Никогда не пушь в `main` и не мёржи PR сам.** Мёрж делает только владелец репозитория.
- **Один PR на сессию.** Все задачи сессии — в одной ветке от свежего `main` и в одном PR, а не отдельный PR на каждую задачу. Имя ветки — понятное: `docs/prompt-review`, `fix/plan-command`, `spike/pptx` и т.п. Перед созданием ветки: `git checkout main && git pull`.
- **Перед созданием PR все тесты должны проходить:** локально `python -m unittest discover -s tests/unit -t tests/unit`, после пуша — зелёный workflow «tests» в PR. Красный CI — не открывать PR на ревью (или сразу чинить в той же ветке).
- **После пуша создай PR в `main`** и дай ссылку на него.
- **Если в PR запускался workflow «golden»** (реальные генерации — PR меняет `prompts/` или `src/generation/`, либо ручной запуск), в описании PR — ссылка на его результат: комментарий бота с таблицей или страница запуска. Если golden пропущен (нет секрета `OPENAI_API_KEY`) — так и напиши.
- **В описании каждого PR — раздел «Что проверить после деплоя»:** 3–5 конкретных действий в боте (что нажать или прислать и что должно получиться) и что сделать в Railway, если нужно (переменные, config path, порядок деплоя сервисов). Если после деплоя проверять нечего (например, PR только с документацией), так и напиши.
- **Если задача зависит от ещё не смёрженного PR** — скажи об этом и подожди. Не делай ветку от чужой ветки.

## Быстрые факты

- Код: `src/`. Бот — `src/main.py` (тексты и клавиатуры диалога со сводкой — `src/dialog.py`), воркер — `src/worker.py` (ARQ). Старый движок (HTML → PDF): генерация — `src/generation/`, схемы — `src/schemas/`, шаблоны — `src/templates/<тип>/template.html`; удаляется в сессии 5.
- Новый движок (PPTX + PDF, фаза 1): ядро — `src/core/` (`pipeline.generate_deck`), выдача в Telegram — `src/bot/delivery.py`, задача воркера — `generate_deck_job(deck_id)`, колоды — таблица `decks`. Декларативные файлы — `layouts/<kind>/<variant>.yaml`, `themes/<id>.yaml`, `fonts/` (метрики fitter'а), `assets/icons/`; промпты — `prompts/v2/`. Доклад (по теме и с материалом: `src/core/ingest/`) — новый движок; питч-дек — старый до сессии 3 (`dialog.engine_for`, D-053).
- Бот и воркер — два отдельных сервиса Railway из одного Docker-образа. Бот — `railway.toml` (CMD из `Dockerfile`), воркер — `railway.worker.toml` (`sh -c "cd src && arq worker.WorkerSettings"`). Все переменные окружения — в `.env.example`, читаются только через `src/config.py`.
- CI — GitHub Actions: `.github/workflows/tests.yml` (юнит-тесты с конвертацией через LibreOffice, снимок промптов относительно базы, `check_case.py` на `tests/fixtures/specs/`; без ключей) и `.github/workflows/golden.yml` (реальные генерации golden-корпуса через `tests/golden/run_golden.py`: доклады — новым движком, питч — старым; ручной запуск со входом `outline_effort`; комментарий в PR, артефакт `golden-decks`; нужен секрет `OPENAI_API_KEY`).
- Параметры запроса и цены моделей LLM — `prompts/models.yaml` (код — `src/core/llm/models.py`; `src/generation/llm_models.py` — реэкспорт для старого движка). Модель — `OPENAI_MODEL`, уровень рассуждений — `OPENAI_REASONING_EFFORT`.
- Тесты: `python -m unittest discover -s tests/unit -t tests/unit` (стандартный unittest, LLM подменяется). Проверка колоды по golden-кейсу ТЗ 7.4 — `python tests/golden/check_case.py <deck.json> <G-01|G-02|G-03>`. Снимок собранных промптов до и после правки `prompts/` — `python tests/golden/prompt_snapshot.py <папка>`.
