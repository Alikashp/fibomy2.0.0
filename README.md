# Fibonacci AI

Telegram-бот и REST API, которые по теме, тексту или документу пользователя собирают готовую презентацию: **редактируемый PPTX** с нативными диаграммами и **PDF**. Пользователь проходит короткий диалог (тип, тема, аудитория, язык, объём, материал), фоновый воркер строит план слайдов через LLM, подбирает вид каждого слайда, пишет текст, подгоняет его под макет без обрезки, рисует PPTX и конвертирует его в PDF.

Аудитория сейчас — студенты и преподаватели, дальше — корпоративные пользователи. К REST API подключён второй бот владельца с **живыми пользователями**, поэтому API меняется только обратно совместимо (`docs/API.md`).

## С чего начать

Порядок чтения для нового разработчика (около часа):

1. **Этот файл:** что где лежит, словарь терминов, быстрый старт, правила.
2. **`docs/ARCHITECTURE.md`:** сервисы, поток данных, этапы ядра, деградация, хранение.
3. **`src/core/pipeline.py`, функция `generate_deck`.** Это всё ядро по порядку этапов: в начале файла — список этапов, в теле — пометки `# 1 INGEST`, `# 2 OUTLINE` и т. д.
4. **`src/core/models/request.py` и `src/core/models/deck.py`.** Это вход ядра (`DeckRequest`) и его главная структура данных (`DeckSpec`). Полное описание — `docs/design/04_CONTRACTS.md`.
5. **Один макет и одна тема:** `layouts/bullets/cards_grid.yaml` и `themes/business_slate.yaml`. Вид слайдов задают эти файлы, а не код.
6. **Запустить тесты и галерею** (раздел «Быстрый старт»): галерея без ключей показывает все макеты во всех темах.

Перед первым PR — раздел «Правила» в конце этого файла и `docs/REVIEW.md`.

### Как ведём документацию (D-080)

- **Код — источник истины.** Документ, разошедшийся с кодом, правится в той же задаче, где это найдено. Требования к тому, каким код должен быть, задаёт `docs/TZ.md`.
- **Документы хранят решения и объяснения, а не перечисления.** Число вариантов, список тем, переменные окружения, роуты — смотрим в источнике (`layouts/`, `themes/`, `.env.example`, `tests/unit/api_contract_v1.json`) или генерируем скриптом, а не переписываем руками.
- **Не подтверждено кодом — так и пишем** («не сделано», «не сверялось»), а не держим в голове.
- **Документация — в той же задаче, что код.** Перенесли файл, добавили этап, сервис, роут или фичу — обновить этот файл, `docs/ARCHITECTURE.md`, файл фичи в `docs/features/` и, для API, `docs/API.md`. Взяли или закончили пункт плана — `docs/ROADMAP.md`.
- **Одно правило — одно место.** Правила репозитория — раздел «Правила» ниже, критерии ревью — `docs/REVIEW.md`, протокол агента — `CLAUDE.md` (D-082); архитектура — `docs/ARCHITECTURE.md`, план — `docs/ROADMAP.md`, API — `docs/API.md`, тесты — `docs/features/quality.md` (D-083). Остальные документы на них ссылаются, а не пересказывают.
- **Проверка в CI:** `python scripts/check_docs.py` — пути в README, CLAUDE.md, `docs/API.md`, `docs/REVIEW.md` и `docs/features/` существуют; каждый роут API описан в `docs/API.md`; каждый документ есть в своей карте (`docs/*.md` — в карте выше, `docs/design/` и `docs/features/` — в своих README); индекс `docs/DECISIONS.md` актуален. Запускается юнит-тестом `tests/unit/test_docs.py`.

## Как устроено

Три сервиса Railway из одного Docker-образа — `bot`, `worker`, `api`; процесс выбирает переменная `SERVICE_ROLE` (`src/start.py`). Бот и REST API принимают запрос, создают строку `decks` в Postgres и ставят задачу в очередь Redis (ARQ). Воркер вызывает ядро `core.pipeline.generate_deck` — INGEST → OUTLINE → SELECT → IMAGES ∥ CONTENT → проверки → FIT → RENDER → CONVERT — и отдаёт PPTX и PDF: в чат или клиенту API (хранилище + webhook).

Главное правило: **`src/core` не знает про Telegram и HTTP.** Порядок этапов знает только `pipeline.py`, этапы друг друга не вызывают.

Схема, путь одного запроса, этапы ядра с файлами, время и параллелизм, деградация, хранение, внешние сервисы — **`docs/ARCHITECTURE.md`**.

## Словарь

| Термин | Что значит | Где определено |
|---|---|---|
| **колода** (deck) | Одна презентация. Id вида `dk_01M4…` (ULID), строка в таблице `decks` | `core/models/ids.py`, `db/models.py` |
| **`DeckRequest`** | Параметры колоды: тема, материал, язык, аудитория, число слайдов, тема оформления. Хранится в `decks.request` | `core/models/request.py` |
| **`DeckSpec`** | Колода целиком как данные: мета и слайды с содержанием. Единственное промежуточное представление: все этапы после OUTLINE дописывают его, рендерер рисует его как есть | `core/models/deck.py` |
| **режим** (`mode`) | `topic` — колода по теме, модель пишет из общих знаний; `material` — по присланному тексту или файлу | `DeckRequest.mode` |
| **`source_mode`** | При материале: `strict` — только материал пользователя, `extend` — можно дополнить | `DeckRequest.source_mode` |
| **`SourceDigest`** | Что извлечено из материала: фрагменты текста и `datasets` | `core/models/digest.py` |
| **dataset** | Таблица чисел из материала с адресами ячеек. Значения диаграмм код берёт отсюда, модель их не пишет | `core/models/digest.py` |
| **outline**, **план** | Ответ OUTLINE: жанр источника, тезисы и `PlannedSlide` на каждый слайд | `core/models/outline.py` |
| **жанр** (`genre`) | Тип источника: `topic`, `report`, `requirements`, `plan`, `article`, `other`. От жанра зависят правила плана | `core/models/outline.py` |
| **kind** | Смысловой тип слайда: `title`, `statement`, `bullets`, `comparison`, `process`, `metrics`, `chart_series`, `chart_share`, `conclusion`, `closing`. Содержание слайда хранится по схеме kind | `core/models/deck.py` |
| **role** | Роль слайда в сюжете: `problem`, `goal`, `results`, `risks`… Влияет на текст, не на вид | `core/models/outline.py` |
| **вариант** (variant) | Раскладка слайда данного kind, например `bullets.cards_grid`. Один kind — несколько вариантов; смена варианта не требует LLM | `layouts/<kind>/<variant>.yaml`, `core/models/layout.py` |
| **`LayoutSpec`** | Загруженный YAML варианта: элементы, рамки, стили, вместимость слотов (`capacity`), условия применимости (`applies_when`) | `core/models/layout.py` |
| **тема** (theme) | Цветовое оформление: палитра, шрифт, декор. Не путать с темой презентации (`input.topic`) | `themes/*.yaml`, `core/models/theme.py` |
| **seed** | Число, от которого детерминированно зависит выбор вариантов: один seed — та же раскладка | `DeckRequest.seed`, `DeckSpec.meta.seed` |
| **fit**, **невлезание** | Подгонка текста под рамки. Текст никогда не режется: кегль → вариант → сокращение моделью → два слайда | `core/fitting/` |
| **деградация** | Запасной путь этапа вместо падения колоды; список — в `DeckSpec.degradations` | `core/pipeline.py` |
| **`DeckError`**, код ошибки | Колода не собралась: `OUTLINE_FAILED`, `RENDER_FAILED`, `UPLOAD_EXPIRED`… | `core/pipeline.py`; коды для клиента — `docs/API.md`, 6 |
| **stage** | Текущий этап колоды для прогресса: `ingest`, `outline`, `content`, `render`, `convert` | `decks.stage`, `GET /v1/decks/{id}` |
| **клиент API** | Внешний сервис с ключом (второй бот): суточный лимит, лимит в минуту, webhook | `api/store.py`, таблица `api_clients` |
| **uploads** | Временное хранилище присланных файлов и текстов; удаляются после обработки | `generation/uploads.py` |
| **golden-корпус**, G-01…G-06 | Набор реальных входов с ожиданиями к колоде; прогоняется настоящей моделью в CI | `docs/TZ.md` 7.4, `tests/golden/` |
| **галерея** | Все варианты × все темы × 4 заполнения без LLM; по ней владелец утверждает дизайн | `tests/gallery/` |
| **старый / новый движок** | Старый — HTML → PDF (`src/generation`), остался только для питч-дека. Новый — PPTX + PDF (`src/core`) | `dialog.engine_for` |

## Быстрый старт

### Локально

Python 3.10, как в образе и CI (3.11 тоже работает). Для PDF и галереи — LibreOffice (`libreoffice-impress`) и шрифты `fonts-liberation`, `fonts-dejavu-core`.

```bash
python -m pip install -r requirements.txt -r requirements-dev.txt   # тем же python, которым запускаете тесты
cp .env.example .env                                                 # и заполнить нужное (ниже)
```

**Тесты** — ключи, сеть, Postgres и Redis не нужны, LLM подменяется:

```bash
python -m unittest discover -s tests/unit -t tests/unit                      # все, включая проверку документации
python -m unittest discover -s tests/unit -t tests/unit -p "test_api*.py"    # контракт REST API
```

**Слайды без ключей** — галерея собирает все варианты тем же путём, что прод, и кладёт `gallery.pdf`, миниатюры и отчёт проверок:

```bash
python tests/gallery/build_gallery.py out/gallery --themes business_slate --fixtures typical
```

**Настоящая колода без Telegram** — нужен только `OPENAI_API_KEY`:

```bash
python tests/golden/run_golden.py --out out/golden --only G-03      # доклад по теме; PPTX, PDF и DeckSpec — в out/golden
```

**Бот, воркер и API** — нужен Redis; бот и воркер работают и без Postgres (пустой `DATABASE_URL`), API — нет: ключи клиентов хранятся в БД. Миграции применяются сами при старте процесса.

```bash
docker run -d -p 6379:6379 redis:7                                                  # REDIS_URL=redis://localhost:6379/0
docker run -d -p 5432:5432 -e POSTGRES_PASSWORD=dev postgres:16                     # DATABASE_URL=postgresql://postgres:dev@localhost:5432/postgres
cd src
python main.py                       # бот (нужен TELEGRAM_BOT_TOKEN)
python -m arq worker.WorkerSettings  # воркер (нужны OPENAI_API_KEY и TELEGRAM_BOT_TOKEN)
uvicorn api.app:app --port 8000      # REST API; ключ клиента: python -m api.keys create --help
```

### Деплой

- **Railway:** три сервиса — bot, worker, api — из одного `Dockerfile`, плюс Postgres и Redis. У каждого сервиса переменная `SERVICE_ROLE` (`bot`, `worker`, `api`); файлы Config as Code не используются (D-062).
- **Что выкатывается:** `main`. По правилам в `main` мёржится только PR с зелёным workflow `tests` (раздел «Правила»); в настройках каждого сервиса Railway стоит включить **Wait for CI** — тогда сборка коммита начнётся только после зелёных проверок GitHub. Включено ли это сейчас, по репозиторию не проверить — сверить в Railway.
- **Порядок:** воркер раньше бота и API — новые аргументы задач должен понимать воркер до того, как их начнут ставить. Миграции применяет каждый процесс при старте под advisory lock, отдельного шага нет.
- **Переменные по сервисам** — шапка `.env.example`. Без чего сервис не работает: бот — `TELEGRAM_BOT_TOKEN`, `REDIS_URL`; воркер — `OPENAI_API_KEY`, `TELEGRAM_BOT_TOKEN`, `REDIS_URL`; api — `DATABASE_URL`, `REDIS_URL`. `DATABASE_URL` нужен всем трём на проде (пользователи, колоды, ключи API). Новая переменная из PR — в «Что проверить после деплоя» с указанием сервиса.
- **CI** (workflow `tests`, `golden`, `siliconflow-probe`) — `docs/features/quality.md`.

### Откат

1. **Railway:** сервис → Deployments → прошлый удачный деплой → Rollback (минуты, образ не пересобирается). Откатывать в обратном порядке выкатки: сначала бот и API, потом воркер.
2. **В репозитории:** Revert смёрженного PR в GitHub → новый PR → мёрж. Пока revert не смёржен, следующий мёрж в `main` выкатит отменённый код снова.
3. **БД не откатывается:** миграции только добавляющие, старый код с лишними колонками работает.
4. **Ограничение — откат через миграцию.** Если откатываемый PR добавил миграцию, старый код на старте падает: `alembic upgrade head` не знает ревизию, записанную в базе (`Can't locate revision`, `db/session.py`; проверено 06.11.2026). Пока это не исправлено (`docs/ROADMAP.md`), такой PR откатывается только revert-ом кода с сохранением файла миграции, а не Rollback на старый образ.

## Правила

Обязательны для всех, кто меняет репозиторий, — людей и агента. В скобках — номер блокера ревью (`docs/REVIEW.md`): нарушение не мёржится.

**Живые пользователи API** (с сессии 3, D-059):
- **REST API `/v1` — только обратно совместимые изменения** (B1). Можно: новые пути, новые необязательные поля запроса, новые поля ответа, новые коды ошибок, значения `stage`, темы. Нельзя: удалить или переименовать поле, сменить тип, сделать поле запроса обязательным, убрать значение перечисления, сменить формат ошибки или смысл кода. Несовместимое — только новой версией `/v2`, старая продолжает работать.
- **Изменили схему — снимок и `docs/API.md` в том же PR** (B2): `python tests/unit/test_api_contract.py --update`. Поведение без смены схемы (лимиты по умолчанию, срок хранения файлов, тексты ошибок) — в `docs/API.md` (таблица изменений 10.1) и в «Что проверить после деплоя».
- **Миграции — только добавляющие** (B3): новые таблицы, колонки nullable или с default, индексы. Откат кода без отката БД должен оставаться безопасным; исключение — только решением владельца.
- **API-тесты зелёные в каждом PR** (B12): шаг «API-тесты (контракт второго бота)» workflow `tests`, локально — команда из раздела «Быстрый старт».

**Ядро:**
- **Текст на слайде не обрезается и не заканчивается «…»** (B4). Невлезание решает `core/fitting/resolve.py`; в схемах ответа LLM нет `maxLength`/`maxItems` — длину проверяет код (D-071).
- **Промпты и параметры моделей — файлами в `prompts/`, не в коде** (B5). Правка промпта — новая строка в `prompts/v2/VERSION` и прогон golden.
- **Вид слайдов — в `layouts/` и `themes/`, не в рендерере** (B8). Рендерер рисует `DeckSpec` как есть и ничего не решает.
- **`src/core` не импортирует бот, API и воркер** (B10); сбой этапа — деградация, а не падение колоды (B11).

**Настройки и секреты:** секреты — только в переменных окружения, никогда в коде, коммитах и документах (B7); настройки читаются только через `src/config.py`, новая переменная — строка в `.env.example` (B6).

**Git и PR:**
- В `main` не пушить, PR не мёржить — мёржит только владелец.
- Ветка — от свежего `main`, с понятным именем (`fix/plan-command`, `docs/prompt-review`). Задача зависит от ещё не смёрженного PR — дождаться его мёржа, не ветвиться от чужой ветки.
- Перед PR — все юнит-тесты зелёные локально; после пуша — зелёный workflow `tests`. С красным CI PR на ревью не отдаётся.
- Описание PR — по `docs/REVIEW.md`, «Автор перед PR»: API-тесты, ссылка на golden, «Что проверить после деплоя».

**Документация** — в той же задаче, что код (B13; правила — «Как ведём документацию» выше). Архитектурное решение — запись в `docs/DECISIONS.md`, итог работы — запись в `docs/PROGRESS.md`.
